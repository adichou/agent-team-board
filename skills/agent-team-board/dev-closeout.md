# dev 提交与待测试收尾

适用于 `/dev <ID>`、`next`、`loop` 的每个条目。用户明确要求不提交时遵从用户，最终说明尚未完成 Git 提交，不宣称完整交付。

## 正常收尾

1. 测试通过后核对 `git status --short`、工作区差异与暂存区差异，列出本单代码、测试和文档。归属不明的混合改动先澄清；不使用 `git add .`，不混入其他任务或他人已暂存的内容。
2. 用 `$ATB report <ID> --framework <框架> --summary "<结果与引入来源>" --by <会话名>` 上报。测量过覆盖率才带 `--coverage`，否则省略。手写 test-report.md 不能代替 report。报告生成后可以补充真实测试明细。
3. 系统收口提交（BUG-20260915-007）：`report` 成功后 atb 在进程内部按认领时快照归因，自动把本单代码、测试、README/design/test-cases、status.json 和 test-report.md 按现行分组规范提交（doc/test/业务，消息带条目编号，只 commit 不 push）——手动 `/dev` 与批量 run 同一口径，Agent 不再手工执行 git 提交（Bash 提交仍会被钩子拦截）。重复 report 只补交报告状态变动，不重复提交；输出 `⚠ 收口提交不完整` 时按提示到任务页「待人工确认」处理，上报与待测试状态不受影响。
4. 用 `$ATB show <ID> --json` 核验状态为 `in-progress`，且 `agentCompletedAt`、`lastReport.at` 对应本轮上报；这才是看板的「待测试」，不是一个可直接设置的 status 值。不得自动置为 done。
5. 核验系统提交的真实 hash、提交文件与差异（`$ATB commit log <ID>`），本单路径无未提交遗漏（含未跟踪文件）；其他任务原有改动允许保留。最终给出条目编号、提交 hash、测试结果及「待测试」，请用户测试后在看板确认完成。

非 Git 项目不初始化仓库、不伪造 hash：report 照常完成，系统按「非 git」口径跳过收口提交并如实说明，仍可上报真实测试结果。收口提交失败、上报失败、状态核验失败或存在未提交遗漏时，分别说明已完成/未完成步骤与错误，不把工作区修改或部分提交描述成完整交付。`report` 成功但收口提交挂起时，说明条目虽进入待测试但交付未完整，按任务页「待人工确认」闭环处理，不擅自回改状态。

## 认领受阻后的明确例外授权

通常先 claim，失败停止。仅在用户明确授权**该条目**例外开发时沿用此授权，不反复询问；其他条目不继承。该授权不允许解除别的条目的挂起、代替人工确认提交、覆盖其他实施者的工作或验收为 done。

已接受或已计划的目标条目，例外修复完成后，可通过 `$ATB status <ID> in-progress` 再 `$ATB report <ID> ...` 完成状态收尾（进入开发时点自动拍快照，report 后同样系统收口提交），并在 design/报告记录授权与原始阻塞。不要手改 status.json，不把 submitted/done 强行迁移，不删除锁、不改挂起账本或关闭保护。若执行端实际拒绝该操作，保留已完成工作并明确报告阻塞；用户授权不意味着可绕过执行端的拒绝。

## loop

每项完成测试 → report（系统收口提交）→ 状态与提交核验，再取下一项。普通认领冲突/开发错误按 loop 规则记录后跳过；收口提交挂起、上报失败或遗留归属不明改动时停止继续取单，避免扩大混合现场。不得用一次性结束汇总代替每项收尾核验。
