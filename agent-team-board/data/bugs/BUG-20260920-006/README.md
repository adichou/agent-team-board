# BUG-20260920-006 为什么在版本计划详情页面，点击合并到 main 按钮没有响应

- 状态：submitted（待人工接受）
- 归属：独立 Bug（引入来源见 design.md）
- 创建：2026-09-20T15:52:24.790Z

## 现象

按登记口径：在构建模块「版本计划」页签的版本详情中，点击「合并入 main」按钮后**没有任何可感知的界面反馈**——确认弹窗不出现、无 toast、无加载指示，体感即标题所述「按钮没有响应」。

经源码核实（2026-09-20），「合并入 main」共有两处入口，均存在点击无反馈的路径：

1. **详情页「合并入 main」步主按钮**（`scripts/web/build.js` `renderMergePane`，2052 行）：禁用条件为 `已合并(merged) / 前置门禁锁定(gate.locked) / 当前分支不在 dev / 全局合并执行中(state.mergeBusy)` 四项任一。按钮禁用后（半透明样式，`scripts/web/style.css` 360 行 `.btn:disabled { opacity: 0.5 }`）浏览器不触发 click 事件，**点击无任何反馈**，原因仅存在于悬停 title 中；且 title 归因有缺陷——禁用由「不在 dev」或「合并执行中」导致时，title 取值 `gate?.reason || '前置条件未满足'`（2052 行），在门禁未锁时一律显示「前置条件未满足」，**与真实禁用原因不符**（真实原因分别是「请自行切换回 dev 后重试」与「合并中，请勿重复触发」；前者页面上方 devBar 有红字提示，但按钮 title 本身误导）。
2. **点击处理静默返回**（`scripts/web/build.js` `openMergeConfirm`，997–1002 行；`doMerge` 同口径 1004–1006 行）：`if (!v || state.mergeBusy) return;` ——当 `findVersion(verId)` 找不到版本（如该版本已在另一标签页 / 窗口被删除，本页 DOM 未刷新、按钮残留）或全局合并执行中时，**点击后直接 return，无 toast、无弹窗、无任何状态变化**。
3. 附带不一致（同链路核实）：左侧版本卡片行内的「合并入 main」按钮（`scripts/web/build.js` 1866 行）禁用条件只看 `merging / merged / mergeBusy`，**不检查文档门禁与「是否在 dev」**——draft 版本文档未提交或不在 dev 时卡片按钮可点击、能打开确认弹窗，确认后才被后端 `POST /api/build/version/merge`（`scripts/server.mjs` 2414–2471 行，`assertOnDev` / `assertMergeDocsGate` 等守卫）以 409 + toast 拒绝；而同样状态下详情页按钮已禁用。两处入口可用性口径不一致，用户在详情页遇到的禁用无反馈与卡片页遇到的「能点但失败」形成反差，加剧「没反应」的困惑。

登记用户实际命中的精确场景（禁用态点击、静默 return、还是其他环境因素）**待确认**；上述三条为已核实的全部可复现无响应路径。

## 复现步骤

前置：项目目录运行 `atb serve`（默认端口 8888，`ATB_PORT` 可覆盖），浏览器打开 `http://localhost:8888`，顶栏选中该项目；构建模块已有一张 draft 版本卡片（已关联条目与 commit）。

**路径一：禁用态点击无反馈（最易复现）**

1. 保持该版本**未在「文档编写」步提交文档**（或把当前分支从 dev 切到 main），进入「构建」模块「版本计划」页签，选中该版本卡片。
2. 右侧详情切换到「合并入 main」步：页面显示「暂不可合并：…」提示（文档未提交时）或红色分支提示（不在 dev 时），底部「合并入 main」按钮呈半透明禁用态。
3. 直接点击该按钮：**无弹窗、无 toast、无任何反馈**；原因只有鼠标悬停才能看到，且「不在 dev」场景下 title 显示「前置条件未满足」而非「请切换回 dev」——即标题所指「点击没有响应」的界面侧。
4. （对照）把文档提交齐 / 切回 dev 后刷新，按钮恢复可点，点击能正常弹出「合并入 main 确认」弹窗——确认是禁用反馈缺失而非合并功能整体失效。

**路径二：点击处理静默返回（竞态）**

1. 两个浏览器标签页打开同一看板；标签页 A 选中某 draft 版本并进入「合并入 main」步（或停留卡片列表）。
2. 标签页 B 删除该版本计划；标签页 A **不刷新页面**。
3. 回到标签页 A 点击「合并入 main」按钮（DOM 仍在、按钮非禁用）：`openMergeConfirm` 中 `findVersion` 返回 null 直接 return——**无弹窗、无 toast、无任何反馈**。

**路径三（对照，非无响应）：卡片与详情口径不一致**

1. 回到路径一的前置（文档未提交或不在 dev），观察左侧版本卡片行内「合并入 main」按钮：**可点击**（卡片禁用条件不含文档门禁 / dev 分支检查）。
2. 点击后确认弹窗可正常打开，点「确认合并」才收到 toast「✕ 合并失败：文档尚未编写提交… / 当前分支是 main，不在 dev…」——同样状态下详情页按钮已禁用，两处行为不一致。

## 期望行为

- **点击必反馈**：「合并入 main」入口（详情页主按钮与卡片行内按钮）在被点击时，只要不可执行，就以可感知方式告知**真实原因**——已合并（merged）/ 合并执行中（merging 或 mergeBusy）/ 文档门禁未过（未编写、未提交、范围过期）/ 当前分支不在 dev / 暂无关联条目，逐项与后端守卫（`scripts/server.mjs` 2414–2471 行）与五步门禁（`scripts/lib/publish-flow.mjs` 257–288 行）的 reason 口径一致；反馈形式为 toast 或界面内联提示（实现方式由开发阶段定夺，含禁用态点击如何捕获）。
- **禁用 title 归因准确**：详情页按钮 title 与实际禁用原因一一对应——「不在 dev」显示切回 dev 的提示、「合并执行中」显示勿重复触发、门禁锁定显示 gate.reason，不再统一回落「前置条件未满足」。
- **静默 return 补反馈**：`openMergeConfirm` / `doMerge` 的守卫分支不再无声——版本不存在（已被删除）时提示刷新列表；全局合并执行中时提示稍候，点击不再「消失」。
- **两处入口口径一致**：卡片按钮与详情按钮在同样状态下的可用性 / 反馈口径一致（统一检查门禁与 dev 分支，或统一放行至确认后由后端拦截并 toast，取哪种由开发阶段定夺）。
- **可合并路径零回归**：draft / failed、文档已提交、在 dev 时，点击 → 确认弹窗 → 确认合并 → 执行反馈（成功 / 失败 toast 与详情刷新）全链路维持现状。
- **待确认（需人工拍板）**：
  1. 禁用按钮的点击反馈实现方式：HTML `disabled` 元素不触发 click，需包一层捕获点击的容器或改用 `aria-disabled` + 样式禁用——是否与既有「禁用 + title 说明」的全局口径（如开发启动、批量执行等按钮）保持一致还是本单单独增强，需确认。
  2. 反馈文案是否进 i18n（若为 toast / 界面文案，须中英同步 `scripts/web/i18n.js`）。
  3. 登记用户实际命中场景（路径一 / 路径二 / 其他）待确认，不影响三条路径均按上述期望修复。

## 验收说明

1. **禁用态点击反馈**：对「文档未提交」「不在 dev」「合并执行中」「已合并」「暂无关联条目」五种状态逐一实测——点击（或等效触发）详情页与卡片「合并入 main」入口，均出现可感知反馈且**原因准确**（与该状态真实拦截原因一致，不再出现「前置条件未满足」误归因）。
2. **title 归因**：五种状态下按钮悬停 title 逐一断言与真实原因对应；中英文案同步（`scripts/web/i18n.js`）并跑 i18n 相关测试。
3. **静默路径**：双标签页删除版本后不刷新点击合并入口 → 有「版本不存在 / 请刷新」类反馈而非无响应；全局合并执行中点击 → 有「合并中，请稍候」类反馈（含 `openMergeConfirm` / `doMerge` 两处守卫分支）。
4. **两处入口一致**：构造同一版本在「文档未提交」「不在 dev」状态，卡片按钮与详情按钮的可用性 / 反馈口径一致，不再一端可点一端禁用。
5. **正常链路回归**：可合并版本走完 点击 → 确认弹窗（提交清单展示正确）→ 确认合并 → 成功 toast「✓ 已合并入 main（…）」/ 失败 toast 与版本详情错误展示；合并执行期间按钮禁用防重复触发维持。
6. **既有口径零回退**：merging / merged 锁定、文档门禁（scopeStale 重提交）、隔离合并增量重试（只补未合并条目）、与产品发布互斥（release git 目标运行时拒绝合并）等行为均与现状一致；`npm test`（`node scripts/tests/run-all.mjs`）全量通过，新增本单测试覆盖上述点击反馈与 title 归因断言。
7. **文案与外观**：新增 / 变更文案中英同步；深浅色与 Electron 桌面壳内禁用态与反馈样式表现一致。

## 界面展示

可交互演示：[`./ui-demo.html`](./ui-demo.html)（单文件、内联 CSS / JS、无外网依赖、无构建步骤，浏览器直接打开可交互；数据为模拟，不连真实看板、不发真实请求、不执行真实 git 操作）。

- 界面布局：还原构建模块「版本计划」页签——左侧版本卡片列表（名称 + 状态章 + 计划号 / 关联数 + 行内「合并入 main」按钮），右侧详情按五步流程导航（版本计划 → 关联条目与提交 → 文档编写 → 合并入 main → 正式发布），合并步面板含发布范围 / 隔离分析 / 分支提示 / 门禁提示 / 主按钮；含合并确认弹窗。
- 交互行为：一键切换「当前（缺陷）/ 修复后（期望）」对照；可切换版本状态（文档未提交 / 已提交可合并 / 合并执行中 / 已合并 / 已被删除竞态）与当前分支（dev / main）——缺陷态下禁用按钮点击无任何反馈且 title 误显「前置条件未满足」、竞态按钮点击静默无响应；期望态下同样操作逐一给出真实原因反馈（toast + title 归因正确），并可走通 点击 → 确认弹窗 → 执行中 → 成功 / 失败 全链路。
- 状态反馈：合并结果 toast（成功 / 失败含原因）；列表可切「正常 / 空 / 加载中 / 加载失败（可重试）」；深浅色随系统并可手动切换。
