# 设计 — BUG-20260908-012 动态候选变化后重复启动完善任务不幂等

> 由 Agent 在 /dev 开发前补充，人可随时批注。

## 引入来源（源单）

本 Bug 由哪个需求 / Bug 引入？登记时可暂空或写「未定位」，修复阶段必须归因（三选一，禁止编造）：

- 引入来源：REQ-20260908-020（已经 `atb list` 核验存在，in-progress）
- 排查过程：`createRefineBatch` 的「同模式队尾幂等」判断源自 REQ-20260906-025（队尾冻结候选与本次一致 → created=false），
  由 REQ-20260907-003 沿用进 refine-store。REQ-20260908-020 把候选口径从「创建时冻结快照」改为
  「每轮实时读取全部已接受单」（absorbNewRefineCandidates），但其 design.md 已预警（第 30 行
  「未结束批次幂等判断改按『进行中任务』判断」、第 106 行「候选从冻结快照改实时读取后需重新评估队尾一致判断」），
  实施未跟进：幂等分支仍要求队尾冻结候选 id 列表与当前新鲜候选完全一致。于是「创建任务 → 新接受单 B →
  重复 create」时两者不一致，落入「新候选」分支新建第二个未结束批次，违反用例 27（单进行中任务与重复启动幂等）。

## 根因分析

`scripts/lib/refine-store.mjs` `createRefineBatch`：

- 幂等条件为 `JSON.stringify(队尾候选 ids) === JSON.stringify(freshNow)`，只在候选集合完全一致时命中；
- 动态候选口径下，创建任务后新接受的单会使 freshNow 增长，等式必然不成立；
- 随后「新候选」分支仅排除已冻结条目，新单 B 不在任何未结束批次中 → 新建 RFB-…-002，
  `unfinishedRefineBatches` 出现两个未结束批次，D04 断言 `again.batchId === b.batchId` 失败。

## 方案

同模式幂等改为「按进行中任务判断」（非勾选范围路径）：

- 存在同模式未结束批次（队尾）时，重复 `refine create` 一律幂等返回该批次（`created: false`，
  `queued/queuePosition` 口径不变），不再比较候选集合；新增候选由原批次每轮 `refine next` 经
  `absorbNewRefineCandidates` 实时吸收（每轮实时读取口径，用例 4），不新建第二个未结束批次。
- 勾选范围（`--ids`）创建路径维持原「候选一致才幂等、否则按剩余候选新建」口径不变。
- 既有口径不回退：候选完全一致幂等返回（新逻辑的子集）、无候选报错
  （「没有可完善候选…」在前置校验抛出，顺序不变；「均已进入更早的未结束完善任务」在
  无同模式未结束批次、候选全部冻结于其他模式批次时仍可触发）。
- 配套文案：CLI 幂等输出「队尾候选一致（幂等返回…）」改为「已有未结束的同模式完善批次（幂等返回…）」；
  Web toast「候选一致（幂等返回）」同步改为「已有未结束任务（幂等返回）」，避免与实际语义不符。

## 风险与边界

- 同模式「想为新增候选单开第二个批次」的旧用法不再可用：新单一律并入进行中批次（与需求用例 27 一致）；
  需要分批时用 `--ids` 勾选或等当前批次结束。
- 跨模式（zcode/codex 两条完善线）不变：仍按「已冻结条目不入新批 + 队列 FIFO」执行。
- 存量两个未结束批次的数据不做迁移：队列 FIFO + 领取排队保护可自然消化（队首批次先跑完）。
- 只改 refine 侧；开发批次（batch.mjs，REQ-20260906-025「有未结束批次时新建入队」语义）不在本单范围。
