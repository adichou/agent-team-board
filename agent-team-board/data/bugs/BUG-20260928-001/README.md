# BUG-20260928-001 版本计划的已合并标签应在文档与翻译合并后再显示。

- 状态：submitted（待人工接受）
- 归属：独立 Bug（引入来源见 design.md）
- 创建：2026-09-27T16:06:36.052Z

## 现象

「发布」模块版本计划的绿色「已合并」标签在「挑选合并」完成时即显示，早于「文档与翻译」合并入 main，标签口径与实际合并进度、发布门禁不一致：

- 版本状态机（`scripts/lib/build-store.mjs` 的 `finishMerge`）：所选条目提交全部 cherry-pick 并入 main 即把版本置为 `merged`——此时只完成五步流程第 2 步「挑选合并」（代码合并）。
- 五步流程第 4 步「文档合并」尚未执行：发布文档与翻译提交（第 3 步「文档与翻译」产出、含语言集内文档与翻译的 docs: 提交）还没有 cherry-pick 重放进 main，`v.docsMerge` 无落账。
- 但界面已显示绿色「已合并」标签（`scripts/web/build.js`：`STATUS_LABEL.merged = '已合并'`、`STATUS_CLS.merged = 'st-ok'`），出现在三处：
  1. 左侧版本卡片标题旁状态标签（`versionChip` → `statusChip`）；
  2. 右侧详情标题旁状态标签；
  3. 删除确认弹窗中的状态标签。
- 左侧卡片 meta 行「阶段」在 `merged` 时同步显示「正式发布」，进一步加重误导（合并尚未走完，文档未合并、更未推送）。
- 同一时刻「发布」步与推送接口门禁仍会拦截：「发布文档尚未合并入 main：请先完成「文档合并」步骤」（`scripts/server.mjs` `/api/build/release/push`，`scripts/lib/publish-flow.mjs` release 步门禁）——与「已合并」标签自相矛盾。

影响：用户看到「已合并」会误以为该版本的代码、发布文档与翻译都已合入 main，实际文档与翻译尚未合并；需靠发布时被门禁拦截才暴露差异。

## 复现步骤

1. 打开「发布」模块 → 版本计划页签，选择（或从已完成单新建）一个版本计划，并关联条目与提交。
2. 进入「挑选合并」步执行合并并等待成功：条目提交全部并入 main，版本 `status` 变为 `merged`。
3. 观察左侧版本卡片：标题旁显示绿色「已合并」标签，meta 行显示「阶段 正式发布」；点进右侧详情，标题旁同样显示「已合并」。
4. 不执行第 4 步「文档合并」（保持 `v.docsMerge` 无落账），刷新页面后再次确认：卡片与详情仍显示「已合并」。
5. 进入「发布」步尝试「推送主分支」：被拦截，提示「发布文档尚未合并入 main：请先完成「文档合并」步骤，再推送主分支」——与第 3/4 步看到的「已合并」标签矛盾。

（第 2-5 步可对照 `scripts/web/build.js` 的 `statusChip` / `renderDocMergePane` 与 `scripts/server.mjs` 的 `/api/build/release/push` 门禁核验。）

## 期望行为

- 「已合并」标签（绿色口径）只在文档与翻译提交合并入 main 之后显示：即 `status = merged` 且 `v.docsMerge` 已落账（重放提交 / main 头证据在账）。
- 文档与翻译未合并前（仅挑选合并完成），三处状态标签位置显示能区分「代码已合并、文档与翻译未合并」的中间态标签与文案（具体文案与样式开发阶段定稿），不得显示「已合并」。
- 已发布版本仍优先显示「已发布」（`versionChip` 现有优先级不变：`release.published` 优先于合并状态）。
- 「计划中 / 合并中 / 失败」三态标签口径不变；版本数据状态机与发布门禁不变——本 Bug 只收敛「已合并」标签的显示口径，不改 `finishMerge` 的状态判定与合并 / 发布门禁逻辑。

## 验收说明

1. 挑选合并完成（`status = merged`）且 `v.docsMerge` 无落账：左侧卡片、右侧详情标题、删除确认弹窗均不显示「已合并」；显示的中间态文案需含「文档（与翻译）未合并」语义，且与「计划中 / 合并中 / 失败 / 已发布」可区分（实现定稿文案：「代码已并入 · 文档与翻译未合并」，样式 st-wait 非绿）。
2. 执行「文档合并」成功（`v.docsMerge` 落账）后：上述三处显示「已合并」。
3. 已发布版本（`release.published`）：仍显示「已发布」，不受本改动影响。
4. 「计划中 / 合并中 / 失败」标签与现有行为一致：merging 禁删、失败显示合并失败原因与重试入口等不受影响。
5. 新增 / 调整的中文文案在英文界面（`scripts/web/i18n.js`）有对应英文翻译。
6. 存量数据兼容：存量已推送 / 已发布计划不受影响；存量 `merged` 且已有 `docsMerge` 落账的显示「已合并」；存量 `merged` 无 `docsMerge` 落账的按新口径显示中间态，不误显示「已合并」。
7. 发布门禁行为不变：`v.docsMerge` 落账前推送主分支仍被拦截（`/api/build/release/push` 与 release 步门禁文案不变）。
8. 左侧卡片 meta 行「阶段」文案与状态标签口径一致（已随本单一并调整：`merged` 且 docsMerge 无落账显示与标签相同的中间态文案，docsMerge 落账后维持既有「正式发布」；实施结论见 design.md）。

## 界面展示

涉及 UI：版本计划状态标签（列表卡片 / 详情标题 / 删除确认弹窗）的显示时机与文案。可交互演示见 [./ui-demo.html](./ui-demo.html)（单文件、无外网依赖，浏览器直接打开）：

- **界面布局**：复刻「发布」模块版本计划页签——左侧版本卡片列表（名称 + 状态标签 + 删除按钮、meta 行：计划号 / 版本号 / 阶段 / 关联单数 / 更新时间），右侧版本详情（标题旁状态标签、五步流程导航「选择条目与提交 → 挑选合并 → 文档与翻译 → 文档合并 → 发布」、当前步内容区）；顶部提供「缺陷现状 / 修复后口径」对比开关与场景切换（主流程 / 空列表 / 加载中 / 合并失败）。
- **交互行为**：点击左侧卡片切换选中版本；右侧步骤导航可切换五步；在「挑选合并」「文档合并」「发布」步提供模拟操作按钮推进版本状态；卡片「删除」打开确认弹窗（含状态标签，演示不真删）；「重试挑选合并」从失败态恢复走合并流程。
- **状态反馈**：缺陷现状下，挑选合并完成即显示绿色「已合并」（阶段「正式发布」），此时尝试推送被门禁拦截，与标签矛盾；修复后口径下同一时刻显示中间态标签「代码已并入 · 文档与翻译未合并」，完成文档合并后才显示「已合并」；覆盖计划中 / 合并中（进行中反馈）/ 失败（原因 + 重试）/ 已发布 / 空列表 / 加载中各态，支持深浅色自适应。
