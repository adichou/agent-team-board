# BUG-20260914-022 历史补交完成后，同路径新改动导致旧提交确认记录复活

- 归属：独立 Bug
- 引入来源：REQ-20260914-001（历史恢复按当前路径脏状态判断旧运行；已核验）
- 创建：2026-09-14T15:56:18.171Z
- 状态以看板机器记录为准，本文不维护状态副本。

## 现象

历史运行已经补交或撤销后，新任务再次修改同一文件，旧运行又被恢复到「待人工确认」阻塞队列，显示「历史部分提交」「仍未入库」与「部分提交，开发未完成」。用户难以区分真实的新提交失败与已经处理的旧记录。

已有定位记录记载截图中 12 条由 BUG-20260914-020 的真实提交失败和 11 条历史恢复记录构成；这是当时现场，当前数量待确认。现有 design.md 记载涉及 scripts/web/build.js、scripts/web/i18n.js；补交盘点见 [历史补交记录](../../commit-recovery-20260914.md)，其中记录了 REQ-20260913-006 的 6aee3737、BUG-20260914-002 的 baede007。实施时仍须逐项核对实际差异，不把报告或提交消息当作全部处理完成的唯一证明。

代码核对：scripts/lib/confirm-store.mjs 的 legacyConfirmViews 遍历历史 auto-commit.json，筛选存在 pendingManual、无已有确认记录、run.phase 为 reported 的运行，并以 pendingManual 路径当前的 Git 状态是否 clean 决定恢复。这个条件不能区分旧遗留内容和后来新任务的修改；当前恢复视图还将 heldGroups 置空。

## 复现步骤

在隔离测试仓库准备数据，避免改动真实项目账本或提交现场：

1. 准备历史运行 A：阶段为 reported，auto-commit.json 包含 itemId 和 pendingManual 路径 p，没有该条目的活动或历史确认记录。
2. 将 A 遗留的实际改动完整补交，使 p 干净；保留原始 auto-commit.json 作为历史事实。
3. 调用 legacyConfirmViews 或刷新待确认队列，确认 A 此时未显示。
4. 以新任务 B 修改同一路径 p，保持这批新修改未提交。
5. 再次调用恢复函数或刷新看板：当前实现会把 A 恢复为历史部分提交，误把 B 的修改解释为 A 尚未入库。
6. 同时准备一个真实未解决的新运行提交失败，观察旧误报与新失败混在队列中的情况。

已撤销历史方案采用相同思路复现：先有可核验的撤销结果，再由新任务修改原路径。具体撤销证明与内容边界待实施时逐项确认。

## 期望行为

- 恢复依据是特定运行遗留内容是否已完整处理，而不是同路径当前是否脏。完整补交或明确撤销并经核验登记后，该旧运行在刷新、服务重启和同文件再次修改后均不复活。
- 处理依据须绑定条目、运行及原账本，并覆盖 pendingManual 与 heldGroups.test/biz。部分补交、遗漏暂扣测试、证明不匹配或无法核验时，不能当作已解决。
- 保留原始账本；独立保存可信处理结果。读取待确认列表不自动制造处理记录。不能仅凭单号命中或文件曾被提交来消除阻塞。
- 当前历史条目逐一核验迁移。已撤销方案不能登记为已补交，也不能为了消除提示重新引入撤销代码。
- 新运行独立判断；BUG-20260914-020 的真实失败仍保留。本 Bug 不以确认旧记录代替人工验收，不负责推断其被截断的 Git 错误原因。

## 界面展示

[打开交互演示](./ui-demo.html)。演示采用截图中的 AI 开发待确认列表布局：顶部标题与数量、卡片上的条目/运行、阻塞原因、部分提交提示、查看与重新核验入口。示例 ID 和计数仅用于演示，不表示现场账本已被修复。

交互：切换「缺陷现象／期望修复后」及正常、空、加载、失败状态；正常状态中旧记录在修复后消失，真实新失败仍可查看。点击「查看并确认」仅展示说明，点击「重新核验」模拟加载并恢复列表，不写任何项目数据。

状态反馈：正常展示仍需处理的记录与数量；空状态明确没有待确认事项；加载时显示核验中且隐藏旧列表，防止把暂时无数据误认成解决；失败时显示读取失败与重试入口，不显示零条成功。卡片沿用现有信息层级，无需新增生产界面开关；演示切换器仅为验收对照。

## 验收说明

- [ ] 运行 A 的遗留未处理时显示；完整补交并登记可信结果后隐藏。
- [ ] A 处理后，新任务 B 修改同路径，A 仍隐藏；刷新与重启恢复结果一致。
- [ ] 仅处理部分 pendingManual，或遗漏 heldGroups 中任一实现/测试路径，不能隐藏未解决运行。
- [ ] 处理记录对应错误条目/运行、原账本不匹配、证明提交不在当前有效历史中时，不误判完成。
- [ ] 已撤销方案有明确核验依据后不复活；未知依据保留待核验，不批量强制清除。
- [ ] 旧运行处理结果不作用于同条目的新运行；真实新提交失败继续展示并阻塞。
- [ ] 迁移逐条记录依据，原 auto-commit.json 保持原貌，读取接口无处理记录写入副作用。
- [ ] 界面数量与实际待确认集合一致，加载/失败不冒充空状态；演示可离线打开并切换前后及四种状态。
