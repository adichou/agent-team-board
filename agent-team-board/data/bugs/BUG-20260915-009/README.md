# BUG-20260915-009 需求模块的 AI 开发和 AI 分析按钮，点击后要分别精准跳到任务模块中的 AI 开发和 AI 分析的页面

- 状态：submitted（待人工接受）
- 归属：独立 Bug（引入来源见 design.md）
- 创建：2026-09-15T01:33:45.664Z

## 现象

需求模块（「需求」页签）列表头的常驻快捷入口是同一个按钮 `#laneQuickEntry`，按筛选档切换文案：「已接受」档显示「▶ AI 分析」、「已计划」档显示「▶ AI 开发」。点击后确实会切到任务模块，但落地的子面板不总是按钮所指的那一个：页面停留在本会话上一次渲染的另一个子面板（如点「▶ AI 分析」却显示「AI 开发」页签高亮 + 批量开发面板内容），用户有时还得手动再点一次目标页签才到位。

出现是间歇性的：本会话内首次进入该子面板、或目标子面板数据发生了变化时，跳转正常；仅当目标子面板的数据自上次渲染后无变化（无进行中任务、候选 / 记录不变，是最常见的稳态）时复现。已接受行的完善徽标（未完善 / 完善中 / 已完善）与快捷按钮共用同一跳转链路（`gotoRuns('refine')`），同样受影响。

## 复现步骤

1. 打开看板 Web 前端，进入任务模块，先点「AI 分析」页签看一眼面板，再切到「AI 开发」页签（两个子面板各自完成过一次渲染，当前页面显示 AI 开发面板）。
2. 保持无进行中任务、候选 / 记录不变（数据稳态），点导航「需求」回到需求模块。
3. 切到「已接受」筛选档，点击列表头的「▶ AI 分析」。
4. 观察：进入了任务模块，但「AI 开发」页签仍高亮、主体仍是批量开发面板——需手动点「AI 分析」页签才切换到位。
5. 反向同理：让面板先停留在「AI 分析」子面板，回需求模块切「已计划」档点「▶ AI 开发」，落地仍停留在 AI 分析子面板。

## 期望行为

- 「已接受」档点「▶ AI 分析」：任务模块打开的瞬间即呈现「AI 分析」子面板（该页签高亮、主体为 AI 分析面板），无需任何手动切换；「已计划」档点「▶ AI 开发」同理精准落到「AI 开发」子面板。
- 跳转语义维持现状：仅导航，不创建任务、不弹确认（创建仍由面板内「启动」承接）；数据刷新仍走既有轮询与签名剪枝（不打断面板内输入），但「进入任务模块时呈现正确的子面板」不得依赖数据是否变化——无缓存数据时可先渲染目标面板的加载态。
- 完善徽标等共用 `gotoRuns` 的入口同步受益于同一修复。

## 验收说明

- 复现场景（两子面板本会话内先后渲染过、随后目标面板数据无变化）下：点「▶ AI 分析」落地即 AI 分析页签高亮 + AI 分析面板内容；点「▶ AI 开发」落地即 AI 开发页签高亮 + AI 开发面板内容；两个方向都要验证。
- 既有场景不回退：首次进入子面板、目标面板数据变化时照常渲染；任务模块内手动切换页签、轮询签名剪枝行为不变；完善徽标跳转（`gotoRuns('refine')`）、全局任务总览跳转（`gotoProjectTask` → `gotoRuns`）不回退。
- 快捷入口仍仅导航：无 `/api/batch/create`、无 `/api/refine/start` 等创建 / 启动请求，无确认弹窗（REQ-20260909-007 既有口径）。
- 建议自动化测试：vm 模式模拟「两子面板先后渲染 → 目标面板数据不变 → 点快捷入口」，断言落地面板 DOM（含高亮页签）与目标 mode 一致（现有 lane-quick-entry-20260909-007.test.mjs 未覆盖签名剪枝命中导致不重渲染的路径）。

## 界面展示

可交互演示：[./ui-demo.html](./ui-demo.html)（单文件 HTML，无外网依赖，浏览器直接打开；支持「缺陷（当前）↔ 修复后」一键对比、深浅色切换，还原需求模块快捷入口 → 任务模块子面板的完整跳转链路）。

- 界面布局：左侧还原需求模块——第四行筛选档 chips（待接受 / 已接受 / 已计划…，可切换）与列表头工具栏（排序占位 + 靠右的快捷入口按钮「▶ AI 分析 / ▶ AI 开发」，随档位切换文案与显隐）及若干条目行（已接受行带未完善 / 已完善徽标）；右侧还原任务模块——「AI 分析 | AI 开发」一级页签与对应面板主体（AI 分析面板：候选统计 + 启动区 + 待完善队列；AI 开发面板：已计划队列 + 启动区）。顶部为演示控制条：缺陷 / 修复模式切换、重置，以及「目标面板数据有变化」开关（用于复现「有时才出现」的间歇条件）。
- 交互行为：点快捷入口 → 切到任务模块并按当前档位定向（已接受 → AI 分析、已计划 → AI 开发）；任务模块内两个页签可手动切换；演示内点「需求」可返回需求模块重演；缺陷模式下当目标面板数据无变化（签名剪枝命中）时落地停留在上次渲染的另一子面板——面板上会出现演示标注说明「需手动切换」，手动点页签即可恢复正确呈现；修复模式下无论数据是否变化，进入即呈现目标子面板（无缓存数据时先显示「加载中…」）。
- 状态反馈：正常态——落地页签高亮与按钮所指一致，附「精准跳转」绿色标注；缺陷态——落地页签与按钮所指不符，附红色标注与原因说明（数据签名无变化 → 未触发重渲染 → 残留上次面板）；「目标面板数据有变化」开启后缺陷模式也会正常渲染，直观解释「有时正常、有时要手动切」的间歇表现；每次跳转在下方事件流里记录 mode / 实际渲染面板 / 是否命中剪枝，便于核对。

## 初步定位（供开发参考，已验证）

- 入口绑定：`scripts/web/app.js` 中 `$('#laneQuickEntry')` 点击 → `gotoRuns(state.reqFilter === 'accepted' ? 'refine' : 'develop')`，`gotoRuns(mode)` 会正确设置 `state.batch.mode`——mode 本身无误。
- 缺陷机制（vm 模拟已复现）：离开任务模块时 `setView` 仅隐藏 `#runsView`，`#batchDrawer` 保留最后一次渲染的子面板 HTML；而面板重渲染被签名剪枝拦截——`refreshRefine()` 的 `if (sig === state.refine.sig) return;` 与 `refreshBatch()` 批量开发分支的 `if (sig === state.batchSig) return;`。目标子面板数据无变化时不调用 `renderBatchDrawer()`，残留的另一子面板（错误页签高亮 + 错误内容）就成为落地页；手动点页签走无条件 `renderBatchDrawer()`，故手动切换始终有效。
- 首次进入（签名初值空）与数据变化时签名必然不同、正常渲染，与「有时出现」的观察一致。
