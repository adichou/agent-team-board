# BUG-20260916-002 任务记录重新执行无法续接已认领后 blocked 的条目

- 状态：submitted（待人工接受）
- 归属：独立 Bug（引入来源见 design.md）
- 引入来源：REQ-20260908-026（引入任务记录「重新执行」及其终态承接路径——终态任务以该条目重建新的待启动任务；该路径经 `createBatch` scoped ids 走「已计划且未认领」候选过滤，未覆盖 blocked 后仍被原 owner 认领的条目；经 `atb list` 核验存在）
- 创建：2026-09-16T01:47:43.508Z

## 现象

复现：条目被原 worker 认领后因边界待确认上报 blocked；确认边界后在任务记录页点击重新执行。实际：提示“指定的条目均不可入队：可能已被认领或不在已计划状态”。预期：生成续接提示词，指示新执行代理沿用原 owner 续认，按单项流程继续实施、测试、上报；不走普通新批次入队，不复用终态旧运行。验收：提示词携带条目编号、原认领身份、项目根与 README/design/worker-spec 文档入口；执行前核对旧 worker 已停止且无活动 worker；使用现有同 owner 续认，不冒充人工接受或完成。仅登记，不实施；不扩展为 hold 复工方案。

## 复现步骤

（依据源码核实，2026-09-16 文档讨论第 1 轮补全）

1. 条目被 worker 认领（in-progress、owner=X）后上报 blocked 回执：运行记为终态 blocked，条目业务状态保持 in-progress、owner 不变（`scripts/lib/batch.mjs` finishRun；`blocked` 属 `FINAL_RUN_PHASES`）。
2. 本轮任务结束（实时队列取空后收尾为 finished，或被终止）。
3. 任务记录页该 blocked 记录仍在「重新执行」可操作集合内（`scripts/web/app.js` runAttemptsHtml：failed / interrupted / blocked 均可重试）。
4. 点击后前端判定任务已终态，走「按原配置重试本项」重建路径 `createBatchAndCopy({ids:[条目]})`（`scripts/web/app.js` retryRunFromRecord）。
5. `createBatch` 按「planned 且未认领」过滤候选，该条目仍 in-progress 被过滤出局 → scoped 空集 → 抛出「指定的条目均不可入队：可能已被认领或不在已计划状态」（`scripts/lib/batch.mjs:525`）。
6. 另一分支：任务仍活跃（未结束）时点击走 `/api/batch/retry` → retryRun，对被认领条目同样拒绝并指引人工「回到已计划且未认领」（`scripts/lib/batch.mjs:809-813`）——两条分支都无法续接。

## 期望行为

- 「重新执行」遇到「blocked 终态记录 + 条目仍被原 owner 认领」时，不再尝试普通新批次入队，而是生成**续接提示词**并自动复制（复制失败可展开手动复制，沿用现有交互），指示新执行代理：
  - 沿用**原认领身份（原 owner）**执行 `atb claim <条目> --by <原owner>` 续认——现有同 owner 幂等续认机制（`scripts/lib/core.mjs` claim：in-progress 同 owner 放行补锁），不修改人工管理的业务状态、不把条目退回已计划；
  - 按单项流程（/dev 口径：读文档 → TDD → `report` 不带 `--run` 收口）继续实施、测试、上报；
  - 不走普通新批次入队、不复用终态旧运行、不新建 run 账目。
- 验收（同现象节所载）：提示词携带条目编号、原认领身份、项目根与 README/design/worker-spec 文档入口；执行前核对旧 worker 已停止且无活动 worker（后端核验该条目无在途运行，旧子代理会话是否停止由提示词与界面提示人工确认）；不冒充人工接受或完成。
- 范围约束：仅登记，不实施；不扩展为 hold 复工方案。

## 验收说明

（交互对照演示见下方「界面展示」；分场景判定，实施后逐条核验）

**A. 续接场景（核心修复）**

- 前置构造：某条目存在终态 blocked 运行记录；条目业务状态仍 in-progress 且 owner 与该记录一致；账本内该条目无在途（非终态）运行；本轮任务已结束（finished）。
- 操作：任务记录页该 blocked 记录行点击「重新执行」。
- 判定标准：
  1. 不再出现「指定的条目均不可入队：可能已被认领或不在已计划状态」，也不引导人工「回到已计划且未认领」；
  2. 生成**续接提示词**并自动复制，toast 引导到原项目会话粘贴发送；复制失败时不得宣称「已复制」，须给出可展开的手动复制交互（沿用现有提示词面板口径）；
  3. 提示词内容核对清单：条目编号与标题；原认领身份（owner）；项目根；文档入口（条目 README.md / design.md、dispatch 的 worker-spec.md——事实源 `skills/agent-team-board/worker-spec.md`，派发时已复制到数据目录）；第一步为「确认旧 worker 已停止且无活动 worker」（后端核验该条目无在途运行，旧子代理会话是否停止由人工确认）；续认指令 `atb claim <条目> --by <原owner>`（现有同 owner 幂等续认）；流程口径为单项 /dev（读文档 → TDD → `report` 不带 `--run` 收口）；红线声明（不走普通新批次入队、不复用终态旧运行、不新建 run 账目、不冒充人工接受或完成）。
- 不变量：不修改人工管理的业务状态（不退回 planned、不清 owner）；不新建运行账目。

**B. 原路径回归（不破坏既有行为）**

- failed / interrupted 终态记录 + 条目 planned 且未认领：仍按原「以该条目重建新的待启动任务并自动复制调度提示词」路径成功（REQ-20260908-026 行为不变）。
- 任务仍活跃时对已认领条目点「重新执行」：维持现有拒绝文案与人工处理指引（本单仅修终态重建分支，活跃分支是否纳入见 design.md 边界，默认保持现状）。

**C. 防线核验**

- blocked 记录但该条目仍存在在途（非终态）运行：不得生成续接提示词（防双执行），按「已有在途执行」口径给出指引。
- owner 与运行记录不一致或条目非 in-progress：不进入续接分支，走既有路径与报错口径。
- 不实现 hold 复工方案、不改 hold 相关机制（范围红线）。

## 界面展示

可交互演示：**[./ui-demo.html](./ui-demo.html)**（单文件、内联 CSS/JS、无外网依赖，浏览器直接打开；顶部开关「缺陷形态（现状）↔ 修复后（期望）」对照同一操作路径的差别，并提供 正常 / 空 / 加载 / 请求失败 状态切换与深浅色适配。表格行与提示词为示意数据）。

- **界面布局**：任务模块「批量开发」子面板——顶部任务状态条（批量开发 · 本轮已结束 finished 徽章）；其下「本轮处理记录」区：工具行（本轮处理记录 / 最近 N 条 · 共 N 条）+ 四列表格（需求 / Bug、执行状态、次数、操作）。blocked 记录行呈现「受阻」状态徽章、受阻原因摘要与「重新执行」按钮；reported 终态行操作列显示「—」。修复后形态在表格下方新增**续接提示词**面板（提示词全文 + 「复制提示词」按钮 + 手动复制指引）。
- **交互行为**：点击 blocked 记录的「重新执行」（按钮带「执行中…」加载过渡）：缺陷形态下 toast 报错「指定的条目均不可入队：可能已被认领或不在已计划状态」，无任何提示词产生；修复后形态下生成续接提示词并自动复制（可勾选「模拟复制失败」对照手动复制路径），toast 引导到原项目会话粘贴发送，面板可随时手动复制 / 重试复制；顶部形态开关切换前后行为，其余骨架与数据不变。
- **状态反馈**：覆盖 正常（blocked 记录可重试、reported 记录不可重试）/ 空态（暂无执行记录）/ 加载中（正在加载执行记录…）/ 请求失败（toast 网络错误口径）四种状态切换；toast 区分成功（✓ 绿）与错误（红）两种口径，自动消失；深浅色随系统 prefers-color-scheme 适配并提供手动切换按钮。
