# BUG-20260914-004 已经纳入版本的条目不应该再出现在其他版本的关联列表或新建版本的关联列表中

- 状态：submitted（待人工接受）
- 归属：独立 Bug（引入来源见 design.md；涉及界面为构建模块「版本计划」前端选单，由 REQ-20260913-001 建立，候选收窄口径见 BUG-20260913-001）
- 创建：2026-09-14T03:32:24.805Z

## 现象

构建模块「版本计划」的条目候选没有「已被版本占用」的过滤：**已纳入任一版本计划的条目，仍会出现在「＋ 新建版本」面板与其他版本的「＋ 添加条目」面板的候选列表中，且能成功提交，造成同一条目（及其关联 commit）同时挂在多个版本计划上。**

具体表现（均经源码核实）：

1. **「＋ 新建版本」候选不过滤已占用条目**：`scripts/web/build.js` `openCreatePanel()`（约 219 行）只做 `doneCandidates()` 过滤（BUG-20260913-001 口径：仅已完成 done 条目进候选），**不排除已纳入任何现有版本的条目**——已挂在版本 A 中的条目 X 依然出现在新建候选里，可勾选、可提交、创建成功。
2. **「＋ 添加条目」候选只排除本版本**：`openAddPanel()`（约 327 行）过滤条件为 `doneCandidates(...).filter((x) => !have.has(x.itemId))`，其中 `have` 仅取自**当前操作版本自身的 items**——其他版本已纳入的条目照常出现，可把版本 A 的条目 X 再加进版本 B。
3. **后端两处接口不兜底**：
   - `GET /api/build/candidates`（`scripts/server.mjs` 约 2058 行）：仅过滤 done，无任何「已被版本占用」维度；
   - `POST /api/build/version`（创建）与 `POST /api/build/version/items`（action=add）（`scripts/server.mjs` 约 2093 / 2116 行起）：仅校验条目存在且 done；数据层 `buildStore.addItems()`（`scripts/lib/build-store.mjs` 161–169 行）的去重只针对**同一版本内**（`normalizeItems` 的 `existingIds` 为本版本已有集合，报错口径「已在本版本中，不可重复添加」），跨版本重复一律放行。
4. **后果**（占用状态可跨 draft / merging / merged / failed 任一状态的版本成立）：
   - 同一条目挂在多个版本，两个版本先后「合并入 main」时，同一 commit 被重复执行 `git merge --no-ff`——已在 main 的提交再合并返回 Already up to date、仍记成功（`scripts/lib/build-git.mjs` 143 行注释口径），git 历史不损坏，但产生冗余合并与冗余合并记录；
   - 版本卡片「N 个关联单」计数跨版本重复累计；
   - 「AI 完善」提示词（`buildPrompt()`，`scripts/web/build.js` 100–110 行）把其他版本的条目一并列入关联清单，生成的版本名称 / 描述混入无关条目；
   - 与 BUG-20260913-001「候选在数据源头收窄」的既有做法口径不一致。

## 复现步骤

前置：看板所在项目为 git 仓库；看板中存在至少 2 条已完成（done）且有关联 commit 的条目（构建页候选列表能看到它们即可）。

1. 打开 Agent Team Board 看板（Web 或 Electron 端），顶栏切到「构建」页，保持「版本计划」子页签。
2. 点右上「＋ 新建版本」，勾选条目 X（有 commit 候选），点「创建版本计划」——版本 A 创建成功，X 出现在 A 的关联条目列表中。
3. **场景一（新建候选不过滤）**：再次点「＋ 新建版本」。
   - **实际结果**：条目 X 仍出现在候选列表中、可勾选、可提交，第二个版本创建成功，X 同时挂在两个版本上。
4. **场景二（添加候选只排除本版本）**：选中另一「计划中 / 失败」状态的版本 B，在右侧详情「关联条目与 commit」区点「＋ 添加条目」。
   - **实际结果**：条目 X（不在 B 中，但在 A 中）出现在候选列表，勾选后点「添加所选条目」成功——X 同时挂在 A、B 两个版本。
5. **后果观察**：分别对两个版本点「合并入 main」并确认——X 的 commit 被合并两次（第二次 Already up to date 仍记成功）；版本卡片「N 个关联单」把 X 重复计数；「AI 完善」提示词中 X 被两个版本都列为关联条目。
6. **对照（边界确认）**：把 X 从版本 B「移出」（draft / failed 态允许移出）后，X 在 A 中依旧不影响它继续出现在新建 / 其他版本添加候选——占用过滤整体缺失，与版本状态无关。

## 期望行为

- **候选过滤（核心）**：已纳入任一现有版本计划（draft / merging / merged / failed 任一状态）的条目，不应出现在：
  1. 「＋ 新建版本」面板的候选列表；
  2. 任何版本的「＋ 添加条目」面板的候选列表（「已在本版本中的条目不再出现」的既有排除继续保留，且需扩展到其他版本）。
- **占用释放口径**（与既有语义一致）：条目从 draft / failed 版本「移出」、或该版本被删除（REQ-20260913-004，merging 不可删）后，条目重新回到候选列表；merged 版本条目锁定不可移出，条目保持不再候选，除非删除该版本记录。
- **实现方向（建议，具体由开发阶段 design.md 落定）**：与 BUG-20260913-001 同法——后端 `GET /api/build/candidates` 在数据源头收窄（响应附带条目占用信息供前端展示），前端新建 / 添加两面板统一过滤；并在 `POST /api/build/version` 与 `/version/items`（add）对跨版本重复做服务端兜底校验（报错口径建议类似「条目 X 已纳入版本 BLD-YYYYMMDD-NNN，不可重复纳入」）。是否附带服务端兜底、以及「所有候选均被占用」时面板空态文案如何区分（现有空态文案只覆盖「无 done 条目」一种情况），**待确认**。

## 验收说明

1. **新建面板过滤**：把条目 X 纳入版本 A 后重开「＋ 新建版本」，X 不再出现在候选；其他未被占用的 done 条目照常出现、可勾选提交。
2. **添加面板过滤**：任一其他版本 B 的「＋ 添加条目」候选不含 X；B 自身已有条目依旧被排除（不回归既有排除口径）。
3. **占用释放**：把 X 从 draft / failed 版本「移出」后，X 重新出现在新建与添加候选；删除该版本（draft / failed / merged）后同理。
4. **状态覆盖**：占用判定覆盖 draft / merging / merged / failed 四种状态的版本（任一状态下条目均视为占用）。
5. **服务端兜底（若按 design.md 落定实施）**：绕过前端直接调 `POST /api/build/version` / `POST /api/build/version/items` 重复纳入，被明确拒绝并给出含占用版本编号的报错；若方案不落地服务端兜底，此条按 design.md 最终口径验收。
6. **不回归**：候选仍仅含已完成（done）条目（BUG-20260913-001）；「全选 / 全不选」即时生效（BUG-20260914-002）；无关联提交条目仍禁用并在全选时跳过；面板加载中 / 读取失败重试 / 空候选等状态展示不受影响。

- **界面布局**：顶栏「构建」页 →「版本计划」子页签；左侧为版本卡片列表（名称 + 状态 chip +「N 个关联单 · 更新时间」，卡内含「AI 完善 / 合并入 main / 删除」操作），右侧为选中版本详情（名称与描述编辑区、「关联条目与 commit」区：条目号 + 标题 + commit 下拉 + 逐条「移出」+「＋ 添加条目」）；右上「＋ 新建版本」与「＋ 添加条目」均打开右侧侧拉选单面板（工具行「全选 / 全不选 / 已选 N 项」+ 候选行：复选框 + 条目号标题 + commit 下拉或「暂无关联提交」标注 + 底部提交键）。
- **交互行为**：勾选候选行联动「已选 N 项」计数与 commit 下拉解禁；全选只纳入有 commit 候选的条目；提交「创建版本计划 / 添加所选条目」后刷新列表与详情。**本 Bug 的缺陷交互**：已纳入版本 A 的条目 X 仍可在新建面板与其他版本添加面板中被勾选并成功提交；**修复后期望**：X 不出现在任何候选列表，仅当其被「移出」或所在版本被删除后重新可选（演示中可操作「移出」验证释放）。
- **状态反馈**：面板打开先显示「正在读取条目…」加载态；读取失败显示错误行内提示 +「重试」；无候选时显示明确空态（修复后需区分「无 done 条目」与「done 条目均已被版本占用」两种空态文案，细节待确认）；提交成功 / 失败经 toast 反馈；同一 commit 重复关联的后果（重复合并、计数重复、AI 完善混入）在演示观察框中说明。
