## 现象

用户复报「BUG-20260920-006 的问题还是没有修复」；关联前单的具体症状是构建模块「版本计划」详情中，点击「合并入 main」后没有可感知反馈。此单目标是查清前次修复后仍无响应的实际链路，并恢复从真实界面点击到反馈的完整行为。

2026-09-21 静态核对当前仓库发现：`scripts/web/build.js` 已存在 `mergeBlockReason`、`openMergeConfirm` 的原因提示、`renderMergePane` 的 `aria-disabled` 按钮、`bindCommon` 对 `[data-ver-merge]` 的 click 绑定，以及 `renderMergeConfirm` 弹窗渲染；`scripts/web/style.css` 已包含 aria-disabled 样式。因而不能把前单所述「仍使用原生 disabled、守卫静默返回」直接作为本单已确认根因。

前单 `test-report.md` 记录的是 VM 假 DOM 行为与静态契约检查，并非本次用户运行环境中的真实点击证据。本轮仅完善文档，尚未进行产品运行环境复现。受影响版本计划 ID、点击时门禁/分支、浏览器或桌面壳版本、实际加载脚本版本、控制台错误及网络请求情况均待确认；旧资源、绑定失效、重渲染或弹窗展示问题只是排查方向，不能写成结论。

## 复现步骤

以下为依据用户复报与前单整理的复现路径，开发时需补充实测结果：

1. 在用户发生问题的运行入口打开该项目看板，进入「构建 → 版本计划」，选择原出问题版本；记录版本 ID、页面地址、应用版本/代码提交和运行入口（待确认）。
2. 进入详情「合并入 main」步骤，记录关联条目、文档门禁、当前分支及合并状态；点击详情主按钮，观察是否出现确认弹窗、原因提示或执行反馈。用户报告的实际结果是仍无响应，精确触发条件待确认。
3. 对照点击同版本卡片合并按钮，并用键盘 Tab 聚焦、Enter/Space 激活，记录两入口反馈是否一致。此为诊断对照，不预先认定卡片也有缺陷。
4. 在同一环境比较初次进入、切换版本后、切换流程步骤后及列表刷新后的点击；记录控制台异常、事件是否到达处理函数、弹窗是否进入 DOM 和可见范围、请求是否发出。
5. 区分两阶段：打开确认弹窗前不应执行合并请求；仅人工确认后才可请求合并。验证实际合并应在开发用隔离仓库进行，不能为复现擅自合并本项目真实版本。
6. 记录普通刷新及重新加载资源前后的结果用于定位资源版本问题；刷新只能作为诊断，不作为修复完成依据。

## 期望行为

- 可合并时，点击详情入口立即呈现可见、可操作、对应正确版本的确认弹窗；取消无合并副作用，确认后展示执行中反馈，结束展示成功或具体失败原因。
- 不可合并时展示准确且可感知的原因（文档门禁、非 dev、正在合并、已正式发布等）；不存在的版本提示刷新。保留既有后端门禁和重复执行保护，不用去除保护来让按钮“有反应”。
- 详情与卡片均可通过实际鼠标/键盘操作到达反馈；版本切换、步骤切换和重渲染后仍成立。反馈不能仅存在于不可见弹层或悬停 title。
- 合并分析加载中显示进度，加载失败显示错误与重试；空列表或无关联条目显示引导。已合并但未正式发布的增量重试沿用现有规则，不错误地一概锁死。
- 修复范围聚焦无响应链路；不扩展到自动切分支、自动推送或改变发布门禁。界面文案变化中英文同步。

## 验收说明

1. 开发阶段记录原用户场景的实际触发条件、运行资源版本和根因；若原环境不可获得，明确保留待确认项，不能只凭前单测试通过宣称原场景修复。
2. 在真实浏览器 DOM 中从详情按钮点击验证确认弹窗可见且版本正确；覆盖初次进入、切换版本、切换步骤、刷新重渲染后的路径，并对照卡片入口。测试不得仅直接调用 `openMergeConfirm` 代替完整点击链路。
3. 鼠标与键盘均能触发可感知反馈。取消无请求；确认后只发送一次合并请求，重复点击不重复执行，成功及失败都有反馈。
4. 覆盖文档未提交/范围过期、非 dev、合并中、已正式发布、版本不存在等守卫；原因与真实阻塞一致，前单修复不回退。
5. 覆盖正常、空、加载、读取失败重试和执行失败重试状态；验证弹窗与提示未被遮挡，页面无导致交互中断的未处理异常。
6. 以实际根因补回归测试；运行相关 UI/i18n 测试及 `npm test`，如有既有失败需记录证据和关联单。产品运行验证与本文演示验证分开记录，不把演示成功当作产品修复证明。
