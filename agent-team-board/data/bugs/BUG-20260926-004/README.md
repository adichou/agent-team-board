# BUG-20260926-004 发布范围变化（scopeStale）后逐文件通过审核永不生效，审查与提交门禁互相死锁

- 状态：submitted（待人工接受）
- 归属：独立 Bug（引入来源见 design.md）
- 引入来源：REQ-20260921-008（引入「已审核 = !scopeStale 且 hash 一致」判定与逐文件通过审核，与 scopeStale「仅重新提交可清除」组合成死锁闭环；scopeStale 机制本身由 REQ-20260920-003 引入）
- 创建：2026-09-26T09:31:21.146Z

## 现象

用户报告：BLD-20260923-001 文档编写步的审查对话框中，「通过审核」按钮点击没有响应。

实际链路是按钮事件与请求都正常：点击后 POST `/api/build/docs/review` 成功（服务端正常记录审核 hash），并弹出一闪而过的 toast「✓ … 已通过审核（0/11）」；但文件四态、页签计数（x/语言数）、底部合计（0/11）与按钮状态在重渲染后与点击前完全相同——审核进度永远不前进，表现为「点了没反应」。

深层数据状态（BLD-20260923-001，2026-09-26 诊断时点）：11 个发布文档磁盘内容 sha256 与 `review.files` 已固化 hash **逐文件完全一致**（此前已全部通过审核并提交，docs commit `f1d15c7`），但版本 `docs.scopeStale = true`（原因：「补入依赖提交：REQ-20260921-012（+1）、BUG-20260921-003（+2）、BUG-20260922-001（+5）、REQ-20260923-002（+2）、BUG-20260925-003（+2）」，由合并步隔离分析「一键加入所有依赖提交」触发）。求值侧因此把全部 11 个文件判为非「已审核」（summarized / translated / pending），reviewedCount = 0/11，canCommit = false。

## 复现步骤

1. 打开发布页，选择 BLD-20260923-001（或任一「文档已全部审核并提交后、发布范围又发生变化」的版本），进入「文档编写」步；
2. 在「合并入 main」步的隔离分析节点「一键加入所有依赖提交」（或任何增删条目 / 换提交操作），版本被标记 scopeStale（提示「发布范围已变化，文档需重新核对 / 提交」），既有审核整体失效；
3. 回到「文档编写」步打开「审查」对话框：各文件显示「已总结待审核 / 已翻译待审核 / 待审核」，按钮为可点击的「通过审核」；
4. 逐文件点击「通过审核」：请求成功、toast 出现（计数仍显示 0/11），但文件状态、页签计数、底部合计、按钮文案全部不变，永远停在待审核；
5. 点「⑤ 提交」：被门禁拒绝，提示「文档未全部通过审查（0/11 已审核）……请在『审查』中逐文件通过审核后再提交」——按提示回第 4 步操作永远无法解锁，形成死循环；
6. 对照数据核验：`agent-team-board/runtime/builds/versions/<ID>/version.json` 中 `docs.scopeStale = true`；磁盘文件 sha256 与 `review.files` 固化 hash 一致（内容并未变化，仅范围变化）。

## 期望行为

按「方案 1」修复：**scopeStale 的门禁语义收敛到提交时点校验，审查对话框不受其阻断**——

1. **审查可恢复**：发布范围变化（scopeStale）后，审查对话框逐文件「通过审核」正常生效（以点击时点磁盘内容固化 hash，与现口径一致），文件可重新回到「已审核」，reviewedCount 实时前进；
2. **提交时点闭环校验**：「⑤ 提交」门禁保持不放宽——全部文件已审核 + 提交时点核验「审核记录之后发布范围未再变化」（审核记录时点晚于最近一次范围变化标记，或提交时重算范围指纹与上次范围变化后基线一致）：若审核过程中范围又变了，如实报错提示重新审查，不静默放行；
3. **门禁不弱化**：merge 步对文档的要求（已提交且范围未过期 → needs-rewrite 拦截）保持现状；scopeStale 标记与 `staleReason` 溯源机制不变；「发布范围变化 → 审核需重新核对」的产品口径不变，只是恢复路径从「走不通」变为「重新逐文件审核 → 重新提交」；
4. **状态展示如实**：scopeStale 期间审查对话框维持现有的失效提示（如提交门禁行的「发布范围已变化，审核已失效需重新审查」），不再出现「已通过审核（0/11）」这类自相矛盾的 toast——toast 计数应与求值结果一致。

### 明确不做

- 不取消 scopeStale 标记或「范围变化使审核失效」的产品口径；
- 不放宽 merge 门禁、不自动代替人工重新审核；
- 不改「一键加入依赖提交」触发范围变化的既有联动。

## 验收说明

- 用 BLD-20260923-001 真实状态（scopeStale = true、11 文件磁盘 hash 与审核记录一致）验证：逐文件点「通过审核」后，该文件立即变「✔ 已审核」，reviewedCount 前进，11 个全部点完后 canCommit = true，⑤ 提交可走通（提交成功后 scopeStale 清除、staleReason 清空）。
- 审核过程中再次触发范围变化（如再补入一个依赖提交）：已重新通过的审核再次失效，提交时点校验报错并如实提示，不放行旧审核。
- 回归：范围未变化的版本审查 / 提交流程不变；增删条目 / 换 commit / 语言集变化等既有 scopeStale 联动测试全量通过；BUG-20260926-002 的提交门禁口径（全部已审核即放行、不叠加整体审查完结条件）不被回退。
- toast 文案与求值结果一致（不再出现「已通过审核（0/11）」矛盾形态）。
- 全量 `npm test` 通过；新增用例覆盖「scopeStale 后逐文件重新审核可恢复 → 提交解锁」与「审核后再变范围 → 提交拦截」两条路径。
