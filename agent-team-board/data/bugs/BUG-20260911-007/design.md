## 引入来源（源单）

本 Bug 由哪个需求 / Bug 引入？登记时可暂空或写「未定位」，修复阶段必须归因（三选一，禁止编造）：

- 引入来源：**REQ-20260910-003**（全局任务看板；已经 `atb list` 核验真实存在）。
  前端类型筛选链路（`renderGlobalView` 过滤 `t.kind === g.kindFilter`）对 `kind` 缺失 / 取值
  不在词表内的简报**没有任何容错**——该行会在所有筛选档位下静默消失，而汇总行
  `globalSummaryText` 按 `status` 计数不看 `kind`，于是出现「执行中 1 但 0 匹配」的自相矛盾态。
  这一缺口随全局看板前端（REQ-20260910-003，后经 BUG-20260911-006 扩为三类）引入。

## 根因分析

- **缺陷机制（已在代码中定位）**：全局任务面板的类型筛选裸比对 `t.kind`，词表外 / 缺失的
  `kind` 在「批量完善」「批量开发」「批量 Commit」任何类型档都不命中；状态档与搜索不影响该
  维度，任务行因此从所有筛选档位下消失。汇总计数不依赖 `kind`，故与列表脱节同屏矛盾。
- **截图时刻的触发面（最相容假设，无法实证）**：看板服务为常驻进程、路由集在启动时固化，
  静态前端却实时读盘（BUG-20260907-017 已落地的同类机制）。截图时刻服务进程很可能旧于前端，
  返回的简报缺 `kind` 字段或为旧口径——恰好拼出截图态。仓库仅一个初始化提交、无历史版本
  记录可查，且 2026-09-11 完善时以现行代码 + 当前账本数据实测**未能复现**（接口返回含
  `kind: "refine"` 的 running 批次）。故触发面按「最相容、不可证」登记，不编造结论。
- **现行服务端无该缺陷**：三个 brief 函数（`batchBrief` / `refineBatchBrief` /
  `commitBatchBrief`）均硬编码 `kind`，结构性保证字段必填；账本侧 RFB-20260910-023
  `status: "running"`、非 aborted，口径内本应显示。

## 方案

**开源选型（REQ-20260909-015）**：未引入开源库。自研理由：纯前端约 30 行兜底逻辑
（前缀表 + 推断函数 + 诊断 flag），无成熟库可复用，引库成本高于自研；不创建 licenses.md。

**修复口径（README「待确认」二选一，选定：前端按批次号前缀推断 + 未知值中性档）**：
兜底必须放在前端——旧服务进程跑的是旧服务端代码，服务端补丁对该场景无效；前端实时读盘
始终为新代码，是版本错位下唯一能救的一层。

1. `scripts/web/app.js` 新增 `globalTaskKind(task)`（`GLOBAL_KIND_PREFIXES` 前缀表）：
   - `kind` 在词表内（`hasOwnProperty` 防原型链键如 `'toString'`）→ 原样返回，`inferred: false`；
   - 缺失 / 未知 → 按批次号前缀推断：`RFB-`→refine、`CMT-`→commit、`batch-`→develop，
     `inferred: true`；
   - 前缀也认不出 → `'unknown'`（中性徽标「未知类型」，至少在「全部类型」档可见，绝不消失）。
2. 消费点全部改用兜底 kind：类型筛选（`globalTaskKind(t).kind === g.kindFilter`）、
   计数行 `globalCountsParts`（缺 kind 的 RFB/CMT 简报按推断类型取「已完成 / 已提交」口径）、
   行内 kind 徽标与跳转挂点 `data-ggoto-runs`。
3. 诊断线索：`inferred` 时行内 flag「类型推断」/「类型未知」，title 说明原始值、推断结果、
   并指引**重启看板服务**（常驻进程旧于前端的自愈路径，对照 `/api/health` 的 pid/startedAt
   版本自检——BUG-20260907-017 机制，本单不改动）。
4. 服务端不改：现行 brief 已结构性必填 `kind`（三个函数硬编码），再加归一层属不可测死代码。

**测试（TDD）**：`scripts/tests/global-kind-fallback-20260911-007.test.mjs`
- K1 推断矩阵（提取 app.js 纯函数求值）：已知原样 / 缺失按前缀 / 未知值按前缀 /
  推不出归 unknown / 原型链键不混入；
- K2 计数行兜底（行为）：缺 kind 的 RFB→「已完成」、CMT→「已提交」、develop 口径回归；
- K3 渲染契约（静态）：筛选不裸比对 `t.kind`、跳转挂点与徽标用 `effKind`、诊断 flag 文案、
  汇总行保持 status 口径；
- K4 服务端主路径回归（真实起 server）：running 完善批次聚合返回 `kind: "refine"` 且不误标推断。

## 风险与边界

- `unknown` 档仅在「全部类型」筛选下可见（无类型档可归），汇总仍计数——满足验收
  「凡计入汇总的任务行必须能通过『全部状态 + 全部类型』筛选被展示」；具体类型档下不可见
  属预期（类型未知无法归类）。
- 前缀推断依赖编号方案固定前缀（refine-store `RFB-` / commit-store `CMT-` / dispatch
  `batch-`）；未来新增批次类型须同步 `GLOBAL_KIND_PREFIXES` 与 `GLOBAL_KIND_LABEL`，
  否则新类型落入 unknown 档（仍可见，不静默）。
- 防再发三层：前端行内诊断 flag + 重启指引（本单）；`/api/health` 版本自检 + `atb serve`
  旧进程自动重启（BUG-20260907-017 既有机制，覆盖本场景）；服务端 brief 硬编码 `kind`
  （既有结构保证，本单不动）。
- 既有行为零回归：全量 `npm test` 190 个测试文件 0 失败；BUG-20260911-006 的 C5 前端
  契约断言随重构同步为「globalCountsParts 函数体内含 commit 分支」（语义不变，仍验证
  commit 计数口径存在）。
- 修复不改变面板只读性、跳转语义、空态 / 骨架 / 错误行等既有行为。
