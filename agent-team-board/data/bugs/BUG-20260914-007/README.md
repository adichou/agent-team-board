# BUG-20260914-007 body-limit.test.mjs 在 run-all 全量跑下偶发失败（单独运行通过）

- 状态：accepted（已接受）
- 归属：独立 Bug（引入来源见 design.md）
- 创建：2026-09-14T04:10:37.580Z

## 现象

现象：node scripts/tests/run-all.mjs 全量执行时 body-limit.test.mjs 偶发失败（3 次全量中 2 次失败、第 3 次通过；单独 node scripts/tests/body-limit.test.mjs 稳定通过）。该测试 spawn 真实 server.mjs 并提交 2MB/14MB 级大请求体（timeout 20s），疑似全量高负载下启动或传输超时的环境抖动；BUG-20260914-005 实施期间发现，与该条目纯前端文案改动无关（该测试仅打 API 端点，不加载前端资源）。建议：失败时输出更详细的超时定位（启动未就绪 vs 请求超时），或放宽全量模式下的等待/重试。

## 复现步骤

1. 在项目根目录执行全量测试：`node scripts/tests/run-all.mjs`（等价 `npm test`）。run-all.mjs 会按文件名顺序执行 `scripts/tests/` 下全部 `*.test.mjs`（当前约 250 个测试文件，每个文件独立子进程，单文件超时上限 180s）。
2. 观察输出中 `===== body-limit.test.mjs =====` 一节：偶发打印 `✗ BUG-20260907-004 请求体上限对齐 + 超限 400 JSON`，run-all 汇总出现失败并整体退出码非 0（登记时实测：3 次全量中 2 次失败、第 3 次通过；两次失败的具体报错文案——「服务应启动」断言失败还是请求 `timeout`——当时未留存：待确认）。
3. 对照单独运行：`node scripts/tests/body-limit.test.mjs`，多次执行均稳定通过（打印「全部通过」、退出码 0）。
4. 触发条件与机器负载相关（全量顺序执行数百个测试、期间大量 spawn 子进程时更易触发），失败点集中于该测试的两处环境敏感环节（依据测试源码 body-limit.test.mjs）：
   - 服务就绪等待：测试 spawn 真实 `scripts/server.mjs`（随机端口 31000–50999）后轮询 `/api/health`，最多 40 次 × 150ms ≈ 6 秒，超时即断言「服务应启动」失败；
   - 大请求体传输：每个 HTTP 请求 `timeout: 20000`（20 秒），高负载下 2MB/7MB 级 base64 大包（最大单请求 ≈ 18.7MB）的写入/回包可能超时，错误仅显示 `timeout`。

## 期望行为

1. `node scripts/tests/run-all.mjs`（`npm test`）全量执行时，body-limit.test.mjs 与单独运行表现一致、稳定通过，不因全量顺序执行的环境负载偶发失败；连续多轮全量执行通过率 100%。
2. 失败可定位：若测试仍因环境原因失败，错误输出应能区分失败环节——服务启动未就绪（健康轮询超时）还是哪一步请求超时（T1 2MB 创建 / T2 总量超限 400 / T3 `/api/new` 超限 400 / 超限后恢复），而非只给出笼统的 `timeout` 或一行断言失败。
3. 修复不改变测试覆盖的功能语义：服务端 `BODY_MAX_BYTES = 12MB`（scripts/server.mjs）上限行为不变——2MB 单附件应 200 创建成功、2×7MB（base64 ≈ 18.7MB）与 13MB 文本应返回完整 400 JSON（含「请求体过大」说明、连接不被掐断）、超限后服务应可继续正常创建。
4. 若采用放宽等待/重试方案：仅对启动等待、传输超时类环境抖动放宽；功能性断言失败（如超限未返回 400 JSON）仍应直接判失败，重试前失败原因需输出留痕，不得静默吞掉真实回归。

## 验收说明

1. 稳定性：连续 ≥3 次执行 `node scripts/tests/run-all.mjs`（或 `npm test`），body-limit.test.mjs 每轮均通过，run-all 汇总「失败 0」、退出码 0；建议在其中至少一轮于系统高负载时段执行，覆盖原触发条件。
2. 单独运行回归：多次执行 `node scripts/tests/body-limit.test.mjs` 仍全部通过，测试内 4 项功能断言保持不变（2MB 附件 200 / 2×7MB 总量超限 400 / 13MB 文本 400 / 超限后恢复创建 200）。
3. 失败定位能力：以实现提供的注入方式（如临时缩短健康轮询预算、模拟启动未就绪与请求超时两类失败）触发失败时，测试输出应能区分「服务启动未就绪」与「请求超时」，并标明具体失败用例环节。
4. 重试留痕（若实现含重试/放宽逻辑）：验证重试确实生效（人为令首次尝试失败后可恢复），且重试前的失败原因被打印留痕，不静默。
5. 边界：不修改 `scripts/server.mjs` 的 `BODY_MAX_BYTES`（12MB）及超限 400 JSON 行为；本修复只应动测试脚本/运行器层面的稳定性与诊断输出（若排查结论另有所指，以 design.md 实际根因分析为准）。
