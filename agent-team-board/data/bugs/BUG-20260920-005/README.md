# BUG-20260920-005 已经合并入 main 的版本计划允许重新关联条目和提交

- 状态：submitted（待人工接受）
- 归属：独立 Bug（引入来源见 design.md）
- 创建：2026-09-20T15:46:05.865Z

## 现象

按登记口径：只有**完成推送到远端仓库**的版本计划才是正式发布的版本；**正式发布后**才应禁止「关联条目和提交」「合并入 main」「AI 完善」。而当前实现的锁定时机整体提前到**合并入 main 完成（merged）**——已合并但尚未在「正式发布」步推送主分支的版本计划，上述三类操作已全部锁死，用户发现漏关联条目 / 提交时只能按提示「新建版本」另起炉灶，与本口径相悖（即标题所指：这类**尚未正式发布**的版本计划应当仍允许重新关联条目和提交）。

现状链路（均经源码核实，2026-09-20）：

1. **条目与提交锁定**：数据层 `scripts/lib/build-store.mjs` 的 `assertItemsEditable`（177–181 行）对 merging / merged 一律抛 `BuildConflictError`（HTTP 409），merged 提示「版本已合并，条目已锁定（如需调整请新建版本）」，`addItems` / `removeItems` / `setItemCommit` 全被拦；对应接口 `POST /api/build/version/items`（`scripts/server.mjs` 2387–2412 行，action = add / remove / commit）同口径。前端 `scripts/web/build.js` 以 `lockItems = ['merging','merged']`（2105 行）联动禁用「＋ 添加条目」（2165 行）、逐条「移出」与换 commit 下拉（2121 / 2125 行）。
2. **步骤导航锁定**：`scripts/lib/publish-flow.mjs` 的 `publishStepsState`（255–288 行）把「关联条目与提交」「文档编写」两步的锁定范围定为 `merging || merged`（260 行 `lockedScope`），merged 的锁定理由为「已合并，范围锁定（如需调整请新建版本）」（278 行）；五步导航据此禁用步骤入口（build.js `renderStepNav`，1947–1957 行）。
3. **合并入口锁定**：`POST /api/build/version/merge` 对 merged 直接拒绝「版本已合并入 main，无需重复合并」（server.mjs 2421–2423 行）；数据层 `beginMerge` 仅允许 draft / failed 发起（build-store.mjs 242–246 行）；左侧卡片「合并入 main」按钮对 merged 禁用（title「已合并入 main」，build.js 1866 行）。
4. **AI 完善锁定**：BUG-20260914-020 把卡片「AI 完善」按钮的禁用口径与合并键对齐——merged 同样禁用（title「已合并入 main，不允许再 AI 完善」，build.js 1862–1865 行），弹窗防御路径同口径拦截（`scripts/tests/bug-build-ver-card-acts-20260913-004.test.mjs` B2 / B7）。
5. **推送完成不新增锁定**：正式发布步「推送主分支」仅要求 merged（server.mjs 2594–2605 行），成功后 `recordPushSuccess`（build-store.mjs 368–382 行）只落 `release.pushedSha / pushedAt`（官网检测时间窗口起点），**不产生任何新锁**——锁定已在 merged 时点提前用尽，「完成推送（正式发布）」这一口径指定的时点反而没有独立锁定语义。左侧卡片 meta 的阶段文案还把 merged 直接标成「阶段 正式发布」（build.js 1881 行），同样与「推送完成才算正式发布」的口径不一致。

补充：合并执行的隔离重放机制本就支持增量语义——逐条目 cherry-pick、已并入提交幂等记成功不重放、重试只补未合并条目（`scripts/lib/build-git.mjs` 385–424 行、build-store.mjs `finishMerge` 255–281 行），「merged 后为补入条目再次合并」在机制上无障碍，仅被上述状态机提前锁死。

## 复现步骤

前置：项目目录运行 `atb serve`（默认端口 8888，`ATB_PORT` 可覆盖），浏览器打开 `http://localhost:8888`，顶栏选中该项目；构建模块已有一张**已合并（merged）且尚未推送主分支**的版本卡片（若无：对任一 draft 版本依次完成「关联条目与提交 → 文档编写（八文件提交）→ 合并入 main」，直至状态变「已合并」，并且**不要**在「正式发布」步点「推送主分支」）。

1. 进入「构建」模块「版本计划」页签，选中该 merged 版本卡片。
2. 观察左侧卡片行内按钮：「合并入 main」禁用（悬停 title「已合并入 main」）；「AI 完善」禁用（title「已合并入 main，不允许再 AI 完善」）。
3. 观察右侧五步导航：「关联条目与提交」「文档编写」两步呈禁用（title「已合并，范围锁定（如需调整请新建版本）」），无法进入补关联——此时该版本**尚未推送、还不是正式发布的版本**，三类操作却已全部锁死，即本 Bug 现象的界面侧。
4. （接口层对照）对该版本调用 `POST /api/build/version/items`（action = add / remove / commit 任一）→ 返回冲突「版本已合并，条目已锁定（如需调整请新建版本）」；调用 `POST /api/build/version/merge` → 「版本已合并入 main，无需重复合并」——数据层同样拦死。
5. 进入「正式发布」步，点「推送主分支」直至成功（出现「已推送主分支 origin（完成时间 …，基准 …）」）。
6. 对比推送前后的按钮 / 步骤可用性：**无任何变化**——三类操作早在 merged 时点就已锁定，推送完成（正式发布）未引入任何新的锁定点；对照登记口径，锁定应发生在这一时点之后而不是之前的 merged 时点。

## 期望行为

- **锁定时机后移到「正式发布（推送完成）」**：「关联条目与提交」「合并入 main」「AI 完善」三类操作的锁定基准从「merged（已合并入 main）」改为「完成推送到远端仓库」（推送成功记录 `release.pushedAt / pushedSha` 落盘；判定基准细节见待确认第 1 条）。
- **merged 且未推送**：三类操作全部可用——
  - 「关联条目与提交」步骤可进入：添加条目、移出条目、换选 commit 全链路可用（UI 与数据层一致），跨版本占用（BUG-20260914-004）、仅 done 条目可纳入等既有校验照常生效；
  - 「合并入 main」可为补入的新条目 / 新 commit 再次执行：沿用既有「只补未合并条目」的增量语义（已合并条目 `mergedAt` 保持不动、已并入提交幂等记成功），完成后回到 merged；
  - 「AI 完善」按钮可用，两段式弹窗（复制提示词 → 粘贴解析 → 应用回填）可完整走通；
  - 增删条目 / 换 commit 后，REQ-20260920-003 的既有范围口径照常：旧文档提交标识失效（scopeStale），重新合并前需在「文档编写」步重新核对并提交，合并门禁不放宽。
- **推送完成（正式发布）后**：三类操作一律禁止——UI 禁用并以 title / 错误信息说明「已正式发布」；数据层 / API 同口径返回冲突；AI 完善弹窗防御路径（无参回落等）同口径拦截。
- **不变口径**：merging（合并执行中）三类操作维持锁定；draft / failed 零回归；「正式发布」步仍要求先完成合并入 main。
- **待确认（需人工拍板，默认可先按括号内口径实施）**：
  1. 「完成推送到远端仓库」的判定基准：默认以五步流程「正式发布 → 推送主分支」成功（`release.pushedAt`）为准；产品发布运行成功（`release.published`，REQ-20260915-002 口径）或官网同步命中是否也计入，需确认。
  2. 「文档编写」步骤的锁定时机是否随后移：默认随后移（merged 未推送阶段与 link 一并放开，否则补关联后无法重新提交文档、重开合并走不通；合并门禁仍要求文档已提交且范围未过期）。
  3. 推送完成后的「删除」键口径：现状 merged 可删（仅移除看板版本记录）；正式发布后是否禁删，需确认。
  4. 卡片 meta 阶段文案（merged 现标「正式发布」，build.js 1881 行）是否改为与推送状态区分的措辞，需确认。
  5. 新增 / 变更的锁定提示文案（title / 错误信息）由开发阶段定夺，中英文案须同步 `scripts/web/i18n.js`。

## 验收说明

1. **merged 未推送可用**：三类操作全链路实测——「关联条目与提交」步骤可进入，添加条目（含 commit 选择）、移出、换 commit 均成功且列表 / 计数正确刷新；卡片「AI 完善」可打开弹窗并完整走通复制 → 解析 → 应用回填；「合并入 main」入口可用（受文档门禁约束）。
2. **补关联 → 重新合并**：merged 未推送版本补入新条目后走合并：仅新条目被重放入 main，已合并条目 `mergedAt` 不动、不重复合并；完成后版本回到 merged，合并结果逐条目展示正确。
3. **推送完成后锁定**：推送成功（`release.pushedAt` 落盘）后，「关联条目与提交」「文档编写」步骤禁用且 title 可解释；`POST /api/build/version/items`（add / remove / commit）与「合并入 main」入口均返回冲突并说明已正式发布；「AI 完善」按钮禁用，弹窗防御路径（直调 / 无参回落）不生效。
4. **状态矩阵回归**：draft / failed 的三类操作与现状一致（可用）；merging 维持锁定（「合并中」口径）；「正式发布」步仍要求先合并入 main；跨版本占用校验不回退。
5. **门禁与范围口径不回退**：补关联 / 换 commit 后旧文档提交标识照常失效（scopeStale），未重新提交文档不得合并；推送基准变化后官网检测窗口起点更新（`recordPushSuccess` 既有口径）不变。
6. **测试同步**：新增本单测试（数据层锁定基准迁移、`publishStepsState` 步骤门禁、UI 禁用断言）；同步调整既有断言——`bug-build-ver-card-acts-20260913-004.test.mjs` B2 / B7 对「merged 禁用 AI 完善」的断言改为「推送完成后禁用」口径；`node scripts/tests/run-all.mjs` 全量通过。
7. **文案与外观**：新增 / 变更文案中英同步（`scripts/web/i18n.js`）并跑 i18n 相关测试；深浅色与 Electron 桌面壳内表现一致，禁用态沿用既有 disabled 口径。

- 界面布局：还原构建模块「版本计划」页签——左侧版本卡片列表（名称 + 状态章 + 计划号 / 版本号 / 阶段 / 关联数 + 行内键「AI 完善 / 合并入 main / 删除」），右侧详情按五步流程导航（版本计划 → 关联条目与提交 → 文档编写 → 合并入 main → 正式发布）切换；含 AI 完善两段式弹窗、添加条目面板、合并确认弹窗。
- 交互行为：一键切换「当前（缺陷）/ 修复后（期望）」对照——缺陷态下 merged 且未推送的版本三类操作全锁、推送完成后锁定无任何变化；期望态下 merged 未推送可自由增删条目 / 换 commit / 重开合并（只补未合并条目）/ AI 完善，推送成功后三类操作即时锁定并给出原因。版本状态 / 推送状态可手动切换，逐步走完「合并 → 补关联 → 重新提交文档 → 再合并 → 推送 → 锁定」全流程。
- 状态反馈：文档门禁（范围变化需重新提交）与合并拦截即时提示；toast 呈现复制 / 应用 / 合并 / 推送结果；列表可切「正常 / 空 / 加载中 / 加载失败（可重试）」；深浅色随系统并可手动切换。
