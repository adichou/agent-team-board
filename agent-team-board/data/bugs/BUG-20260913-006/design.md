## 引入来源（源单）

本 Bug 由哪个需求 / Bug 引入？登记时可暂空或写「未定位」，修复阶段必须归因（三选一，禁止编造）：

- 引入来源：REQ-20260911-009（dev 分支开发 + 到待测试自动 commit——`autoCommitForRun` 的「预留时工作区快照 → 收尾时差集」归因设计与 `changedPathsSince` 实现即本 Bug 根因所在；该需求编号已经 `atb list` 目录核验存在于看板）。

## 根因分析

1. **快照粒度不足**：`batch.nextItem` 在预留时调用 `gitFlow.workingTreeSnapshot`（scripts/lib/git-flow.mjs）写 `run.treeSnapshot`：对已跟踪文件只记 porcelain 状态码（path→XY），仅对未跟踪（??）文件额外记录内容哈希。预留前已脏（' M'）的已跟踪文件没有任何内容指纹。
2. **差集判定失真**：`changedPathsSince` 以「状态码是否变化」判变更，但 porcelain 状态码不随已跟踪文件的内容修改而变化——预留前 ' M' 的文件运行期再被修改后仍是 ' M'，`beforeCode === code` → 不计入变更集。代码注释声称该口径用于排除「预留前就脏且运行期间未动过」的路径，但实现无法区分「未动过」与「动过但状态码相同」。
3. **归因规则静默放大**：`autoCommitForRun` 对非看板路径「只认快照差集」（不在 `changed` 内直接 continue），漏判的 build.js 既不进 test/biz 组，也不进 excluded——连「未归因」的痕迹都不留，完全静默。
4. **连锁后果**：预留时快照每一单看到的都是同一个 ' M'，脏改动永远无归属；而已提交的 test（aeb07f9 断言 `data-ver-answer` / `data-ver-merge`）只对工作区脏版本成立，对 HEAD 版被测代码必失败——历史自洽性破坏；脏 diff 持续叠加（当前 +191/−35）。

## 方案

**开源选型（REQ-20260909-015）**：本单为 atb 自身 git 流程逻辑修复，不引入开源库（无合适库；保持 scripts/lib 零第三方依赖现状，理由：改动面仅在本仓库既有快照/归因函数内部）。

修复分两层，具体取舍由 /dev 定稿：

- **快照升级（识别层，必做）**：`workingTreeSnapshot` 对预留时已脏的已跟踪文件（XY 含非空工作区位）比照未跟踪文件记录内容哈希（sha1）；`changedPathsSince` 增加哈希比较分支——「预留码相同但哈希变化」即识别为「预留前已脏且本单动过」路径。只增不改：旧快照（无哈希）按现行为处理，不做猜测归因。
- **处置层（二选一或组合，design 定稿待确认）**：
  1. 显式待人工：识别出的路径写入回执提示与 `auto-commit.json`（如 `pendingManual` 字段），auto-commit 状态如实标记（不得表现为全量 committed），看板徽标口径同步；
  2. 拆分归属提交：注意语义只能是「整文件按当前工作区内容提交」，预留前的旧脏内容会一并带入该提交——若可接受（如经人工确认）则归入本单对应组；不可接受时退回方案 1。不做 hunk 级 diff 拆分（复杂度高且无法可靠归因）。

## 风险与边界

- **不得回退归因安全性**：「预留前无关改动绝不卷入」是原设计目标——哈希判定只在「同一路径运行期内容确有变化」时生效，方案 2 须有人工确认兜底，避免把预留前的无关改动静默带入提交。
- **兼容性**：升级前预留的旧 run（快照无哈希）维持现行为（跳过 + 提示人工核对），不产生新的静默漏判即可；幂等跳过、prevFailed 差集续传、`validateCommitSubject`、PATH_CHUNK 分块、`commit --only` 等既有机制零回归。
- **范围**：只改 scripts 层（git-flow.mjs / batch.mjs 及相应测试），不涉及 web 界面——无 UI 改动，本单不需要 ui-demo.html。
- **存量遗留**：当前工作区 build.js 的 +191/−35 未提交改动（含 004/005 已提交测试所依赖的实现）如何补录，不属本单自动机制处理范围（避免对历史遗留做猜测归属），建议修复合入后人工核对补提交——待确认。
- **测试自洽验收方法**（待确认）：对 HEAD 版源码跑该单已提交 test 的验证方式（临时 worktree / stash）由 /dev 定稿，注意不得污染用户工作区。
