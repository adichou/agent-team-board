# BUG-20260925-002 文档编写中 AI 校对的建议接收后点击刷新，又会再提示，但修改后报错。

- 状态：以系统看板为准（本文件为完善阶段说明，未实施修复）
- 归属：独立 Bug（引入来源见 design.md）
- 创建：2026-09-24T16:11:44.538Z

## 现象

文档编写页（发布流程五步装配的「③ AI 校对」环节，右侧「校对建议」侧栏）存在两个连续问题：

1. **刷新后决断丢失、已接受的建议重新提示为待处理**：对某条建议点击「接受」成功（toast「✓ 已接受并保存 …」，卡片显示「已接受」，「待处理 N 项」计数减一，文档内容已被替换并保存）。刷新浏览器页面重新进入文档编写页后，该条建议重新以「待处理」出现：状态回到「待处理」、计数回涨、「④ AI 翻译」再次被门禁拦截（提示「AI 翻译未解锁：尚有 N 条校对建议未处理（逐条接受或拒绝后解锁，见右侧校对建议栏）」）——此前已做的接受 / 拒绝决断全部丢失。切换版本再切回同因复现。
2. **对已应用过的建议再次接受，误报「建议基于的文本已变化」**：对上述重新提示的建议再次点击「接受」时报错，toast「✕ 建议已过期：建议基于的文本已变化，未覆盖当前内容（请重新校对或点「✎ 修改」手动处理）」，卡片标记「过期」并附注「建议基于的文本已变化：未覆盖当前内容，请重新校对或点「✎ 修改」手动处理。」——实际上该建议此前已成功应用并保存，报错与事实不符，用户无法区分「已处理过」与「处理失败」。

登记原文「修改后报错为：建议基于的文本已变化：未覆盖当前内容，请重新校对或点「✎ 修改」手动处理。」对应上述第 2 条的卡片附注文案。

### 已核实的代码依据（当前 dev 代码阅读结果，尚未在浏览器现场录制复现证据）

- 决断会话态不持久化：`scripts/web/build.js` 的 `defaultPf` 中 `chkDecisions`（键 `'runId|file|idx'` → accepted / rejected / stale）注释明确「决断会话态……不持久化」，仅存于页面内存。
- 整页刷新 / 切换版本会整表丢失：`scripts/web/build.js` 的 `applyPendingRestore`（页面加载恢复视图）与 `selectVersion`（切换版本）均置 `state.pf = null`；重新进入文档编写页时以 `defaultPf` 重建，`chkDecisions` 归 null，全部决断（含已接受 / 已拒绝 / 过期）清零。
- 再次接受命中过期路径：`applyChkSuggestion` 按「该行包含原文 before / 全文 indexOf before」定位替换；建议首次接受后原文已被替换为 after，刷新丢失决断后再次应用通常找不到 before，返回 stale，即出现前述报错。
- 页面内「刷新」按钮（`data-pf-refresh` → `refreshDocsPane`）不重建 `state.pf`，会话内决断保留，不会复现重新提示；重新提示发生在浏览器整页刷新 / 版本切换之后。登记原文「点击刷新」对应的具体操作方式见「待确认」。

## 复现步骤

前置：进入某版本「发布」→「文档编写」，五步装配就绪（phase ready）；已点击「③ AI 校对」派发核查且回执完成（run phase done），右侧「校对建议」栏中至少有一条可自动应用的建议（含「第 N 行：……「A」→ 建议「B」」形态）。

1. 点击该条建议的「接受」→ 观察：toast「✓ 已接受并保存 <文件> 的建议：文件回到待审核，翻译基准已更新」，卡片状态变为「已接受」，「待处理 N 项」计数减一；该文件状态回到「已总结待审核」。
2. 刷新浏览器页面（整页重新加载 Web 界面），重新进入同一版本的「文档编写」页。
3. 观察「校对建议」侧栏：该条建议重新显示为「待处理」，「待处理 N 项」计数恢复，「④ AI 翻译」再次提示未解锁（尚有 N 条未处理）——步骤 1 的「已接受」决断未体现。
4. 对该条建议再次点击「接受」→ 观察：报错 toast「✕ 建议已过期：建议基于的文本已变化，未覆盖当前内容（请重新校对或点「✎ 修改」手动处理）」，卡片状态变为「过期」并显示附注——与该建议实际早已应用成功的事实不符。
5. 同因场景（可选核对）：不刷新页面，切换到其他版本再切回，步骤 3-4 现象同样出现。

## 期望行为

1. 已决断（已接受 / 已拒绝）的校对建议，在浏览器整页刷新后重新进入文档编写页、以及切换版本再切回后，均保持决断结果：不再以「待处理」重新提示，「待处理 N 项」计数不回涨，「④ AI 翻译」门禁不因刷新回退（已决断条目不计入「尚有 N 条校对建议未处理」）。
2. 对已成功应用过的建议，即使决断记录因故不可用，再次触发「接受」时界面不得以「建议基于的文本已变化」类失败口径误报；应能区分「该建议此前已应用」与「原文确被人工改过」两种情况——前者给出非失败的明确反馈（如提示已处理过、无需重复操作），后者才标记过期并引导重新校对或点「✎ 修改」手动处理。实现口径（决断持久化的位置、已应用建议的识别方式等）留待开发阶段在 design.md 定稿，本条只约束行为结果。
3. 新一轮「③ AI 校对」产生新 run 后旧决断的保留口径：现有实现按 runId 绑定，新 run 后旧决断自然失效；是否需调整为「旧结论保留并逐条重新决断」由开发阶段核实定稿（见 design.md），本轮不因本 Bug 单方面扩大改动范围；若保留失效口径，界面应对新 run 旧决断失效有可感知的说明，不得让用户误以为刚处理过的建议凭空回到待处理。
4. 既有保护口径不回退：接受前逐条核对磁盘原文、不一致标记过期不覆盖人工修改；「✎ 修改」手动处理入口与定位；「拒绝」不改动原文；接受成功后文件回到待审核、翻译基准更新提示。

## 界面展示

[打开可交互演示](./ui-demo.html)。演示仅使用内存模拟，不读取或修改真实文档，不代表修复已完成。

- **界面布局**：文档编写页相关区域——顶部五步条（① AI 总结 ② 二次编辑 ③ AI 校对 ④ AI 翻译 ⑤ 提交）；左侧发布文档文件列表（文件名 + 状态标签）；右侧「校对建议」侧栏（标题 + 「待处理 N 项」计数、文件下拉、逐条建议卡片：问题类型 / 行号 / 状态标签 / 建议原文 / 「查看修改前后差异」折叠 / 接受 / 拒绝 / ✎ 修改）。演示顶部另设「缺陷现象 / 期望修复后」模式切换、场景切换与「刷新页面（模拟浏览器整页刷新）」按钮，均属评审控件，不是产品新增功能。
- **交互行为**：缺陷模式下可完整走通复现路径——接受建议 → 模拟整页刷新 → 建议回到「待处理」→ 再次接受 → 出现过期报错；期望模式下接受 / 拒绝后刷新，决断保持、计数不回涨、④ 门禁不回退。「✎ 修改」打开简化编辑弹窗可保存修改；「③ AI 校对」重试场景演示新一轮 run 覆盖旧结论（旧决断随新 run 失效的口径以待确认为注）。
- **状态反馈**：建议卡片状态标签覆盖 待处理 / 已接受 / 已拒绝 / 过期 / 待确认；侧栏覆盖 尚未校对（空态）/ 校对进行中（加载态）/ AI 校对中断（失败态，含重试）/ 校对完成且该文件未发现问题（空态）；接受过程有「接受中…」禁用态，刷新过程有「正在读取最新内容…」读取态；toast 区分成功 / 失败；「④ AI 翻译」在有待处理建议时给出未解锁门禁反馈。深浅色跟随系统。

## 验收说明

以下为开发及人工验收标准，不是已经通过的测试结果：

- [ ] 接受 / 拒绝某条校对建议后，整页刷新浏览器并重新进入文档编写页：该条建议不再以「待处理」重新提示，决断状态保持，「待处理 N 项」计数不回涨。
- [ ] 刷新后「④ AI 翻译」门禁不回退：门禁计数只统计真正未决断的建议，已接受 / 已拒绝 / 过期条目不计入。
- [ ] 切换版本再切回：决断保持口径与整页刷新一致。
- [ ] 对已应用过的建议再次触发接受（含决断记录不可用的路径），不得报「建议基于的文本已变化」类失败；对原文确被人工修改的情形仍标记过期且不覆盖人工内容（既有保护不回退）。
- [ ] 新 run 与旧决断的关系按 design.md 定稿口径实现并有测试覆盖；若旧决断随新 run 失效，界面有可感知的说明。
- [ ] 会话内既有行为不回退：接受成功 toast 与文件回「已总结待审核」、拒绝不改原文、「✎ 修改」定位跳转、接受前原文核对。
- [ ] 侧栏空态（尚未校对 / 该文件未发现问题）、加载态（校对进行中 / 接受中 / 读取中）、失败态（校对中断 + 重试）不回归；失败与误报在界面可区分。
- [ ] 涉及文案中英文同步（scripts/web/i18n.js），i18n 相关测试通过；测试先行（scripts/tests/ 新增 bug-20260925-002 测试先红后绿），`npm test` 全量通过。

## 待确认

- 登记原文「点击刷新」未指明是页面内「刷新」按钮还是浏览器整页刷新。代码核实：页面内「刷新」按钮保留会话决断、不会复现；浏览器整页刷新与版本切换可复现。现场实际操作方式待人工确认（不影响缺陷成立——整页刷新是常规操作）。
- 决断持久化的实现位置（服务端账本 / 浏览器本地存储 / 其他）与「已应用建议再次接受」的识别方案，留待开发阶段 design.md 定稿。
- 新一轮「③ AI 校对」后旧 run 决断是否保留，待确认（现有实现按 runId 绑定、新 run 后失效）。
- 首个出现该现象的版本与引入来源归因，见 design.md（本完善阶段未改写 design.md，归因留待开发阶段）。
