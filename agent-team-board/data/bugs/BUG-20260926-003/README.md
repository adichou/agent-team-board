# BUG-20260926-003 发布隔离分析将标题引用单号误判为混合归属，祖先提交统称依赖导致一键纳入受阻

- 状态：submitted（待人工接受）
- 归属：独立 Bug（引入来源见 design.md）
- 创建：2026-09-26T07:13:14.834Z

## 现象

用户报告：版本发布「合并入 main」步的隔离分析发现 20 个未选祖先、影响 63 个所选条目；点击「一键加入所有依赖提交」后 20 个全部未能纳入，无一进入发布范围。跳过原因分布：

- **12 个因提交主题包含引用单号被判「混合提交（关联 A、B），无法安全归因」**。示例（均已在仓库核验）：
  - `81bec844` 实际只修改 REQ-20260921-012 条目文档（README / design / test-cases / ui-demo 四个文件），但主题中引用 REQ-20260921-010 而被判混合；
  - `176c37c2` 主题开头引用旧 Bug BUG-20260920-006，末尾归属单号为 BUG-20260921-003，同样被判混合；
- **3 个对应 submitted（未完成）条目**。示例：`15b06de7` 仅新增未完成需求 REQ-20260921-009（当前状态 submitted）的讨论文档，因「尚未完成」被跳过；
- **5 个对应已不存在条目**：主题引用的旧单号条目已不在看板中。

根因方向：归因反查（scripts/lib/git-flow.mjs `itemCommitStatusIndex`）把提交主题文本中出现的任何 REQ-/BUG- 单号都算作关联条目，未区分「主题末尾归属单号」与「正文引用单号」；提交账本等更权威的归属证据未被优先采用。详见 design.md 根因分析。界面演示见下方「界面展示」。

## 复现步骤

1. 打开发布页，选择一个未推送的版本，进入「合并入 main」步；
2. 隔离分析节显示汇总行「发现 20 个未选祖先（依赖）提交 · 影响 63 个所选条目」（数字随仓库时点变化），可展开「查看依赖明细」看到逐条 短 hash + 提交主题 + 归属所选条目；
3. 点击「一键加入所有依赖提交」按钮，按钮短暂进入「加入中…」禁用态；
4. 观察返回的跳过清单：「⚠ 以下 20 个依赖未能纳入」，逐条列出短 hash + 提交主题 + 原因，其中 12 条为「混合提交（关联 …），无法安全归因」、3 条为「条目 X 尚未完成（当前状态：submitted）：仅已完成（done）条目可纳入」、5 条为「条目 X 不在本看板中」；
5. 对照 `git show --name-only <hash>` 核验：被判「混合提交」的提交（如 81bec844）实际变更路径只触及单一条目目录，与其标题中引用的额外单号无关——误判成立。

## 期望行为

1. **区分提交实际归属与标题引用**：归因优先核验更权威的证据链——（a）提交账本（report 自动收口记录的经核验归属）、（b）规范主题末尾归属单号（提交规范「类型: 描述 单号」，主题校验见 scripts/lib/commit-store.mjs）、（c）提交实际变更路径（如变更是否只触及单一条目目录）；仅当真实多条目归属（多个单号均经核验成立）时才判混合提交并保护，不再因正文引用单号误判。
2. **区分 Git 祖先关系与已证明的内容依赖**：分析展示不再把全部未选祖先统称「依赖」，避免将未完成或已删除条目的纯讨论 / 删除文档暗示为必须发布的功能依赖；祖先只是「普通 merge 会带入、隔离合并不带入」的提交，是否必须随版本发布应按内容依赖另行判断。
3. **保留既有门禁，不走向另一极端**：done 纳入门禁保留（未完成条目仍不可纳入、不自动完成条目）；不盲目纳入全部祖先——仅纳入经归因核验确属所选条目的提交；真实混合提交仍阻断；merging / 已正式发布锁定、发布范围变化标记（文档需重新核对 / 提交）等守卫不回退。

## 验收说明

- 以用户报告的 20 个提交为用例集：一键加入后可纳入 / 不可纳入逐条有明确且准确的原因；12 个标题引用型提交不再被判混合，按真实归属纳入发布范围（新条目或补入既有条目）。
- 构造真实混合提交反例（一个提交的变更同时触及多个条目目录）：仍被判混合并阻断，「无法安全拆分」的保护不回退。
- submitted 条目与已删除条目对应的提交仍被拦截，但原因展示准确（如实说明门禁 / 不在看板，不再以「依赖」措辞暗示其是必须纳入的功能依赖）。
- 无未选祖先时展示「所选提交无未选祖先：变更可独立进入主分支」，按钮不渲染；一键加入后发布范围变化标记、merging / 已正式发布锁定行为与现状一致。

## 界面展示

本条目涉及发布页「合并入 main」步隔离分析节的布局、交互与状态反馈（现象由「一键加入所有依赖提交」交互触发，修复会改动纳入 / 跳过原因展示）。可交互演示见 [./ui-demo.html](./ui-demo.html)（单文件、内联 CSS/JS、无外部依赖，浏览器直接打开；顶部开关可对比「缺陷现象」与「期望修复后」两种展示，并可切换有依赖 / 无依赖 / 已锁定场景）。

- **布局**：隔离分析节自上而下为——一行汇总（「发现 N 个未选祖先（依赖）提交 · 影响 M 个所选条目」+「一键加入所有依赖提交」主按钮）→ 依赖明细折叠（每条：短 hash + 提交主题 +「为 X 的依赖」）→ 一键加入结果（纳入清单 + 跳过清单）→ 单行状态条（混合提交阻断 / 豁免说明，非红色长文）。
- **交互**：点击一键加入 → 按钮进入「加入中…」禁用态防重复触发 → 返回后逐条展示纳入结果与跳过原因，不静默丢失；无依赖时按钮不渲染，显示「所选提交无未选祖先：变更可独立进入主分支」；已正式发布 / 合并中时按钮 aria-disabled，真实原因经 title 与点击 toast 三通道可达。
- **状态反馈**：
  - 缺陷现象：20 个依赖全部跳过，标题引用型被误报「混合提交…无法安全归因」，用户无法从原因分辨哪些提交其实可安全纳入；
  - 期望修复后：标题引用型按真实归属纳入并显示「✓ 已纳入」清单；仅真实混合 / 未完成门禁 / 条目已不存在被跳过，原因如实描述；真实混合提交反例在两种模式下均由单行阻断状态条提示（保护不回退）。
