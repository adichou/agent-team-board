  而在其交付时**未配套「版本错配丢数据」防护**——静态前端实时读盘立即可用新弹窗，而常驻旧服务进程

## 根因分析

见 README「2026-09-09 静态与运行时核实」：旧常驻服务（登记时 pid 10988 / startedAt 03:59:11Z）+
新静态前端（实时读盘）版本错配；旧 `/api/new` 处理器忽略请求体多余字段 `attachments`，按旧口径创建返回
201，截图数据无痕丢失（全树无 `attachments/` 目录佐证）。旧进程同时缺条目附件路由（登记时实测
`GET /api/item/:id/attachment/:name` 得 404「未知接口」）。**旧进程代码已固化不可打补丁**，任何修复只能
落在「新前端不发会丢数据的请求」或「新服务端能力探测」上。

## 方案

**前端创建前预检**（`scripts/web/app.js`，参照 BUG-20260909-005 演示链接预检先例）：

- 新增 `shotServeSupportsAttachments()`：GET `/api/item/REQ-20990101-999/attachment/probe.png`（只读探测，
  占位编号走到服务端「找不到条目」分支即止，不创建/不落任何数据）。
  - 响应 JSON error 以「未知接口：」开头（404）→ 判定服务进程早于截图功能上线 → 返回 false；
  - 2xx / 新进程对占位条目的 400 业务错误 / 网络异常 → 一律放行（保守拦截，不放大误伤面——网络异常时
    真正的创建请求同样会失败，不会静默成功）。
- `submitNew` 的需求 / Bug 分支：`newShots` 非空时先预检，false 则 toast
  「创建失败：看板服务版本过旧，提交会丢弃截图。请在终端运行 atb serve 自动重启过旧服务，然后重试」，
  不发 `/api/new`，保留弹窗、已填内容与截图（对齐 REQ-20260907-004 失败可重试口径）；
  无附件不预检（早于截图功能的旧服务上旧口径创建不受影响，S5 兼容）。

**为何不选另两个方向**：

- 服务端版本握手拒绝：握手逻辑只能进新代码，而丢数据发生在**旧进程**（代码已固化、无法热改），
  新服务端行为无法影响旧进程的 `/api/new`；且 health 携带版本需要前端在创建时刻再握手，等价于本预检
  而多一套版本号协议。
- 仅维持文档指引：不改动代码无法收敛丢数据路径，不满足期望行为「不得静默丢数据」。

**测试**：`scripts/tests/item-shot-ui.test.mjs` U8（vm + fetch mock）：

- U8a 过旧拦截：预检 404「未知接口」→ 不发 `/api/new`、错误 toast（创建失败/版本过旧/atb serve/截图）、
  截图与弹窗保留、按钮与截图入口复位。mock 响应按 README 登记时对真实旧进程的实测记录构造
  （`{"error":"未知接口：GET /api/item/REQ-20990101-999/attachment/a.png"}`）；登记时的旧进程已被
  重启（复现前置已消失），当前 8888 进程（pid 60377）实测同 URL 返回 400「找不到 REQ-20990101-999」
  → 预检放行，即 U8b 分支的真实环境佐证。
- U8b 新服务放行：400 业务错误 → 照常提交且 attachments 齐全；U8c 预检网络异常放行；U8d 无截图不预检；
  U8e 静态契约（submitNew 带附件路径必须经预检函数）。

## 风险与边界

- 带截图创建多一次只读 GET（毫秒级、无副作用），仅带附件路径触发；判定只认「未知接口：」前缀，
  与 BUG-20260907-017 / BUG-20260909-005 的既有口径一致，不新增版本协议。
- 服务端与既有防护零改动：附件后缀白名单、单张 8MB、防穿越、张数上限 9、附件端点 CSP/nosniff/no-store
  全部保持；`<img>` 加载失败占位文案口径（app.js linkupDocImages）不回归（U6 绿）。
- `atb serve` 过旧自动重启行为不回归（serve-stale.test.mjs 绿）；Electron 壳「探活复用」口径维持
  BUG-20260909-005 裁定不扩展。
- 已丢附件的存量单不可恢复（数据从未落盘），补救靠人工重建/手动放置附件；「重新上传截图」入口
  属增量功能（需新端点 + 编辑流程），超出本 Bug「不得静默丢数据」收敛范围，如需另立需求。
