# 设计 — BUG-20260929-001

## 引入来源（源单）

BUG-20260917-001，已用 `atb show BUG-20260917-001 --json` 核验真实存在。
`git log -S "function versionChip" -- scripts/web/build.js` 定位提交 `cf0f3cb`：成功发布标签仅接入列表，详情仍依赖合并状态。原有只读判断分散在条目关联、发布确认锁等局部，未建立发布成功后的全版本写入校验。

## 根因分析

发布成功（任一 succeeded 运行）与发布确认锁是两个不同事实。列表读取前者，详情只读取合并状态；信息、删除、文档和发布接口没有共用成功发布校验。后续失败不应撤销既有成功，确认后更早锁定的规则也不应因此取消。

## 实施方案

- `statusChipFor` 优先显示成功发布标签，列表、详情和删除确认保持一致。
- 前端集中枚举修改控件，渲染后设置 disabled、aria-disabled 与统一原因，取消行内编辑；捕获事件及业务处理函数再次校验。保留导航、搜索、分页、复制、审查查看及关闭入口，新建版本独立。
- 构建 POST 统一在执行回调前按 body.id 校验成功运行；发布 API 按 bldId 或运行所属版本校验，目录打开保留。数据层信息保存、删除、关联变更亦校验。
- 发布运行枚举只接受与 readRun 一致的合法编号，非运行目录不参与判断；合法运行损坏仍明确报错，写入失败封闭。
- 使用现有发布事实源和 DOM 能力，无新增依赖；引入库成本高于这些局部判定和属性设置。

## 验证与边界

新增测试先红（已发布信息保存仍成功），实现后转绿。隔离数据构造成功后失败运行，验证成功不可逆；覆盖存储拒写、前端 disabled 与键盘捕获、17 个实际 HTTP 写接口拒绝及数据不变、只读 GET 可用。既有合并标签与发布失败恢复测试继续通过。全量测试结果见 test-report.md。

不执行真实远端发布，不变更人工状态，不自动推送。
