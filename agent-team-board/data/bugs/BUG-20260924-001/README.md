# BUG-20260924-001 一键迁移失败，请修复

- 归属：独立 Bug
- 创建：2026-09-24T04:31:12.939Z
- 本文为完善阶段说明；实时状态以系统看板为准，未实施修复、未执行真实项目迁移。

## 现象

用户在一键迁移中收到以下错误，旧布局迁移无法完成：

```text
失败：迁移目标已存在：/Users/adichou/Documents/src/DarlingHelper/agent-team-board/runtime/.locks（源 /Users/adichou/Documents/src/DarlingHelper/docs/agent-team-board/.locks）；请人工核对后重试（可重试；迁移幂等，已完成部分不会重复执行）
```

界面提示可重试，但源、目标 `.locks` 目录同时存在的条件不变时，再次迁移仍会被相同检查拦截。该错误只证明目标路径存在，不能证明目录内有不同内容的文件冲突。

### 已核实的代码依据

- `scripts/lib/migrate-layout.mjs` 的 `migrateLayout` 将旧布局 `.locks` 等应用数据按整个目录交给 `movePath`；`movePath` 遇到目标存在即报错，尚未区分空目录、可合并目录与真实文件冲突。
- `scripts/web/app.js` 的设置页「数据布局迁移」提供确认、执行与失败反馈，失败后附加“可重试；迁移幂等”提示；CLI 与页面使用同一迁移实现。
- 上述为当前代码阅读结果，尚未在 DarlingHelper 项目现场执行复现；该项目源、目标目录内容、活动锁情况、首次触发版本与目标目录创建来源均为「待确认」。

## 复现步骤

### 用户现场复现路径（现场条件待确认）

1. 在 Status Board 选择 DarlingHelper 项目，进入设置页「数据布局迁移」。
2. 项目同时存在 `docs/agent-team-board/.locks` 与 `agent-team-board/runtime/.locks`。
3. 点击「一键迁移到新布局」，在确认框点击「开始迁移」。
4. 观察迁移失败及上述源、目标路径提示；保持目录条件不变再次操作，检查是否重复失败。

### 开发阶段最小复现夹具（步骤规范，尚未执行）

1. 使用隔离临时项目，准备旧布局条目文档、有效条目状态与旧 `.locks` 目录；所有锁均使用测试数据，不对实际正在运行的项目操作。
2. 预先创建新布局 `agent-team-board/runtime/.locks` 空目录，旧 `.locks` 也可为空，以排除真实文件冲突。
3. 在测试项目设置页执行迁移，或使用同一版本 CLI 执行 `atb migrate --dir <临时项目根>`。
4. 当前代码预计报「迁移目标已存在」，目标为新布局 `.locks`；该预期来自代码路径，执行证据留待开发阶段补充。
5. 扩展夹具：源和目标各放不同名称的文件，检查可合并目录场景；同名文件分别准备相同内容、不同内容，检查重复与冲突场景；另覆盖目录与文件同名的类型冲突。

## 期望行为

1. 目标 `.locks` 仅为空目录时，迁移应继续，不要求用户删除目录；源目标目录中不重名的文件应完整保留并迁入目标。
2. 同一路径、同类型、同内容的普通文件可判为已迁移或重复，不重复产生副本；不同内容同名文件与类型冲突必须保留双方数据，明确报出具体冲突路径，不静默覆盖或清空目录。
3. `.locks` 属运行数据，迁移不得以“解决冲突”为由删除有效锁、伪造解锁或让互斥失效；如何识别活动锁、是否需要暂停运行任务及完整冲突策略为「待确认」，开发时依据现有锁协议核实，不能仅按文件存在推断锁失效。
4. 部分迁移后再次执行能够继续未完成部分；真实冲突未解决时如实提示需核对，不将无条件点击重试描述为可自动解决。
5. 完成后文档归入 `data/`，应用数据归入 `runtime/` 且不进入 Git 跟踪；条目 ID、状态、标题与数量保持一致，文档内容与附件保留，不自动提交，不修改项目业务代码。
6. 修复范围为本次迁移目录碰撞与相关反馈；复用迁移入口及其既有数据保护约束，不新增自动删除、强制覆盖或锁清理入口。
