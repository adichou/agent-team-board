## 根因分析

`movePath`（scripts/lib/migrate-layout.mjs）把旧布局应用数据（`.locks`、dispatch、settings 等）
按整个目录交给 `fs.renameSync` / `git mv`，搬移前只做一次「目标存在 → 抛错」检查，没有区分三种
本质不同的情况：

1. **目标只是空目录**（新布局运行时自建，如 `agent-team-board/runtime/.locks` 被锁模块或目录
   初始化预先创建）：无任何文件碰撞，却整单失败。用户界面的「可重试」提示无法解决——源、目标
   目录同时存在的条件不随重试变化，再次执行仍在同一路径被拦。
2. **目录可合并**（源、目标各有不重名文件）：逐文件迁入即可，无需人工干预。
3. **真实冲突**（同路径一方为文件另一方为目录，或同名文件内容不同）：此时才需要人工核对。

旧实现把 1/2 一律按 3 处理，导致用户现场（DarlingHelper）只要新布局 `.locks` 已被创建，
一键迁移就永远无法完成。

## 方案

`movePath` 目标已存在时按「目录合并 / 内容判重 / 冲突上报」三分类处理（CLI 与设置页共用同一
`migrateLayout` 实现，两入口同时修复）：

1. **目录对目录**：递归合并——源目录内逐项按同口径（跟踪状态逐路径查询 `git ls-files` 快照）
   迁入目标，不重名互不干扰；迁移后源壳清空（递归内即时 `rmdir`，残留由既有 `pruneEmptyTree`
   兜底）。空目录对空目录为合并的天然边界，直接通过。
2. **同名同内容文件**（字节级比对一致）：判为已迁移 / 重复，不产生第二份副本——
   源已跟踪且目标未跟踪时，移除目标副本后走原 git mv / untrack 流程（保留历史与跟踪口径）；
   否则保留目标副本、清掉源副本（源已跟踪时经 `git rm` 退索引），计入 `moved.duplicate` 统计
   （CLI 迁移结果行新增「同名同内容判重 N 项」）。
3. **真实冲突**：同名异内容报
   `迁移冲突：<dst>（源 <src>）同名文件内容不同；双方数据均已保留，请人工核对处理后再重试`；
   目录-文件类型不一致同理报「类型不一致（源为目录/文件、目标为…）」。双方数据原样保留，
   不静默覆盖、不清目录。
4. **界面反馈对齐**（scripts/web/app.js + scripts/web/i18n.js）：迁移失败分支以
   `迁移冲突：` 前缀区分真实冲突——冲突失败渲染
   `失败：<msg>（真实冲突：需人工核对处理，直接重试不会自动解决）`，不再无条件附带
   「可重试；迁移幂等」诱导重试；其余失败（临时环境问题等）保留既有可重试提示。
   新增 EN_DYNAMIC 词条同步英文；`迁移冲突：` 判定前缀为逻辑键，入 ALLOWLIST 注明原因。

**开源选型（REQ-20260909-015）**：未引入开源库（目录合并 / 字节比对 / 冲突上报为
node:fs 原生能力的少量自研逻辑，无合适且必要的库级抽象，引入成本高于自研），不创建 licenses.md。

## 风险与边界

- **锁数据保护**：同名同内容判重仅在字节级一致时清掉其中一份副本，内容零丢失；
  内容不同一律走冲突上报，绝不以「解决冲突」为由删除任何一份——有效锁不会被删除或伪造解锁。
  活动锁识别（锁协议层）不在本 Bug 范围（README「待确认」第 3 条），如需暂停运行任务另立需求。
- **幂等与续迁不变**：源不存在仍为 no-op；部分迁移后重入按同分类续迁；迁移前后条目清单
  （ID / 状态 / 标题）核验逻辑未动。
- **git 口径不变**：跟踪文件仍优先 git mv（保历史）；应用数据仍退出版本控制本地保留；
  不自动 commit / push。
- 回归面：layout-migration / data-layout 既有用例（M1–M3、L3–L7）与 i18n 全套
  （coverage / dict / lang / runtime / wiring）全部保持通过。
