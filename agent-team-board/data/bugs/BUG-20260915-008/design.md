# 设计 — BUG-20260915-008 确认与核验流程同步跑测试阻塞看板服务数分钟，面板整体冻结且无进度提示

> 由 Agent 在 /dev 开发前补充，人可随时批注。

## 引入来源（源单）

- 引入来源：REQ-20260914-001（挂起确认闭环：`confirm-store.mjs` 的 `runProjectTests` 用 `spawnSync('npm', ['test', '--silent'], { timeout: 600_000 })` 同步跑项目测试，核验（verifyCommitConfirm）与确认并继续（confirmCommitContinue）的「补交后测试复验」都经它执行——同步阻塞自引入起即存在，测试量增长后体验恶化为面板整体冻结）。
- 关联：BUG-20260915-006（其 design「风险与边界」已预告本问题：「核验期间面板无响应属另一体验问题，如需治理另立需求：改异步 spawn + 进度上报」——本单即该治理项）。

## 根因分析

（登记时已定位，修复阶段核实行号）

`scripts/lib/confirm-store.mjs` `runProjectTests()`：`spawnSync` 是**阻塞式**子进程调用，调用期间 Node 事件循环完全停摆；它被 server 的 HTTP 处理路径同步调用（核验/确认接口），因此一个请求能把整个服务冻结到测试结束（上限 600s）。前端在等待期间没有任何进行中反馈，忙态按钮与冻结页面无法区分。

## 方案

**开源选型（REQ-20260909-015）**：无合适库（异步子进程与任务状态用 Node 内置 `child_process.spawn` + 内存任务表即可；进度回传复用面板现有 2 秒轮询，不引入 SSE/WebSocket 库——引入成本高于自研）。

方向（开发阶段细化并补测试）：

1. **异步化**：`runProjectTests` 拆出异步版本（`spawn` + Promise），HTTP 接口改为「立即返回任务句柄（taskId/条目级运行态）」，结果异步落 confirm 账本（verify 字段口径不变）。
2. **进度上报**：运行态含阶段（核验 → 补交 → 测试 → 恢复队列）、开始时间、超时上限；前端轮询读运行态渲染「测试运行中 · 已 N 秒」；账本落盘保证服务重启后可识别中断态。
3. **互斥**：同条目运行中时拒绝再次触发（提示运行中），跨条目不互斥。
4. **范围排查**：批量回执路径（run receipt / autocommit）若同样在 server 进程内同步跑测试，一并纳入异步化；CLI 直跑路径（atb 终端命令）保持同步语义不受影响。

## 风险与边界

- 异步化引入状态机复杂度：崩溃恢复（运行中任务 + 服务重启）、超时取消、与挂起闭环/队列恢复的时序一致性（不能出现「测试完成但确认未落账」）——验收 3/5 专门针对此；
- 进度粒度做到「阶段 + 时长」即可，不追求单测试文件级进度（需要解析测试输出，收益低）；
- 与 BUG-20260915-007（report 系统收口提交）有实现交集：两者都动「收尾编排」，建议排期上先 007 后 008，或合并为一个开发批次避免互相冲突。
