# BUG-20260928-005 推送完成即判定已正式发布并锁定范围，未以用户点击发布按钮并二次确认为准

- 状态：submitted（待人工接受）
- 归属：独立 Bug（引入来源见 design.md）
- 引入来源：REQ-20260926-002（发布五步重定义将「发布」的完成口径落在推送动作上：`pushed = release.pushedAt`，推送即判已发布并锁定范围，未与「用户点击发布按钮 + 二次确认」的正式发布动作绑定）
- 创建：2026-09-28T04:26:55.310Z

## 现象

BLD-20260927-001 在 2026-09-27 16:18 完成向 origin/main 的推送（pushedSha=687c88eb）后，版本立即被判为「已正式发布」：

- 版本计划发布界面显示「⚠ 暂不可合并文档：已正式发布，范围锁定（如需调整请新建版本）」，文档合并步被锁定；
- `isPushed(v)`（scripts/lib/build-store.mjs:245，判定 `release.pushedAt` 是否存在）返回 true，条目增删、文档合并等范围操作全部锁定。

但用户**没有**亲自点击发布按钮并通过二次确认——推送动作不等于用户语义上的「正式发布」。此时官网资料更新也未完成（`release.site.status=missed`），用户视角本版本尚未正式发布，却被系统锁定范围。

## 复现步骤

1. 打开 BLD-20260927-001 版本计划发布界面（已完成挑选合并与文档合并，文档提交 7a71eabc 已重放为 687c88eb 合入 main）。
2. 触发推送动作使 `release.pushedAt` 落账（本例为 2026-09-27 16:18 推送 origin/main）。
3. 观察界面提示与门禁状态。

实际结果：推送完成后界面出现「⚠ 暂不可合并文档：已正式发布，范围锁定（如需调整请新建版本）」；版本被系统判定为已正式发布，范围操作全部锁定。

## 期望行为

- 「正式发布」的判定以**用户亲自点击发布按钮并通过二次确认**为准（对应 BUG-20260928-002 补充的发布按钮交互意图）；
- 仅完成推送（自动/间接触发的 git push、或其他途径使 `release.pushedAt` 落账）**不应**使版本进入「已正式发布」锁定态；
- 未完成「点击发布按钮 + 二次确认」前，版本范围操作（文档合并、条目增删等）不应被「已正式发布」口径锁定。

## 验收标准

1. 未点击发布按钮并二次确认前，即使远端推送已完成，版本不显示「已正式发布，范围锁定」，文档合并等操作不被该口径锁定；
2. 用户点击发布按钮并二次确认通过后，版本才进入正式发布锁定态（范围锁定、提示文案与现状一致）；
3. 已推送但未经发布按钮确认的存量版本（如 BLD-20260927-001）有明确的处理口径（解锁或补确认路径），不残留歧义状态；
4. 中英文文案同步（scripts/web/i18n.js），相关测试覆盖上述判定边界。
