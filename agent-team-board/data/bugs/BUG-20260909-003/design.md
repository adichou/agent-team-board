- 引入来源：REQ-20260908-011《修改单需支持修改标题和描述。》（已通过 `atb list` 核验存在，当前 in-progress 待人工确认）

## 根因分析

REQ-20260908-011 实施时，design.md 在「按钮文案候选〔待确认〕」中默认采用了主候选「✎ 改标题/描述」
（该需求 test-cases.md U4 备注：最终文案以人工确认为准）。人工随后确认的期望简短文案为「修改」，
但代码未同步，导致列表卡片（`reqRowEl` 的 `card-rename-btn`）与详情抽屉
（`drawerActionsButtonHtml()` 的 submitted 分支）两处仍渲染「✎ 改标题/描述」。
纯前端可见文案问题：`data-rename-id` → `bindRenameButtons()` → `editItem()` 的编辑链路、
权限约束（仅 submitted）、弹窗语义均无缺陷，无证据表明编辑保存本身失效。

## 方案

- `scripts/web/app.js` 两处按钮的可见文字 `✎ 改标题/描述` → `✎ 修改`：
  - 卡片：`reqRowEl()` 内 `card-rename-btn`（列表操作区「✓ 接受 / ✎ 修改 / 🗑 删除」）；
  - 详情抽屉：`drawerActionsButtonHtml()` 的 `case 'submitted'`。
- 保持不变：按钮位置、顺序、`btn small card-rename-btn` 样式、铅笔图标、
  `aria-label="编辑 <编号> 标题与描述"`、`title="编辑标题与描述（仅待接受）"`、
  `data-rename-id` 行为链路与仅待接受权限；弹窗标题、字段名、保存/取消语义均不动。
- 测试（TDD）：`scripts/tests/edit-content.test.mjs` U1 文案断言更新为「✎ 修改」，
  新增 U6 静态契约——两处入口均显示「✎ 修改」、全文件不再出现「改标题/描述」、
  aria-label/title 保留标题与描述 + 仅待接受语义（含条目编号）。
  文案缩短后不再可能出现旧长文案导致的换行/截断；U4 的 `>修改</button>` 精确匹配
  与新按钮 `>✎ 修改</button>` 不冲突，仍能守住「无提示词编辑残留」契约。

## 风险与边界

- 「修改」文案与 BUG-20260908-022 已下线的旧「修改（提示词）」按钮重名：
  aria-label 与悬停说明仍明确「编辑标题与描述（仅待接受）」，且旧功能符号
  （`data-edit-id` 等）已全部下线，静态断言继续守护，不构成功能回退。
- 仅改可见文字，不触碰后端、权限、编辑保存逻辑；非 submitted 状态不新增任何入口。
- 弹窗标题「编辑 <编号>」是否改「修改 <编号>」为原登记待确认项，本次不改（README 已注明不列入必需范围）。
