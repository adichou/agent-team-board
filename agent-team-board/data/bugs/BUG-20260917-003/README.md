# BUG-20260917-003 挂起确认面板「归属待确认」路径缺少批量计入/排除操作，大量路径时须逐项选择

- 状态：submitted（待人工接受）
- 归属：独立 Bug（引入来源见 design.md）
- 创建：2026-09-17T08:02:24.159Z

## 现象

现象：BUG-20260917-001 提交挂起确认时，「归属待确认」路径多达 358 个（发布产物、看板共享文件等）。面板对每个路径只提供独立的「计入本次补交 / 排除」下拉（app.js renderConfirmForm → fileRow，选择存于 confirmSide.attr / confirmAttrOf），无「全部计入 / 全部排除」批量操作；且存在未处理项时确认被拦截（app.js 提交前校验 + confirmPanelMsg 提示「每个路径须显式选择」），人工须逐项点 358 次才能确认。

代码层面的事实：

- 挂起确认侧拉面板（`scripts/web/app.js` `renderConfirmForm`，develop 形态）把候选文件分两组渲染：「本单可归属（own）」与「归属待确认（undetermined）」，组头文案为「归属待确认（N）——全局 / 来源不明，不得静默归为本单」。
- 归属待确认的每一行渲染独立 `<select class="attr-select">`（`fileRow(f, true)`），选项仅三个：待选择（归属待确认）/ 计入本次补交 / 排除（保持工作区）；选择结果存于前端 `confirmSide.attr`（`Map`），组头与表格没有任何批量操作入口。
- 每次选择只就地更新「确认范围」摘要与「待核对」提示（`updateConfirmScopeSummary`，不整页重渲染）；摘要口径为「本单可归属 N 个 + 归属待确认已计入 M 个 = 将补交 N+M 个路径（排除 K 个）；U 个归属待确认未处理」。
- 存在未处理项时点「确认并继续」被 `confirmContinueAction` 拦截：红字提示「确认被拦截：归属待确认项未处理（<全部未处理路径列表>）——每个路径须显式选择「计入本次补交 / 排除」，全局文件不得静默整批归为本单」；358 个路径时该提示会把全部路径串进一行。
- 归属选择只存前端内存：面板关闭重开后 `openConfirmPanel` 将 `confirmSide.attr` 重置为空 `Map`，逐项选择须重来。
- 服务端契约：确认时 `POST /api/confirms/:id/continue` 的请求体 `include` 显式携带「计入本次补交」的路径（`scripts/lib/confirm-store.mjs`），全局文件不静默并入（BUG-20260915-003 的设计约束）。

期望：归属待确认清单提供批量操作（全部计入 / 全部排除，或分组批量：按目录/类别一键排除），并保留逐项覆盖能力；服务端口径不变（include 显式携带，全局文件不静默并入的设计保留——批量操作只是显式选择的效率工具）。

引入来源：未定位（排查过程：REQ-20260914-001 确认闭环引入逐项显式选择设计；批量操作自始缺失，非回归）。

## 复现步骤

1. 准备一个走开发流程（已 claim）的条目，除本单实现/测试文件外，在工作区制造大量归属不明的路径（如发布产物 `dist/`、看板共享数据文件等）；执行 `atb report` 收口时，自动提交判定这些路径归属不明（`pendingManual`），`scripts/lib/confirm-store.mjs` `finishRun` 据此创建 kind=develop 的提交挂起记录。（BUG-20260917-001 的现场即「归属待确认」达 358 个；路径数量不影响缺陷成立，少量路径即可复现操作缺失。）
2. 打开看板 Web 界面，进入「任务」页：顶部出现「⚠ 待人工确认（1）——阻塞队列」卡片（`renderConfirmArea`），点「查看并确认」打开右侧挂起确认面板。
3. 面板文件表分两组：「本单可归属」与「归属待确认（N）——全局 / 来源不明，不得静默归为本单」；检查组头、组内表格与页脚：没有任何「全部计入 / 全部排除」类批量操作入口，每个路径只有行内「归属处理」下拉（待选择 / 计入本次补交 / 排除）。
4. 不做任何选择直接点页脚「确认并继续」：面板红字提示「确认被拦截：归属待确认项未处理（<未处理路径列表>）——每个路径须显式选择…」，确认被拦。
5. 只能逐个把归属待确认的下拉选完（每次 change 只更新该行与摘要）；选到一半关闭面板再打开，所有已选项被重置（`confirmSide.attr` 重建为空 `Map`），须从头逐项再选。
6. 全部 358 项逐项选完后「确认并继续」才放行——按每项一次下拉计，人工须点 358 次（外加误选/重开面板重来的成本）。

## 期望行为

- 「归属待确认」分组提供批量操作入口，至少包含「全部计入」「全部排除」；是否补充按目录/前缀的分组批量（如一键排除某目录）：待确认（由 design.md 设计阶段定）。批量操作作用于组内所有未入库的归属待确认行。
- 批量操作的语义是显式选择的效率工具：把组内每行的归属显式置为对应值（等价于逐项选择），不是服务端静默归组；已入库（已提交）的行不参与批量与计数（与现状 `updateConfirmScopeSummary` 按 `state !== '已入库'` 过滤的口径一致）。
- 批量操作后：每行下拉同步显示所选值，「确认范围」摘要与「待核对」提示即时更新；用户仍可对任意行逐项覆盖（以最后一次操作为准），批量操作可反复使用、相互覆盖。
- 服务端口径不变：`POST /api/confirms/:id/continue` 请求体的 `include` 仍显式携带「计入」路径清单，全局文件不静默并入（BUG-20260915-003 设计保留）；存在未处理项时「确认并继续」仍被拦截，拦截判定与现有口径不弱化（文案可因批量入口存在而微调）。
- 面板关闭重开归属选择重置的现状保持（是否持久化逐项选择超出本单范围：待确认）。
- 新增界面文案按 BUG-20260912-001 同步中英双语（`scripts/web/i18n.js`）。

## 验收说明

1. 构造一个归属待确认 ≥ 3 条（未入库）的 develop 挂起确认，打开面板：点「全部排除」后组内所有行下拉变为「排除（保持工作区）」，摘要显示「排除 N 个」、「待核对」提示消失；点「全部计入」后摘要显示「归属待确认已计入 N 个 = 将补交 …」，两种批量均一步生效。
2. 批量后再逐项改任意一行为另一选项：摘要即时反映变化（已计入/排除个数相应增减），批量不锁死逐项覆盖；再次批量可整体覆盖逐项结果。
3. 存在未处理项时点「确认并继续」仍被拦截，拦截消息的未处理路径集合与实际未选行一致；全部处理完后再确认，请求体 `include` 与界面所选「计入」集合完全一致（服务端无静默并入，全局文件不会被批量静默归为本单）。
4. 已入库（已提交）行不受批量操作影响、不计入摘要与拦截判定；批量操作入口在面板 busy / 已确认（resolved）态与行内下拉一致禁用。
5. 新增界面文案在 `scripts/web/i18n.js` 中英双语同步并通过 i18n 相关测试；按仓库 TDD 规范在 `scripts/tests/` 新增 `bug-20260917-003.test.mjs`（先红后绿），交付前 `npm test` 全量通过。

## 界面展示

**界面布局**：演示还原「任务」页挂起确认卡片与右侧挂起确认侧拉面板（develop 形态）——面板自上而下为：标题（提交挂起 · 条目号）与范围说明、挂起原因、提交计数行、「本单可归属」分组文件表（文件/变更/状态/差异）、「归属待确认」分组文件表（文件/变更/状态/差异/归属处理下拉）、「待核对」警示、差异查看区、最近核验、处理说明输入、面板消息区、「确认范围」摘要与页脚按钮组（关闭 / 保持挂起 / 重新核验 / 确认并继续）。

**交互行为**：顶栏可切换「缺陷现状 / 期望修复后」两种模式对照——现状模式下归属待确认组只有逐项下拉，无任何批量入口（并提供点击计数器，直观展示 358 项须逐项点的痛点）；期望模式下组头出现「全部计入 / 全部排除」批量条，另有按目录批量排除的设计选项演示（是否采纳待确认）。批量与逐项选择互相覆盖，摘要与「待核对」提示即时更新；「确认并继续」在有未处理项时红字拦截（列出未处理路径），全部处理后模拟走「正在核验提交与测试…」到成功回填；每行「查看差异」可展开模拟 diff。

**状态反馈**：演示覆盖正常态（两组文件表 + 实时摘要）、空态（无待提交文件：全部路径已入库）、加载态（正在读取挂起详情…）、失败态（挂起详情读取失败 + 重试恢复）；归属选择、批量操作、拦截/成功消息、busy 按钮禁用均有即时反馈；支持深浅色切换（默认跟随系统）。
