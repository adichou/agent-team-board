# BUG-20260914-021 commit 消息对条目标题有截断，请修复

- 状态：submitted（待人工接受）
- 归属：独立 Bug（引入来源见 design.md）
- 创建：2026-09-14T15:52:11.648Z

## 现象

「开发完成到待测试」自动提交（REQ-20260911-009）拼装提交消息时，描述只取条目标题前 20 个字符，超过 20 字的标题后半句被静默丢弃。例如这条就是典型：

4d66ce5
fix: 分支浏览页面中的 main 分支通过发布 BUG-20260914-018

该条目（BUG-20260914-018）标题实为「分支浏览页面中的 main 分支通过发布流程推送的文字删掉」（29 字符），提交消息里只剩前 20 字「分支浏览页面中的 main 分支通过发布」，末尾「流程推送的文字删掉」9 字被截掉；同单 doc / test 组提交（883f0a3、815e30c）同样截断。同类实例：REQ-20260914-004「优化需求说明、设计文档中右键讨论菜单生成的提示词」（24 字符），其提交消息为「feat: 优化需求说明、设计文档中右键讨论菜单生成 REQ-20260914-004」，截去「的提示词」。

被截断的消息直接展示在看板 Web「分支浏览」页面的提交记录列表（scripts/web/build.js 渲染 `c.subject`）与 CLI `atb commit log <ITEM-ID>` 输出中，读起来是半句话。

截断源头（代码事实）：

- `scripts/lib/commit-store.mjs:19` — `DESC_MAX_CHARS = 20`：提交消息规范约定描述 ≤20 字（不含单号），`validateCommitSubject` 据此核验。
- `scripts/lib/git-flow.mjs:279`（`autoCommitForRun`，开发完成到待测试自动提交及 `atb run autocommit` 重试）与 `scripts/lib/git-flow.mjs:534`（`supplementCommitForRun`，人工确认补交 doc 组）— 两处均为 `const desc = [...String(title)].slice(0, DESC_MAX_CHARS).join('')`，再经 `commitSubjectOf` 拼成「类型: 描述 单号」。为预先通过 ≤20 字核验而截断标题，超长时既不告警也不报错。

## 复现步骤

1. 准备一个标题超过 20 字的条目（看板新建即可；历史实例可用 BUG-20260914-018，标题 29 字符）。
2. 按常规流程走完开发并上报：领取开发（`atb dev next`）→ 改动代码 / 文档 → 上报测试报告（`atb dev report ...`），触发「开发完成到待测试」自动提交（REQ-20260911-009；失败路径 `atb run autocommit <RUN-ID>` 重试同样命中）。
3. 查看提交消息，任选其一：
   - 终端：`git log --oneline -5`；
   - CLI：`atb commit log <ITEM-ID>`；
   - 看板 Web「分支浏览」页：点开对应分支，提交记录列表中的提交说明列。
4. 观察：doc / test / fix（或 feat）各组提交消息的描述均为标题前 20 字，第 21 字起内容缺失（本例缺「流程推送的文字删掉」），全程无截断告警。代码级复核见上「现象」节列出的两处 `slice(0, DESC_MAX_CHARS)`。

## 期望行为

- 自动提交各组（doc / test / feat|fix）消息的描述完整保留条目标题，不再出现半句截断；看板「分支浏览」提交列表与 `atb commit log` 展示的消息与条目标题一致、可读。
- 具体修复口径「待确认」，由开发阶段 design.md 定夺（放宽 / 取消 `DESC_MAX_CHARS` 上限；或超限标题完整保留并同步放宽 `validateCommitSubject` 核验；或超限时改为显式策略——如报错阻断、要求精简标题——而非静默截断）。无论选哪种，`git-flow.mjs` 两处截断与 `commit-store.mjs` 的 `DESC_MAX_CHARS` / `validateCommitSubject` 口径必须保持一致，不得出现「提交时截断、核验按另一套上限」的矛盾。
- 存量已截断的历史提交消息是否批量回改：「待确认」，由设计阶段决定（默认不动历史）。

## 验收说明

- 用标题 >20 字的条目走完开发 → 上报 → 自动提交流程后，`git log` / `atb commit log` 中各组提交描述均包含完整标题（可新建长标题条目实测，或以单元测试构造长标题 run 验证 `autoCommitForRun` 产出的 subject）。
- 标题 ≤20 字的条目提交消息保持「类型: 描述 单号」格式不变（回归）。
- 拼装与核验口径一致：单元测试覆盖「长标题 → 完整描述且 `validateCommitSubject` 通过」，并同步更新 `scripts/tests/dev-flow-20260911-009.test.mjs`、`scripts/tests/auto-commit-pre-dirty-20260913-006.test.mjs` 中涉及 `DESC_MAX_CHARS` 的断言；`atb run autocommit` 重试与人工确认补交（`supplementCommitForRun` doc 组）路径同样不截断。
- run-all 全量测试通过；看板「分支浏览」提交列表展示完整描述，控制台无报错。

## 界面展示

本 Bug 现象在看板「分支浏览」页面的提交记录列表中直接可见（展示被截断的 commit 消息），修复后同一列表展示完整标题。布局 / 交互 / 状态反馈说明：

- 界面布局：仿看板分支浏览页——左侧为分支列表（本地 / 远端两组），右侧为选中分支的提交记录面板（头部是分支名与搜索控件，下方是提交列表：hash、提交说明、作者 · 时间）；面板上方另设「条目标题 ↔ 提交消息对照卡」，直接呈现标题在第 20 字处被截断的位置。
- 交互行为：点击左侧分支加载该分支提交记录；搜索框输入关键词点「搜索」按提交说明 / 作者 / hash 过滤，点「清除」恢复默认列表；「模拟读取失败」开关可演示读取失败后的行内报错与「重试」恢复；核心是「修复前 / 修复后」切换——修复前提交说明只显示标题前 20 字并高亮截断点（悬停可见完整标题与缺失字数），修复后显示完整标题，可逐条对照差异。
- 状态反馈：加载中（「加载提交记录中…」）、正常列表、搜索无命中空态（「没有匹配的提交」+ 一键清除）、空分支（「该分支暂无提交」）、读取失败（行内错误 + 重试按钮）；深浅色跟随系统（可选能力，演示已适配）。
