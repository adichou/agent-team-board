# 设计 — BUG-20260910-011 bug 的说明文档还是没有写上 ui Demo

> 由 Agent 在 /dev 开发前补充，人可随时批注。

## 引入来源（源单）

- 引入来源：BUG-20260908-017（`atb list` 核验存在，in-progress）。其修复更新了提示词生成
  （buildRefinePrompt/buildRefineWorkerPrompt 的 Bug 侧界面展示口径）与 `analyzeItemDocs` 的
  Bug 侧演示三查，但未覆盖三个既有面：①批次提示词按 REQ-20260908-020 设计在创建时冻结，
  长跑批次（RFB-20260909-016~022 时代）沿用旧口径，BUG-20260910-001 的展示层归一仅做词语级，
  未覆盖 Bug 演示口径差异；②`finishRefineRun` done 核验沿 REQ-20260908-020/025 口径只验
  「真实变更」不验完整性；③UI 关键词启发式（REQ-20260908-015）的探测文本不含标题，
  登记未带 `--desc` 时现象/期望为占位文本导致漏报。三者叠加 → 003~007 完善后无演示仍被记「已完善」。

## 根因分析

（与 README 三条成因一致，核验属实）

1. 长跑批次冻结旧口径提示词：`refine/batches/RFB-20260909-022/batch.json` 的 `prompt` Bug 分支
   只有「Bug 补现象/复现步骤/期望行为/验收说明。」，约束行演示创建权限只给需求
   （「涉及 UI 的需求可另建约定的 ui-demo.html」）——003~007 在该口径下完善并回执成功。
2. `finishRefineRun`（refine-store.mjs）对 result=done 只核验 summary 非空且 ≤200 字、状态
   accepted|planned、指纹相对冻结基线有变化，不重跑完整性判定——`analyzeItemDocs` 对 003/004/006/007
   报「涉及 UI 缺 ui-demo.html 演示」、对 005 报「涉及 UI 需界面展示」（实测 complete:false），
   五者却均为 refined，标记与判定矛盾。
3. `uiDemoReasons` 探测文本为 Bug 的 现象+期望行为 节正文；未带 `--desc` 登记时两节为占位/空，
   标题中的 UI 关键词（如 007「操作按钮」）不参与探测 → 领取缺失原因无任何 UI 演示提示；
   词表外界面词（010 的「边框」）同样漏报（演示系执行端按新提示词主动补齐）。
4. 附加事实：005 的界面展示节用的是三级标题「### 界面展示、交互与状态反馈」，`sectionsOf`
   只识别 `##` 二级节，分析器视其为无节。

## 方案

**开源选型（REQ-20260909-015）**：无合适库——本修复全部为项目内部完善流程逻辑
（Node 内置 fs/crypto/child_process 即可），不引入任何第三方依赖，不创建 licenses.md。
自研理由：无合适库（领域专属的看板账本/启发式判定逻辑，无可复用的开源实现）。

### 定案 1 —— done 回执核验增加完整性门槛（范围：UI 演示三查）

`finishRefineRun` 对 result=done 在「真实变更」指纹核验之后，重跑 **UI 演示三查**
（与 `analyzeItemDocs` 同一 `uiDemoReasons` 函数与同一探测文本口径），仍报缺失原因时
拒绝回执，错误信息附原因清单与补齐指引（界面展示节链接 ./ui-demo.html + 条目目录创建
可交互演示），或提示改用 `refine fail` 登记原因。

- **为什么只重跑 UI 三查而非全量 `analyzeItemDocs`**：README 允许「或至少 UI 演示三查」。
  其余维度（四节齐备 / 说明不过简）是内容质量软启发式，REQ-20260908-020/025 的历史回执口径
  从未以其为门槛，存量「短说明即 done」的合法形态大量存在（既有测试夹具即如此）；UI 演示是
  可机械判定的硬性产物（文件存在性/占位/链接），本 Bug 的实害（已完善却无演示）正在于此。
  全量门槛会把大量与 UI 无关的历史合法形态一并拦下，超出本 Bug 修复面。
- **不做人工豁免机制**：启发式误判已有文档级出口——界面展示节写明「不涉及界面改动」即免三查
  （沿用 015 兜底）；真无法补演示的场景走 `refine fail --reason` 留痕（账本可查），不再新增
  豁免通道，避免降低质量门槛。
- 条目类型取 `resolveItemDir` 的 type（与候选冻结同源）。
- 门槛同时作用于需求与 Bug（同一 uiDemoReasons；需求侧演示三查口径本身不变，只是补上门槛）。

### 定案 2 —— 领取时 UI 探测补漏

- **探测范围**：Bug 的探测文本在 现象+期望行为 之上，纳入 **README 一级标题行**（即条目标题，
  `# BUG-… 标题`）——未带 `--desc` 登记的 Bug 标题含 UI 关键词时，领取缺失原因报
  「涉及 UI 需界面展示」。`--desc` 原文落盘在现象节内、本就在探测文本中，无需另读。
  **需求侧探测文本不变**（仍仅描述节）——需求侧口径按零回归要求不动。
- **词表增补「边框」**（010 实测漏报词；与 按钮/输入框 同级的界面词），UI_KEYWORDS 与其固化
  断言测试（refine-store.test.mjs S5 词表）同步更新。
- **三级标题层级识别不并入本修复**：`sectionsOf` 改动影响全量条目的节判定（说明过简计数、
  各节缺失原因都会变），风险大于收益；存量 005 的 README 由定案 4 直接规范为二级节。

### 定案 3 —— 长跑批次口径同步（账本不回写）

- **展示层归一扩展**（normalizePromptForDisplay 两条新规则，沿用 BUG-20260910-001 口径：
  仅展示/回显层，账本文件原样保留）：①RFB-20260909-016~022 时代冻结的 Bug 分支行
  「design/test-cases 留待开发阶段；Bug 补现象/复现步骤/期望行为/验收说明。」→ 现行四行
  （含「涉及 UI 的 Bug……同样须提供界面展示」与质量门槛）；②旧约束行
  「只编辑条目目录下 markdown（涉及 UI 的需求可另建约定的 ui-demo.html）。」→
  「（涉及 UI 的需求或 Bug 可另建约定的 ui-demo.html）。」。为防两处字面量漂移，
  Bug 分支行与演示质量门槛文案常量收敛到 task-settings.mjs（沿用 REFINE_SCHEDULER_* 常量
  模式，refine-store 反向 import，避免环引），生成层与归一层共用唯一事实源。
- **领取侧现行口径已具备**：CLI `atb refine next` 输出的「下一步」行已携带现行口径
  （Bug 侧「涉及 UI 的 Bug 同样须界面展示——创建可交互 ui-demo.html 并在界面展示节链接
  ./ui-demo.html」）——执行 Agent 无论拿到哪个时代的冻结提示词，领取输出都以现行口径为准；
  本次以回归测试固化该行，防回退。不改为在 nextRefineItem 返回值中新增字段（CLI 文本输出
  即执行 Agent 的直接信息面，改协议载荷属扩大面）。

### 定案 4 —— 存量 BUG-20260910-003~007 补齐（由本 worker 直接补演示）

不采用「重新接受触发再完善」（需人工操作）与「人工豁免」（降低质量门槛）：由本修复直接
在五个条目目录创建 ui-demo.html（单文件、内联 CSS/JS、无外网依赖、可交互，对照缺陷现象与
修复后状态），并在 README 界面展示节链接 ./ui-demo.html、清理「未创建 HTML 演示」的过时声明；
005 的「### 界面展示、交互与状态反馈」规范为二级节「## 界面展示、交互与状态反馈」。
补齐后 `analyzeItemDocs` 对五者 complete（验收时逐项核验）。

## 风险与边界

- **done 门槛对在途完善批次的影响**：核验时点（2026-09-10）所有完善批次（RFB-…-023）均已
  finished、无在途运行，门槛上线即生效且无在途回执可被拦。此后新回执被拦时错误信息给出
  可操作指引（补演示 / refine fail），Agent 可自愈。
- **标题探测的影响面**：仅 Bug 侧新增；对既有 refined 条目只影响候选展示原因（无批次运行中，
  不触发 done 门槛），不影响需求侧与指纹（FINGERPRINT_VERSION 保持 v2，指纹口径零变更）。
- **归一规则为整行精确匹配**：只覆盖 RFB-20260909-016~022 时代两种已知形态（本 Bug 成因 1
  的冻结原文）；更早（RFB-20260908-001~015，无演示口径时代）的已结束批次提示词不再逐一归一
  ——领取侧现行口径行（定案 3）对任何时代的执行 Agent 均生效，账本原文不回写。
- **存量补齐不改动缺陷事实**：演示按各 README 界面展示节的文字定案绘制，其中「待确认」项
  在演示中以示意标注，不虚构已确认事实。
