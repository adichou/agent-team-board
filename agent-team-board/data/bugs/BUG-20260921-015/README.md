# BUG-20260921-015 一键加入依赖跳过已关联条目的其他提交，导致发布范围不完整及实现代码漏发风险

- 状态：submitted（待人工接受）
- 归属：独立 Bug（引入来源见 design.md）
- 创建：2026-09-21T10:58:08.935Z

## 现象

在构建模块「版本计划 → 合并入 main」步，「隔离分析」发现所选提交存在未选祖先（依赖）提交。点击「一键加入所有依赖提交」后：

- 界面出现跳过清单「⚠ 以下 12 个依赖未能纳入」，逐条原因为「条目 … 已在本版本（当前关联另一提交）」；toast 反馈「⚠ 未能加入任何依赖提交（原因见隔离分析清单）」。
- 被跳过的 12 个提交是 6 个已关联条目的其余提交（多为 feat / fix / test）。「关联条目与提交」列表中对应条目仍只关联原提交，发布范围未变化。
- 重复点击按钮结果完全相同（接口幂等但依旧跳过），无法经此入口补齐；隔离分析持续显示 12 个未选祖先，警告常驻不收敛。
- 合并入 main 经临时工作树逐条 cherry-pick、只重放所选提交：同条目未选中的实现 / 测试提交不会进入主分支，存在发布缺少实现代码的风险（本次排查未执行合并，不将风险表述为已发生漏发；祖先关系本身也不等于已证明存在语义依赖，见「影响」）。

伴随缺陷：对尚未在本版本中的新依赖条目，若其有多个依赖提交，接口也只保留其中一个「最新」提交，其余提交同样不进发布范围。

## 复现步骤

前置条件：项目为 git 仓库，dev 分支上同一条目存在多个提交（如 doc + feat + test），且版本计划中该条目已关联其中一个提交（如 doc 提交）。

1. 打开 Web 界面「构建 → 版本计划」，左侧选中版本计划 BLD-20260920-001，进入「合并入 main」步。
2. 「隔离分析」节显示汇总行「发现 12 个未选祖先（依赖）提交 · 影响 6 个所选条目」，右侧有「一键加入所有依赖提交」按钮；展开「查看依赖明细」可见逐条短 hash、提交主题与「为 … 的依赖」归属。
3. 点击「一键加入所有依赖提交」：按钮短暂变为「加入中…」（执行中禁用重复触发）。
4. 实际结果：toast「⚠ 未能加入任何依赖提交（原因见隔离分析清单）」；隔离分析节内出现跳过清单，12 条原因均为「条目 … 已在本版本（当前关联另一提交）」；汇总行仍为「发现 12 个未选祖先（依赖）提交」；切到「关联条目与提交」步，6 个条目的 commit 关联未变化（每条目仍只有原关联提交）。
5. 再次点击「一键加入所有依赖提交」：结果与第 4 步完全相同，无法补齐。

期望结果见「期望行为」。

## 定位记录
- scripts/server.mjs 的 add-dependencies 接口按提交查归属，但 inVersion.has(itemId) 时直接 skipped；git blame 指向 02cde5ad（REQ-20260921-015）。
- scripts/lib/build-store.mjs 的 normalizeItems 禁止 itemId 重复，版本模型仅允许一条目一个 commit。
- 同一新依赖条目有多个提交时，接口也仅保留一个所谓最新提交。
- scripts/lib/build-git.mjs 的 analyzePublishIsolation 按 hash 计算未选祖先；mergeIsolatedIntoMain 则逐个 cherry-pick，仅重放选中提交的差异，不自动包含祖先提交。
- scripts/tests/req-20260921-015.test.mjs 的 B2 测试将「已有条目其他提交被跳过」写成预期，缺少同条目多个提交完整纳入并发布的验证。

## 影响
四个条目当前只选中了 doc 提交，实际 feat/fix 在跳过清单中，存在合并冲突或发布缺少实现代码的风险；本次排查未执行合并，不将风险表述为已发生漏发。祖先关系本身也不等于已证明存在语义依赖。

## 期望行为

- 发布范围应支持一个条目的多个提交；「关联条目与提交」界面能体现条目关联的全部提交。
- 「一键加入所有依赖提交」按提交 hash 去重（而非按条目去重）：保留条目原有关联，补齐已在本版本条目的其余符合纳入条件的依赖提交；同一新条目有多个依赖提交时全部保留，不再只取「最新」一个。
- 补入的提交按 Git 依赖顺序参与合并重放；隔离分析、合并执行与发布包含性校验使用一致的提交集合。
- 不能仅隐藏警告、用后续提交替换原关联，或把所有同条目祖先视为已发布。
- 界面反馈：一键加入成功且全部依赖可纳入时，隔离分析收敛为「所选提交无未选祖先」、按钮随依赖消失；跳过清单仅保留真正无法纳入的提交并逐条说明原因；成功后按既有机制标记发布范围变化（文档需重新核对 / 提交）。
- 具体数据兼容与迁移方案在开发阶段明确。

## 验收标准
- 同一条目已有一个关联提交时，可补入其余符合纳入条件的依赖提交；上述 12 个提交不再因条目已存在而跳过。
- 同一新条目有多个依赖提交时全部保留，不再只取一个提交；重复执行幂等，不重复添加。
- 隔离分析、合并执行和发布包含性校验使用一致的提交集合；对全部依赖均可纳入的场景，添加后未选祖先集合清空。
- 通过真实临时 Git 仓库验证 doc/test/feat 多提交场景：合并结果包含实现、测试和文档内容，不能只断言提示消失。
- 保持未完成、跨版本占用、混合归属和发布锁定等已有校验；真正无法纳入的提交明确说明原因。
- 兼容已有单提交版本数据，保留范围变化文档门禁、合并失败重试和增量合并行为。
- 补充先红后绿回归测试；新增界面文案中英文同步，交付前 npm test 全量通过。

### 验收说明
- 界面路径验收：按「复现步骤」操作，修复后第 4 步应看到成功 toast 与跳过清单消失 / 收敛，第 5 步重复点击幂等（无重复添加、无新增警告），「关联条目与提交」列表可见各条目补齐后的全部提交。
- 数据路径验收：以真实临时 Git 仓库构造 doc/test/feat 多提交场景，执行一键加入并合并入 main，核验主分支包含实现、测试与文档内容（不能只断言警告文案消失）；npm test 全量通过（含先红后绿回归测试）。
- 界面对照演示见「界面展示」。
