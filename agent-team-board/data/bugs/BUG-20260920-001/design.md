# 设计 — BUG-20260920-001 在一个旧目录架构的项目中，点击设置界面提示如下文字，无法进行目录迁移

> 由 Agent 在 /dev 开发前补充，人可随时批注。

## 引入来源（源单）

- 引入来源：REQ-20260909-001 × REQ-20260916-007（两单号均经 `atb list` 核验真实存在，2026-09-20 修复时归因）。
- 排查过程：REQ-20260909-001 重构设置页时引入「`/api/dispatch/settings` 读取失败即整页替换设置视图并 return」的早退模式；REQ-20260916-007 随后把「数据布局迁移」入口并入该视图、与派发设置并行加载。旧布局项目（无 `agent-team-board/` 数据目录）派发设置接口在服务端必然失败（`/api/dispatch/*` 于 dataDir 缺失时报「未找到 agent-team-board，请先初始化」），早退把并行发起、本可成功的布局检测结果一并丢弃，迁移入口随整页错误消失。两单单独看均合理，组合后在本场景显性化。

## 根因分析

- 服务端 `/api/layout/state`、`/api/migrate` 本就设计为无需已初始化看板（按请求体 path 执行），旧布局可检测、可迁移（layout-migration-20260916-007 已覆盖）。
- 缺陷纯在前端 `renderSettingsView()`：派发设置读取失败时 `view.innerHTML` 整页替换为「设置加载失败 + 重试」并提前 return，既丢弃同轮并行加载结果，也阻止迁移分区渲染；「重试」只会原样重进，无法恢复迁移入口。

## 方案

- 把派发设置读取抽为 `loadDispatchSettings()`：失败只记录到 `state.codex.settingsError`，不再中断整页渲染；设置页新增独立「派发设置」分区就近显示原因与重试（`#csRetry` 只重读该设置并重绘，不动迁移卡片）。
- 各分区（官网仓库 / 批量任务 / Git 工作流 / 数据布局迁移）失败反馈本就各自独立（loading / error / 数据三态），整页早退移除后天然满足「互相独立、迁移入口保留」。
- **开源选型（REQ-20260909-015）**：未引入开源库。理由：本单为设置视图渲染控制流的分区化错误反馈修复，属既有前端 stub 结构内的局部改动，无对应能力开源库可复用（无合适库）。

## 风险与边界

- 服务端不动：`/api/dispatch/*` 未初始化仍拒绝（派发能力本就要求已初始化看板），`/api/layout/state`、`/api/migrate` 口径不变。
- 旧契约同步：settings-runparams-removed-20260909-011 T3/T4 原锁定「整页设置加载失败」行为，随本单改为「局部失败 + 重试、整页不再替换」。
- 词典清理：整页键「设置加载失败：◇」随唯一使用点移除，替换为「派发设置加载失败：◇」，中英同步（i18n-coverage 卡点校验）。
