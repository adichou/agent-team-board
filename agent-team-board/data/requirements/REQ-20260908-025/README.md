# REQ-20260908-025 完善文档指纹算法版本化，避免基线口径不一致导致误报

## 描述

背景：REQ-20260908-021 给完善文档指纹算法新增 ui-demo.html 后，常驻看板服务冻结的旧算法基线与新 CLI 复核口径不一致，导致 refine 领取时误报「冻结后文档已被人工编辑，基线失效」而跳过。运行账本核实（docs/agent-team-board/refine/runs/）：RFB-20260908-010 与 RFB-20260908-011 两批共 4 条 skipped 同因，条目为 BUG-20260908-017 / BUG-20260908-018（原文所写 BUG-20260907-017/018 与账本不符、该编号目录亦不存在——server.mjs L1174 注释引用的 BUG-20260907-017 是「/api/health 暴露 pid/启动时间」另一桩；本条按账实修正），对应 run：run-20260908-220809-092d、run-20260908-220809-a6f8（RFB-20260908-010）、run-20260908-220942-f557、run-20260908-220942-5549（RFB-20260908-011），出局原因均为「冻结后文档已被人工编辑，基线失效」。需求：指纹随基线一起记录算法版本，复核时按冻结时的版本口径重算比对，算法演进不使存量基线失效；算法升级时给出明确迁移/失效策略。

### 现状（源码为真实路径）

- 指纹无版本标识：`docsFingerprint`（scripts/lib/refine-store.mjs L223-234）对 `DOC_FILES`（L44：README.md / design.md / test-cases.md / ui-demo.html，REQ-20260908-021 起纳入演示文件）逐文件内容做 sha1（缺失记 `<missing>`），返回裸 40 位十六进制哈希；参与文件集与哈希构造没有任何版本概念。
- 基线冻结四处、均为裸哈希落盘：`createRefineBatch`（L438，创建时初始值）、`absorbNewRefineCandidates`（L636，吸收新候选时）、`requeueReacceptedRefineItems`（L655，终态后重新接受重排队时）、`nextRefineItem`（L715，领取时重冻结——BUG-20260908-011）；`batch.candidates[].baseline` 只有 `['baseline','id','reasons','title','type']` 字段（现存批次 RFB-20260908-014 可证），无算法版本。
- 比对三处、全部「当前代码算法重算 === 裸基线」直比：① zcode 路径 done 核验 `finishRefineRun`（refine-store.mjs L798）；② codex 执行前复核 precheck（scripts/server.mjs L882，不一致即出局「冻结后文档已被人工编辑，基线失效」）；③ codex 结算 settle（server.mjs L960，changed = 重算 !== 基线）。
- 跨时点/跨进程必然漂移：`atb refine next`（冻结）与 `refine done`（比对）是两次独立 node 进程；server 为常驻进程（server.mjs L1174-1176 注释自认「服务为常驻进程、路由集启动时固化……代码更新后旧进程缺新接口」，由 `atb serve` 版本检测自动重启兜底）。算法在冻结与比对之间演进时（如 REQ-20260908-021 给 DOC_FILES 增加第四个文件，使所有条目的哈希值整体改变），旧基线对新算法重算必然不等——「人工编辑」判定失真，即事故成因。
- BUG-20260908-011 已消除「创建→领取之间人工编辑」的误报（领取时重冻结），但未解决「冻结方与比对方算法版本不一致」这一层：裸哈希一改算法就全部失效，且无法从哈希本身区分是哪种历史口径（REQ-20260908-021 前三文档 / 后四文档）产生的。

### 目标

1. **指纹自带算法版本**：`docsFingerprint` 产出「版本 + 哈希」形态的指纹；四处冻结点统一随基线记录冻结时的算法版本。
2. **按基线版本重算比对**：三处比对点按基线记录的版本选择对应口径重算当前文档指纹再比——算法演进后，存量旧版本基线仍得出正确结论（未编辑→一致、有编辑→不一致）。
3. **人工编辑检测语义不变**：版本化只消除「算法不同」假阳性；同版本口径下领取后文档确实被人工改动的，codex precheck 仍出局、zcode done 核验行为不变。
4. **算法升级迁移/失效策略成文**：版本常量与升级登记要求（调整 DOC_FILES 或哈希构造必须登记新版本并保留旧版本重算能力）、旧版本重算实现的保留与废弃时机、存量裸哈希基线的确定性兼容/迁移规则，形成书面策略。

### 边界与非目标

- 不改基线的用途与语义：仍只用于「领取后文档确有变更」核验与 precheck 人工编辑出局，不新增其他用途。
- 不做 server 热重载/模块刷新：常驻进程代码陈旧由既有 `atb serve` 版本检测自动重启机制兜底；本需求只保证旧版本基线在新算法代码下仍正确可比对。
- 已结束（finished）批次的存量裸基线不做回溯迁移（无比对需求）；RFB-20260908-010/011 的 4 条历史 skipped 账本不回改。
- 版本标识具体形态（字符串前缀如 `v2:<sha1>` 还是结构化字段）、历史口径重算的实现方式（保留旧版本函数还是参数化分派）：design.md 定案。
