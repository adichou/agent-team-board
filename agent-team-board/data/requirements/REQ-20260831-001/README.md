# REQ-20260831-001 /dev 先出实现方案并置「待对齐」，人工对齐后再实施

- 状态：submitted（待人工接受）
- 创建：2026-08-31T12:44:31.427Z

## 描述

改造 /dev 流程：1) 先读取需求/Bug 的 README、design、test-cases 等说明文档；2) 先输出一稿实现方案（写入 design.md 并在会话中呈现），不直接开始写代码；3) 输出方案后，条目状态置为新状态「待对齐」（pending-alignment）；4) 与用户对齐方案（会话讨论、必要时修订 design.md），用户确认后才开始实施（进入 in-progress 的 TDD 开发）。需要扩展状态机与看板：新增「待对齐」状态及对应列/按钮，claim 语义调整为 accepted → 待对齐（或等效设计），「待对齐 → in-progress」的对齐确认必须由人工触发。注意与 /dev loop 的交互：loop 模式下每个条目也应停在待对齐等人工对齐（或提供经用户明确同意的跳过方式），具体设计在 design.md 阶段定。

## 验收标准

**流程（/dev 命令与 skill 规范）**

- [ ] `/dev <ID|next>` 先读说明文档，输出实现方案初稿（写入该条目 `design.md` 并在会话中呈现），**不直接开始写代码**。
- [ ] 方案输出后条目状态为「待对齐」；用户对齐确认后才进入实施（TDD 开发），确认动作由人工触发（会话明确同意或看板按钮），Agent 不得自行推进。
- [ ] 对齐过程中可按用户意见修订 `design.md`，修订后再等确认；实施阶段以最终对齐版方案为准。
- [ ] 文档信息不足时，在方案阶段（而非实施中途）提出澄清问题。

**状态机与看板（运行时代码）**

- [ ] 新增状态「待对齐」，流转：`accepted ──Agent claim+出方案──▶ 待对齐 ──人工对齐确认──▶ in-progress ──人工──▶ done`；「待对齐 → in-progress」与 accepted/done 一样属于人工专属，Agent 与钩子侧均受保护。
- [ ] Status Board 新增「待对齐」列与「对齐确认」按钮；卡片拖拽、2 秒轮询、深浅色正常；`atb list/show` 输出新状态。
- [ ] 旧数据兼容：已有条目（in-progress 等）不受迁移影响，历史记录可追溯状态变更。

**与 loop 的交互**

- [ ] `/dev loop` 遵守同一闸门：每条目出方案后停在「待对齐」，不未经对齐直接实施；批量对齐/经用户明确同意的跳过方式在 design.md 定稿。

**不破坏**

- [ ] `/req`、`/bug`、`/board` 及状态机其余流转边不受影响；现有测试全过。
