# REQ-20260914-007 人工确认完成和版本合并成功后自动提交管理文件，失败时明确提示并支持重试

- 状态：submitted（待人工接受）
- 创建：2026-09-14T15:39:19.803Z

## 描述

本需求为两个人工闭环入口补上管理记录的自动入库：人工「确认完成」（条目 in-progress → done）操作成功后，自动提交本次操作更新的条目 status.json，以及本次确有刷新的 confirmations.md、decisions.md 等条目管理留痕文档；版本「合并入 main」成功写入最终结果后，自动提交对应的 builds/versions/<版本编号>/version.json 及本次操作实际更新的必要管理记录，使这些状态记录不再长期积累为未提交状态。

自动提交只包含本次操作对应的管理变更：不使用全量 git add，不夹带业务源码、其他条目、未跟踪需求资料或用户预先暂存的内容，目标文件含无法安全分离的其他变更时明确报告待人工处理；提交说明包含操作类型及条目/版本编号；同一仓库的 Git 写操作串行协调；无变化时视为已同步，不制造空提交；重复请求和失败重试不重复执行完成确认或版本合并本身。版本记录提交到持有最终版本数据的分支（合并目标 main），不擅自切换当前工作区分支、不推送远端。

提交失败不得伪装成完整成功，也不撤销已成功的业务操作：条目保持已完成、版本保持已合并，界面在完成状态/合并结果附近展示独立的「管理记录提交」反馈——提交中显示进度提示并禁用重复重试；成功显示提交短 SHA；失败显示持续可见（刷新后仍可见）的提示，包含原因、未提交文件列表、处理建议和「重试提交」按钮，重试只补交管理记录，成功后清除失败提示。CLI / API 调用同样返回可识别的提交结果，不能只写后台日志。

## 背景
人工确认完成和版本合并成功会继续更新看板管理文件，但这些更新未自动进入 Git，造成状态记录长期积累。本次已手动补交 30 个状态文件、1 个人工确认记录和 1 个版本记录。

## 目标与范围
1. 人工点击「确认完成」且操作成功后，自动提交本次操作更新的条目 status.json，以及本次确有更新的 confirmations.md 等对应管理记录。
2. 版本合并成功并写入最终结果后，自动提交对应 builds/versions/<版本编号>/version.json，以及本次操作实际更新的必要管理记录。明确提交所在分支，确保记录保存在持有最终版本数据的分支，不擅自切换当前工作区或推送远端。
3. 每次提交仅包含本次操作对应的管理变更；不得使用全量 git add，不夹带业务源码、其他条目、未跟踪需求资料或用户预先暂存的内容。目标文件含无法安全分离的其他变更时，明确报告待人工处理。
4. 提交说明包含操作类型及条目/版本编号；串行协调同一仓库的 Git 写操作。无变化时视为已同步，不制造空提交；重复请求和失败重试不得重复执行完成确认或版本合并。

## 界面与交互
在条目详情的完成状态附近，以及版本详情的合并结果区域展示独立的「管理记录提交」反馈。业务操作成功但提交失败时保留真实的已完成/已合并状态，明确区分两种结果。
提交中显示进度提示并禁用重复重试；成功显示提交短 SHA；失败显示持续可见的提示（刷新后仍可见），包含原因、未提交文件列表、处理建议和「重试提交」按钮。重试只补交管理记录，成功后清除失败提示。沿用现有布局和深浅色样式；CLI/API 调用也返回可识别的失败信息，不能仅写后台日志。

## 界面展示

可交互演示：[ui-demo.html](./ui-demo.html)（单文件、内联 CSS/JS、无外网依赖、无构建步骤，浏览器直接打开；单号、标题、commit 与文件路径均为演示数据）：

- 界面布局：两个入口的状态区各自展示独立的「管理记录提交」反馈块——条目详情的完成状态（[已完成] 徽标 + 确认时间）附近，以及版本详情的合并结果区域（版本卡 + 逐条目 ✓ 合并结果）下方；反馈块内联展示提交状态、提交短 SHA 或失败明细（原因 / 未提交文件列表 / 处理建议 / 重试按钮）。沿用现有布局和深浅色样式。
- 交互行为：演示中可点击「确认完成」/「合并入 main」重放完整闭环（业务操作成功 → 管理记录自动提交）；失败状态下的「重试提交」只补交管理记录，不重放业务操作；任一提交进行中时全局禁用其他 Git 写操作入口（串行协调）；演示控制台可切换提交成功 / 无变化已同步 / Git 锁冲突 / 钩子失败 / 身份配置缺失等场景与重试结果，并支持真实页面刷新验证失败提示持久可见。
- 状态反馈：正常（提交中显示进度提示并禁用重复重试 → 成功显示「管理记录已提交 · <短 SHA>」）；空（无新变化时显示「已同步 · 无新变化」，不制造空提交）；失败（业务状态保持已完成/已合并，反馈块显示「操作已成功，管理记录提交失败」+ 原因 + 未提交文件列表 + 建议 + 重试入口，刷新后仍可见）；重试成功后清除失败提示。

## 验收标准

确认完成入口：

- [ ] 人工点击「确认完成」且操作成功后，本次更新的条目 status.json 与本次确有刷新的 confirmations.md / decisions.md 等对应管理记录被自动提交，相关文件不再遗留为未提交状态。
- [ ] 每次提交仅包含本次操作对应的管理变更：不使用全量 git add，不夹带业务源码、其他条目、未跟踪需求资料或用户预先暂存的内容，原有暂存状态不被破坏。

版本合并入口：

- [ ] 版本合并成功并写入最终结果后，对应 builds/versions/<版本编号>/version.json 及本次实际更新的必要管理记录被自动提交；最终记录所在分支与提交所在分支一致（保存在持有最终版本数据的合并目标分支）。
- [ ] 自动提交不擅自切换当前工作区分支、不推送远端；目标文件含无法安全分离的其他变更时明确报告待人工处理，不强行整文件提交。

提交纪律：

- [ ] 提交说明包含操作类型及条目/版本编号（如「doc: 人工确认完成 REQ-…」「doc: 版本合并记录 BLD-…」）；同一仓库的 Git 写操作串行协调，无并发互踩。
- [ ] 无变化时视为已同步，不制造空提交；重复请求不重复执行完成确认或版本合并，幂等不产生重复提交。

失败反馈与重试：

- [ ] Git 锁冲突、提交钩子失败、身份配置缺失等失败会清晰反馈（原因、未提交文件列表、可执行处理建议），管理文件保留在工作区，刷新页面/重启服务后仍能发现并重试。
- [ ] 提交失败不伪装成完整成功，也不撤销已经完成的确认或合并：条目保持已完成、版本保持已合并，界面明确区分「业务操作成功」与「管理记录提交失败」两种结果。
- [ ] 「重试提交」只补交管理记录，不重复执行完成确认或版本合并；重试成功后清除失败提示并显示提交短 SHA。

界面与接口反馈：

- [ ] 提交中显示进度提示并禁用重复重试；成功显示提交短 SHA；失败提示持续可见；沿用现有布局和深浅色样式。
- [ ] CLI / API 调用返回可识别的提交结果与失败原因，不能仅写后台日志。
- [ ] 自动提交自身的状态反馈不引起受跟踪文件无休止变脏（状态记录写入被忽略的账本目录或随本次提交一并收纳）。
