# REQ-20260927-003 待测试的需求支持退回已计划

- 状态：submitted（待人工接受）
- 创建：2026-09-27T08:36:58.306Z

## 描述

### 一句话目标

为需求条目补齐一条人工回退边：**开发中（in-progress）→ 已计划（planned）**——人工可把开发中的单退回已计划队列，等待开发启动后按最旧优先重新取单。

### 背景与现状（已核实）

当前状态机（`scripts/lib/core.mjs` 的 `TRANSITIONS`）为单向主干 + 三条人工回退边：

```
submitted → accepted → planned → in-progress → done
人工回退：done → in-progress（驳回完成）、accepted → submitted（驳回接受）、planned → accepted（移出计划）
```

「开发中 → 已计划」目前只有一条**专用通路**：REQ-20260911-007 的待人工决策复工（`atb hold resume` / 看板「待人工确认」区复工按钮，`hold-store` 校验决策齐备后调 `resumeItemToPlanned`），并且刻意不进通用 `TRANSITIONS`——源码注释明确普通 `setStatus` / 网页状态接口不提供此边。

由此产生的空档：

- 开发启动后（或 Agent 已认领），人工想把某张单撤下重新排期，没有通用操作——详情页开发中条目只有「✓ 确认完成」一个状态操作（`scripts/web/app.js` 的 `drawerActionsButtonHtml`）；
- 终端 `atb status <ID> planned` 对开发中的单报「非法流转」；
- 唯一出路是让 worker 走 hold 受阻声明再人工复工，为「撤单重排」引入整套决策闭环，语义不匹配、链路也长。

### 目标方案

1. **状态机**：开放人工回退边 in-progress → planned（进通用 `TRANSITIONS`；`planned` 仍在 `HUMAN_ONLY_TO`，人工专属铁律不变）。
2. **清理口径**：退回时清空 owner、删除认领锁、释放实施占用（与「待人工决策复工」「驳回完成」同口径），历史留痕；实施互斥恢复可用。
3. **网页入口**：详情页开发中条目操作区新增「↩ 退回已计划」按钮（warn 风格，对齐「↩ 移出计划」「↩ 驳回完成」）。
4. **终端入口**：`atb status <ID> planned` 对开发中的单放行；非法流转报错文案同步更新合法路径说明。
5. **闭环完整**：与既有回退边拼通——开发中 → 已计划 →（移出计划）已接受 →（驳回接受）待接受；回已计划队列的单参与最旧优先调度重新取单。
6. **不破坏 hold 闭环**：REQ-20260911-007 复工专用通路保持原样；有活跃 hold（待人工决策未闭环）的开发中单不得借新边绕过决策闭环（见交互行为）。

### 范围与待确认

- **条目类型**：状态机为需求/Bug 共用，本边开放后 Bug 条目同链路生效；标题口径为「需求」，Bug 是否同步放开**待确认**（默认同步生效，两类型状态机不分开）。
- **批量退回**：看板列表勾选多个开发中单批量退回**待确认**（默认首版仅详情页单个操作；后续可对齐「批量移出计划」演进）。
- **撤销语义**：详情页状态操作免二次确认 + toast 附撤销（REQ-20260906-014）；「退回已计划」的撤销需把单重新置回开发中并恢复占用，语义复杂，是否提供**待确认**（默认首版仅成功提示、不附撤销）。
- **done 是否直达已计划**：已完成单仍走「驳回完成（退回开发）」，不提供 done → planned 直达边（单阶段回退口径，REQ-20260903-001）；如需**待确认**（默认不做）。

## 界面展示

本条改动 Status Board（详情页操作区 + 状态反馈），属 UI 需求，界面展示见可交互演示：[./ui-demo.html](./ui-demo.html)（单文件、内联 CSS/JS、无外网依赖、无构建步骤，浏览器直接打开；含正常开发中 / 有活跃 hold / 服务失败等场景切换与深浅色切换，覆盖档位联动、时间线留痕与成功 / 失败 / 禁用状态反馈，全部数据为模拟，不访问真实服务、不修改任何条目状态或文件）。

以下界面布局 / 交互行为 / 状态反馈为文字说明，与演示页对照阅读。

### 界面布局

- 详情抽屉操作区（`drawerActionsButtonHtml` in-progress 档）：现有「✓ 确认完成」（primary）旁新增「↩ 退回已计划」（warn），主操作在前、回退操作在后，样式与既有回退按钮一致。
- 看板列表：无新增列/档；退回后条目卡片从「开发中」档移入「已计划」档，状态标签同步（开发中 → 已计划）。
- 「待人工确认」聚合区（REQ-20260911-007）不受影响，布局不变。

### 交互行为

- 点击「↩ 退回已计划」免二次确认（对齐既有回退按钮）；成功后抽屉保持打开、状态区即时刷新为已计划，操作按钮切换为已计划档的「↩ 移出计划」。
- 有活跃 hold 的开发中单：按钮禁用 + tooltip「待人工决策中，请在『待人工确认』补齐决策后复工」（与 claim 防呆、确认完成防呆同口径）；是否允许显式越过（force）**待确认**（默认不提供）。
- Agent 侧仍被 state-guard 拦截（planned ∈ HUMAN_ONLY_TO），无需新增拦截面，验收时验证即可。

### 状态反馈

- 成功：toast「✓ <条目ID> 已退回已计划」；列表条目即移入已计划档；详情时间线新增一条「开发中 → 已计划」留痕（人工操作者署名）。
- 失败（状态已变化 / 服务异常）：toast 展示错误信息，界面状态不变，可重试。
- 有活跃 hold 时按钮禁用态与禁用原因稳定可见。
- 退回后的单再次被调度取单（claim）时按既有口径流转开发中，时间线可追溯完整闭环（认领 → 退回 → 再认领）。

## 验收标准

- [ ] 开发中（in-progress）条目可由人工退回已计划：网页详情页「↩ 退回已计划」与终端 `atb status <ID> planned` 双入口均可用；退回后状态为 planned，看板「已计划」档即时可见。
- [ ] 退回时自动清空 owner、删除认领锁、释放实施占用（实施互斥恢复可用，其他实施入口不再被本单阻塞）；历史留痕含操作者与「退回已计划」语义。
- [ ] 退回后的单回到已计划队列，开发启动后按最旧优先正常重新取单（claim 成功，状态回开发中）；完整闭环（认领 → 退回 → 再认领 → 上报 → 确认完成）走通且无残留锁。
- [ ] 有活跃 hold（待人工决策未闭环）的开发中单，退回入口被拦截：按钮禁用 + 引导文案（终端报错说明原因），REQ-20260911-007 的决策闭环（补齐 → 复工）行为不回归。
- [ ] 人工专属铁律不变：Agent 直写 planned（含新边）仍被 state-guard 拦截；只有人工（网页/终端）能执行退回。
- [ ] 既有回退边与防呆零回退：done → in-progress、accepted → submitted、planned → accepted、确认完成 hold 防呆、完善中驳回拦截（REQ-20260908-020）均不受影响；`atb status` 非法流转报错文案更新后仍准确列出合法路径。
- [ ] Bug 条目同链路行为与需求一致（若「范围与待确认」定为不同步，以人工确认结论为准并在 design 记录）。
- [ ] UI 状态反馈符合「界面布局 / 交互行为 / 状态反馈」三节：成功 / 失败 / 禁用（hold）三态可见，深浅色与既有按钮、toast 风格一致；新增文案中英文同步（`scripts/web/i18n.js`）并通过 i18n 相关测试。
