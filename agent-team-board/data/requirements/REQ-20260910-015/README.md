# REQ-20260910-015 创建需求或 bug，支持创建并接受

- 状态：accepted（已接受；实际状态以 status.json 为准）
- 创建：2026-09-10T04:54:08.101Z

## 描述

看板当前创建需求 / Bug 的所有入口都固定落「待接受（submitted）」，接受必须人工再做第二步：Web 看板列表的「✓」按钮、详情页「✓ 接受」、待接受档的「接受所选」批量，或终端 `atb status <ID> accepted`。对明确要做的单子，人工要在「填写创建表单」和「找到新单再点接受」之间往返两次，创建与接受被割裂成两个动作。

本需求：在**人工**创建需求或 Bug 时支持一步到位「创建并接受」——同一次操作里完成创建与接受，条目直接以 accepted 状态出现在看板，省去人工二次接受。覆盖两个人工入口：Web 看板统一新建弹窗与终端 `atb new` 命令。讨论单（ask 类型）没有接受概念，不在本项范围内。

### 现状依据（基于当前代码，2026-09-10 核实）

- 创建固定 submitted：`scripts/lib/core.mjs` `createItem()`（第 521–574 行）写死 `status: 'submitted'`，history 首条 `from: null → submitted`；CLI 帮助文案也是「创建需求（状态 submitted）」（`scripts/atb.mjs` USAGE 第 44–45 行）。
- CLI 入口：`atb new req|bug <标题> [--desc <描述>]`（`scripts/atb.mjs` 第 175–198 行），创建后提示「等待人工接受（Status Board『接受』或终端 atb status <ID> accepted）」。
- Web 入口：统一新建弹窗（`scripts/web/index.html` 第 178–217 行：类型 / 标题 / 描述 / 截图区块 / 底部「取消 | 创建」两个按钮）→ `submitNew()`（`scripts/web/app.js` 第 3738–3801 行）→ `POST /api/new`（`scripts/server.mjs` 第 2057–2079 行，`by: 'board'`，支持截图附件 REQ-20260909-009）→ 返回 201，前端 toast「✓ 已创建 XX（待接受）」并刷新列表。
- 人工接受现状（第二步）：卡片「✓」按钮（app.js 第 1898 行）、详情页「✓ 接受」（第 2984 行）、待接受档批量「接受所选」`acceptItems()`（第 2406–2450 行，逐条 `POST /api/item/:id/status {to:'accepted'}`，带页内异步确认对话框 BUG-20260907-009）；终端 `atb status <ID> accepted`。
- 接受的连带动作（「创建并接受」必须与分步接受等价）：`setStatus()` 进入 accepted 时写入 history，并按 REQ-20260908-020 把条目置「未完善」refine 索引（`scripts/lib/core.mjs` 第 782–788 行），使其进入批量完善候选（已接受未完善）。
- 人工专属纪律：accepted 属 `HUMAN_ONLY_TO`（core.mjs 第 26 行）；Agent 侧由 `scripts/state-guard.mjs` 拦截——Bash 规则(2)拦 `atb status <ID> accepted`、规则(3)拦 curl 调 `/api/(item|new)` 且带 accepted token（第 544–574 行）。

### 改动口径

1. **Web 新建弹窗增加「创建并接受」入口**：底部操作区在「取消 | 创建」之外提供「创建并接受」；仅类型为需求 / Bug 时可用，类型切到「讨论」时不展示（讨论无接受概念）。交互形态建议为独立按钮（本 README 与演示按此口径，最终以开发阶段 design.md 定稿为准，**待确认**）。
2. **`/api/new` 支持接受语义**：请求体增加可选的「创建并接受」标记（字段名**待确认**，如 `accept: true`）；缺省时行为与现状完全一致（落 submitted），旧客户端零影响。服务端按人工操作口径记 `by: 'board'`。
3. **CLI `atb new` 支持一步创建并接受**：增加开关（命名**待确认**，如 `--accept`），例如 `atb new req "标题" --accept`；帮助文案同步更新。仅限用户本人在终端执行。
4. **与分步接受完全等价**：创建并接受产出的条目，状态 accepted、README / design / test-cases 文档结构、附件落盘、history 可追溯（记录创建与接受两步来源与操作者；具体记录形态**待确认**）、refine 索引置「未完善」——均与「先创建再人工接受」的结果一致。创建与接受应作为一次原子操作：接受环节失败时不得留下状态与索引不一致的半成品（失败处理策略——整单拒绝 / 回滚删除 / 落 submitted 并明确报错——**待确认**，design.md 定稿）。
5. **人工专属纪律不可破**：Agent 不得借新入口越权置 accepted——`state-guard.mjs` 拦截口径同步扩展：Bash 规则覆盖 `atb new ... --accept`（或定稿后的开关名），规则(3)覆盖 curl 调 `/api/new` 携带接受标记的形态（当前只匹配 `accepted` 字面 token，覆盖不到新字段，必须同步，否则成为越权后门）。
6. **既有流程不回归**：原「创建（submitted）→ 人工接受」分步路径、待接受编辑（✎）/ 删除（🗑）/「接受所选」批量、截图上传与粘贴、讨论单创建均保持现状。

### 不改动

- 状态机流转方向与 `HUMAN_ONLY_TO` 定义（`submitted → accepted` 合法路径、人工专属集合不变；「创建并接受」只是把两步人工动作合一）。
- 讨论单（ask）链路：`/api/discussion` 创建、讨论两态（讨论中 / 已归档）不受影响。
- 批量完善 / 批量开发等下游模块逻辑（仅自然消费新增的已接受条目）。
- `status.json` 写入协议与既有字段结构（沿用 `writeStatus` 原子写）。

### 待确认

1. 弹窗内交互形态：独立「创建并接受」按钮（本 README 口径）还是「创建后立即接受」复选框。
2. CLI 开关与 `/api/new` 字段的最终命名。
3. 创建与接受的原子性失败策略（见「改动口径」第 4 条）。
4. history 的记录形态：两条（null→submitted、submitted→accepted）还是一条直达 accepted（建议保持可追溯两步语义）。

## 验收标准

- [ ] Web 新建弹窗：类型为需求 / Bug 时出现「创建并接受」入口；点击后条目直接以 accepted 出现在「已接受」档，toast 提示「已创建 XX（已接受）」类文案，无需再人工接受。
- [ ] 弹窗类型切到「讨论」时「创建并接受」入口不展示（或不可用），讨论单创建流程与现状一致；「创建」按钮仍走原 submitted 路径，行为与现状完全一致。
- [ ] 创建并接受的结果与分步接受等价：status 为 accepted；条目目录含 README / design（/test-cases）模板文件；history 可追溯创建与接受；refine 索引为「未完善」（出现在批量完善候选中）；带截图创建时附件照常落盘并在 README 生成引用行。
- [ ] CLI `atb new req|bug <标题> [开关]` 一步创建并接受成功，输出明确提示已接受；不带开关时输出与现状一致（submitted + 等待人工接受提示）。
- [ ] 守卫同步：Agent 会话内执行 `atb new ... --accept`（或定稿开关名）被 state-guard 拦截并给出人工专属提示；curl 调 `/api/new` 携带接受标记同样被拦截。
- [ ] 失败反馈：创建并接受请求失败时弹窗保留已填标题 / 描述 / 截图，toast 报错可重试，不产生重复条目或状态与 refine 索引不一致的半成品。
- [ ] 提交中防重复：请求在途时「创建」与「创建并接受」按钮禁用、文案变为「创建中…」，截图添加 / 移除入口同步禁用（对齐现有防竞态口径）。
- [ ] 旧服务兼容口径不回归：带截图创建前的服务能力预检（BUG-20260909-010）在创建并接受路径同样生效。
- [ ] `npm test`（`node scripts/tests/run-all.mjs`）全绿；新增行为有测试覆盖（/api/new 缺省行为不变、接受标记路径、守卫拦截新口径），既有创建 / 接受相关断言不回归。
- [ ] 界面验证：深浅色两种外观下弹窗布局（三按钮底栏 / 讨论类型收敛）无错位、无残留占位。

## 界面展示

- **布局**：改动集中在统一新建弹窗底部操作区——由「取消 | 创建」两按钮扩展为「取消 | 创建 | 创建并接受」；「创建并接受」为次级强调按钮，仅类型为需求 / Bug 时渲染，讨论类型下操作区回落为现状两按钮；表单其余部分（类型 / 标题 / 描述 / 截图区块）与现状一致。看板列表侧无新增布局，效果体现为新条目直接落在「已接受」档并带「未完善」徽标（与分步接受后一致）。
- **交互**：打开弹窗默认普通「创建」；类型切换联动「创建并接受」入口显隐（讨论隐藏）与截图区块显隐（沿用 `syncNewFormFields` 联动范式）；标题为空提交时提示「标题不能为空」；「创建并接受」与「创建」共用标题校验、防重复提交（在途禁用）、失败保留表单可重试口径。
- **状态反馈**：正常——普通创建 toast「已创建 XX（待接受）」、条目落待接受档；创建并接受 toast「已创建 XX（已接受）」、条目落已接受档且带「未完善」徽标，刷新后状态稳定。加载——提交按钮变「创建中…」并禁用，截图入口同步禁用。失败——toast 报错、表单内容与附件保留、可重试，不产生半成品条目。空——标题必填，空标题给行内 / toast 提示。深浅色适配沿用看板 `prefers-color-scheme` 双主题。
