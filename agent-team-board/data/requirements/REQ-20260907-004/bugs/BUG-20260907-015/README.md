# BUG-20260907-015 已接受页面无法全选

- 状态：in-progress（已上报，待人工确认）
- 归属需求：REQ-20260907-004
- 引入来源：REQ-20260907-004（经 `atb list` 核验；排查过程见下）
- 创建：2026-09-07T13:53:45.188Z

## 现象

需求列表的「选择可操作项」全选入口在看板没有待接受条目、只有已接受未认领条目时
处于禁用状态：典型如切到第四行筛选「已接受」档，或待接受条目全部被接受之后。
此时行内复选框仍可逐个勾选，但无法一键全选进入批量实施。

## 复现步骤

1. 打开看板需求模块，确保没有待接受条目（或全部接受完），且存在已接受未认领条目。
2. 切到第四行筛选「已接受」档，列表显示已接受条目，行内复选框可用。
3. 观察列表标题右侧「选择可操作项」按钮为禁用态，点击无反应，无法全选。

## 根因

`scripts/web/app.js` `syncAcceptance()` 中：

```js
const selectBtn = $('#selectOperable');
if (selectBtn) selectBtn.disabled = a.pending || eligible.size === 0;
```

`eligible` 仅由 `submittedItems()`（待接受条目）构成。REQ-20260907-004 选择工具条
已把该按钮语义扩展为「待接受 / 已接受未认领」两类（按钮 title 与点击逻辑均同时
选择 `submittedItems()` + `implCandidates()` 两类集合），但禁用条件未同步扩展，
仍沿用批量接受时代只统计待接受的写法，导致仅有可实施条目时按钮被误禁用。

排查过程：本项目目录非 git 仓库，无法 blame 历史；按代码注释考古——按钮 title
「选择可操作的条目（待接受 / 已接受未认领…）」与点击逻辑均标注 REQ-20260907-004
（选择工具条合并两类计数），而 disabled 判断无对应扩展注释，为合并入口改造时
遗漏的同步点。

## 期望行为

「选择可操作项」按钮在待接受与已接受未认领两类候选**任一非空**时可用（接受中
`pending` 仍禁用），两类都为空才禁用；点击后全选两类候选，行为与按钮 title 一致。

## 修复

`syncAcceptance()` 禁用条件改为两类候选都为空才禁用：
`selectBtn.disabled = a.pending || (eligible.size === 0 && implCandidates().length === 0)`。
回归用例补在 `scripts/tests/impl-entry-ui.test.mjs`（E3 扩展 S1/S2，先跑红复现
再修复跑绿）与 REQ-20260907-004 `test-cases.md` 缺陷回归段（S1–S3；S3 既有边界
由 accept-ui A1/A5 与 E3 原有断言保持）。全量 `npm test` 70 个测试文件通过。
