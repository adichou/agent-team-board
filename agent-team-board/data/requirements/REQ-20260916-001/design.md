# 设计 — REQ-20260916-001

## 事实来源与边界

现有批次协议区分 blocked 回执、条目状态与人工 hold 决策；参照 ../../batch-execution.md，并在实施前核对实际代码。概括层统一聚合执行阻塞与 hold，使用项目真实路径、batchId、runId、itemId、阻塞轮次关联，不以批次 ended 或进程退出推断阻塞已解决。历史只有 blocked/blocker 的记录也必须呈现，不强制先有 hold；缺少结构化问题时提示人工整理问题，保留原 blocker。

## 读模型与界面

概括返回按条目去重的未解决阻塞数、未答决策条目数及展开列表引用；列表按需读取原始 blocker 和当前决策版本。原阻塞回执不可改写为成功。已确认待复工、依赖未满足和提交失败分别标记，不压缩成统一“已结束”。blocker 路径在服务端解析、规范化并验证归属当前项目运行目录，拒绝路径穿越与符号链接越界；以转义文本渲染不执行内容。

侧栏遵循 README 布局。人工答案保存为草稿，确认前生成 README/design 精确差异及完整目标文件清单；采用现有 hold/decisions 审计入口可复用的部分，保持人工权限守卫，不新增 Agent 可绕过的确认通道。原生人工复工入口仍为独立动作，本需求不新增自动恢复授权。

## 文档更新与提交事务

1. 为每轮确认生成幂等事务标识，记录条目、问题版本、文档基线哈希、答案、人工审阅的差异和提交文件白名单。执行账本通过受控服务写入，不能手改条目 status.json。
2. 人工确认请求校验全部问题已答及上下文版本；使用项目内文档事务互斥，再次核对文件未发生并发修改。冲突返回差异并要求重新审阅，不覆盖新内容。
3. 仅修改已审阅 README.md/design.md 和必要且已预览的 decisions.md。以可恢复事务保存各文件；部分写入失败留存阶段，不宣称完成。未修改部分不产生虚假差异，不把历史无关文字替换成模板。
4. 提交基于隔离 Git 索引构造，不能 git add . 或直接提交用户当前索引。提交树相对父提交仅含此次已批准文档差异，逐文件/逐差异校验白名单；同文件已有改动也不自动夹带。无法可靠隔离时显示提交冲突并保留现场，等待人工处理。
5. 提交前后校验 HEAD 与工作区/用户索引并发变化，确保原有未暂存与已暂存改动均保留；不得 reset、clean、stash 或覆盖用户文件来完成提交。HEAD 并发更新需重算并重核验，禁止强制改写。Git hooks/身份缺失/仓库不可用等失败显示原因为可操作提示，不绕过保护。
6. 提交信息标记条目及事务标识，记录真实 commit OID、父提交与文件差异摘要。服务在 commit 已成功但结果尚未落盘时重启，先按事务核实提交，再补记录，不能重复 commit。文档成功/Git 失败的重试只处理未完成阶段，答案与文档不可重复追加。
7. 只有文档保存与提交证据齐备才显示已提交。无差异的重复确认关联已有提交；没有可核实提交则显示“无新差异，待核对”，不能虚构成功提交号。不 push。

## 状态与权限

事务状态、运行阻塞状态与条目业务状态分离。确认边界不调用 accept/done/claim/resume。提交失败保留待处理提示和阻塞计数；提交成功后有条件的信息阻塞转为决策已确认待人工复工，其他依赖仍需自身证据解除。服务重启恢复事务、项目切换丢弃旧请求响应；人工复工按当前批次/hold机制核对锁、owner 与已执行记录。

## 实施与验证范围

只在实施阶段选择具体接口、持久化路径与已有 hold 服务扩展点，不把本文当作现成 API。优先复用项目现有 Git/文件与 UI 工具；若引入新依赖，按项目开源许可规则核验并补 licenses.md。本次为文档设计，尚未实施和测试。
