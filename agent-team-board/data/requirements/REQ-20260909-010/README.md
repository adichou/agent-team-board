# REQ-20260909-010 支持需求完善后自动转入计划，提供配置，默认是手动

- 状态：accepted（已接受；实际状态以 status.json 为准）
- 创建：2026-09-09T04:53:44.529Z

## 描述

批量完善（refine）面向已接受（accepted）条目批量补文档，条目全程保持 accepted：done 回执核验通过后只把完善账本置「已完善」（refined），条目状态仍是 accepted。而批量开发的候选口径是「已计划（planned）且未认领」——每条完善完成的单都要人工再做一次「移入计划」（accepted → planned：详情页按钮或已接受档批量勾选），才能进入下一轮批量开发，形成重复的人工步骤。

本需求要求：提供「完善完成后自动转入计划」配置项，**默认关闭（= 手动，保持现状）**。开启后，完善回执 done 核验通过（summary 达标、文档相对冻结基线确有变更、条目仍为 accepted）时，由回执处理逻辑自动把条目 accepted → planned，免去人工移入计划一步；条目随即落入批量开发候选（planned 未认领），形成「接受 → 完善 → 自动计划 → 批量开发」的连贯流转。

### 现状依据（基于当前代码）

- 完善回执（zcode 路径）：`scripts/lib/refine-store.mjs` 的 `finishRefineRun`——done 分支核验（summary 必填、条目仍 accepted、`docsUnchangedSince` 基线比对）通过后落 done 终态并 `setRefineItemState(…, 'refined')`，**不触碰条目 status.json**；CLI 入口 `atb refine done`（`scripts/atb.mjs`），回执原样返回主会话。
- 完善回执（codex 路径）：看板服务侧结算（`scripts/server.mjs` 完善运行 `settle` 的 done 分支），同样只落完善账本。注意存量口径差异：该处仍按 `st.status === 'submitted'` 核验（面向已接受单的 REQ-20260908-020 之前的旧口径），与 `finishRefineRun` 的 accepted 核验不一致——接入自动流转时是否一并对齐属开发阶段决策（见「待确认」）。
- 状态机与人工专属：`scripts/lib/core.mjs` 的 `TRANSITIONS`（`accepted → planned` 为合法边）与 `HUMAN_ONLY_TO`（accepted / planned / done 仅限人工）；Agent 侧由 `scripts/state-guard.mjs` 在 PreToolUse 拦截 `atb status <ID> accepted|planned|done` 命令与 status.json 直写。
- 人工移入计划现状：看板详情页「移入计划」（免二次确认 + 撤销）、已接受档批量「移入计划」（REQ-20260908-018）；反向操作「移出计划」（planned → accepted）保留。
- 批量开发候选：`scripts/lib/batch.mjs` 的 `candidateItems` = planned 且未认领——自动转入计划后条目立即可被下一批量开发批次吸收（实时吸收口径，`absorbNewPlannedItems`）。
- 任务设置存储：`scripts/lib/task-settings.mjs` 读写 `<dataDir>/tasks/settings.json`（现含 `agents` + `models`），看板「设置 → 批量任务」区（`scripts/web/app.js` 的 `taskSettingsHtml`）编辑、`/api/tasks/settings`（GET/POST）读写——本需求新配置的自然落点（具体字段结构留 design.md）。
- 完善三态账本：`scripts/lib/refine-states.mjs`（未完善 / 完善中 / 已完善，只落 `refine/states.json`，不写条目 status.json）。

### 目标口径

1. **新增配置「完善完成后自动转入计划」，默认关闭**：关闭时行为与现状完全一致——refine done 后条目保持 accepted，需人工移入计划。
2. **触发点**：完善回执 done 核验通过处（zcode 路径 `finishRefineRun`；codex 路径 server 侧 settle 的 done 分支——两路径同口径）；`refine fail` / `refine release` / `abort` 出局（skipped）**不触发**流转。
3. **流转条件**：仅当条目当前仍为 accepted 才流转；人工已提前移入计划（planned）或状态已变化的不重复流转、不报错、不阻断回执。
4. **系统行为而非 Agent 命令**：自动流转由回执处理逻辑内部调用状态机完成，条目 history 记录流转事件并标注自动化来源（如关联 runId / 「完善后自动转入计划」备注，具体标注形态留 design.md）；**不改变 Agent 纪律**——子代理仍不得执行 `atb status <ID> planned`，state-guard 拦截规则不变（用户开启配置 = 授权系统在回执处理内代执行这一步，与「人工专属状态」铁律不冲突的口径需在 design.md 论证并落地）。
5. **回执可见**：done 回执与 CLI 输出体现流转结果——成功（如「已自动转入计划：<ID>」）或未转及原因；自动流转失败时**回执仍成功**（完善完成事实不丢失、完善账本仍记已完善），输出警示提示人工移入计划。
6. **生效时机**：保存设置后仅对后续 done 回执生效；进行中与已完成的完善运行不追溯、不补流转。
7. **人工操作不回退**：「移出计划」（planned → accepted）、详情页撤销等人工反向操作保持可用；自动置计划的条目与人工置计划的条目无差别（同样可被批量开发吸收、可移出、可被领取认领）。

### 待确认（开发阶段 design.md 须给出结论或降级口径）

- Bug 条目完善 done 后是否同样自动转入计划：完善流程候选含需求与 Bug（req 优先），流程名即「需求完善」；建议同口径一并生效，但本需求标题以需求为主，最终范围开发阶段确认。
- 配置的具体存储结构（settings.json 新增字段形态、是否挂在 refine 分区下）与是否提供 CLI 设置入口（现状任务设置仅看板设置页可改，CLI 侧 `atb refine done` 只读不写）。
- codex 服务侧 settle 与 zcode CLI 路径核验口径的存量差异（server 侧仍按 submitted 核验）是否随本需求一并修正——不修正则 codex 完善路径几乎必然核验失败，自动流转形同虚设；修正则属行为变更，需在 design.md 明确。
- 自动流转失败的兜底展示位置（CLI 输出行 / 回执 JSON 字段 / 看板任务面板记录标注）与 history 中自动化来源的标注格式。

## 界面布局

改动集中在两处：设置页新增开关、看板上流转结果的既有位置呈现（不新增页面/列）。

1. **设置 → 批量任务区**（`scripts/web/app.js` 的 `taskSettingsHtml`）：在「批量完善」配置块下方（批量开发块之前）新增一行独立开关：

```
┌ 批量任务 ────────────────────────────────────────────────┐
│ 说明文字（现状保留，末尾补一句流转口径说明）                 │ │
│ 批量完善：［执行 Agent / 模型来源 / 子代理模型 / 推理强度 /  │
│            是否隐藏 表格——现状不动］                        │
│ 完善流转：[ ] 完善完成后自动转入计划                         │
│           （开启后：完善回执 done 核验通过且条目仍为已接受时， │
│             自动移入计划（planned）；默认关闭=人工移入计划）   │
│ 批量开发：［表格——现状不动］                                │
│ ［保存批量任务设置］  已加载设置 / 有未保存的更改              │
└──────────────────────────────────────────────────────────┘
```

2. **看板流转呈现（复用既有位置，无新增列）**：
   - 状态看板：开启后完善完成的条目从「已接受」档出现在「已计划」档（六列分组视图现状不变）；
   - 条目详情：history 新增一条 accepted → planned 流转记录（标注自动来源）；
   - 任务模块「批量完善」面板执行记录：done 记录旁标注流转结果（如「已自动转入计划」），具体形态留 design.md。

3. **CLI 回执输出**：`atb refine done` 成功输出在回执 JSON 前增加一行流转结果提示（成功 / 未转及原因 / 警示），形态为建议、以 design.md 为准。

## 交互行为

1. **开关草稿**：切换「完善完成后自动转入计划」只改本地草稿，状态行即时提示「有未保存的更改」；未保存不生效（沿现状 tsDirty 口径）。
2. **保存**：点击「保存批量任务设置」随既有表单一并提交 `/api/tasks/settings`（新开关字段并入 patch，非法值整体拒绝不落半截配置，沿用 `saveTaskSettings` 口径）；保存期间按钮禁用防重复提交；成功 toast「已保存批量任务设置（流转开关仅对后续完善回执生效）」，失败 toast 错误且草稿不清空。
3. **完善回执联动（开启后）**：子代理执行 `atb refine done <RUN-ID> --summary …` 核验通过时，回执处理内部把条目 accepted → planned；CLI 输出与回执体现「已自动转入计划：<ID>」；条目随后可被批量开发批次吸收（进入候选队列最旧优先）。
4. **完善回执联动（默认关闭）**：输出与现状一致，条目保持 accepted；可附带一行提示「未开启自动转入计划：需人工移入计划」（是否加此提示留 design.md，不作为硬性要求）。
5. **条件与失败**：回执时条目已非 accepted（如人工已移入计划）→ 不流转不报错，回执成功并说明原因；自动流转异常 → 回执仍成功，输出警示提示人工处理，完善账本照记已完善。
6. **人工操作不回退**：已计划条目仍可「移出计划」退回已接受；详情页撤销、拖拽换列等既有交互不变。
7. **不触发的路径**：`refine fail`、`refine release`、批次终止（abort）、领取出局（skipped）以及完善中（refining）状态的条目均不发生流转。

## 状态反馈

- **正常**：开关回显已保存值（默认关闭）；开启后完成的条目在看板「已计划」档出现，详情 history 有自动流转记录；任务面板完善记录带流转标注。
- **加载**：进入设置视图沿用现有「正在加载任务设置」骨架与锁定编辑；读取失败显示「任务设置加载失败：<原因> + 重试按钮」，重试成功回显完整设置（沿 `renderSettingsView` 现状）。
- **保存中**：按钮禁用防重复提交；成功 / 失败 toast，失败保留草稿。
- **回执侧**：CLI 输出流转结果行；开启且流转成功 → 明确成功行；未开启 → 现状输出（或提示行）；流转未发生 / 失败 → 原因或警示行，回执本身不失败。
- **空 / 初始化**：项目从未保存过任务设置时开关显示关闭（手动缺省），其余设置按现有默认渲染；存量已保存设置加载后新开关字段缺失按关闭回退（兼容旧存储）。

## 验收标准

- [ ] 默认关闭（手动）：未改设置时完善 done 回执后条目保持 accepted、完善账本记已完善（现状零回归）；条目需人工移入计划才能进入批量开发候选。
- [ ] 开启生效：设置开启后，`atb refine done <RUN-ID> --summary …` 核验通过时条目自动 accepted → planned（status.json、看板档位、批量开发候选三处同步生效），无需人工移入计划。
- [ ] 条件流转：回执时条目已非 accepted（如人工已移入计划）→ 不重复流转、不报错，回执成功并输出原因说明。
- [ ] 失败不丢单：自动流转异常不导致回执失败或完善账本回退；输出警示提示人工移入计划。
- [ ] 仅 done 触发：`refine fail` / `refine release` / 批次终止出局 / 完善中状态的条目均不发生流转。
- [ ] 流转可追溯：条目 history 记录 accepted → planned 事件并标注自动化来源（如关联 runId / 备注文案，形态以 design.md 为准）。
- [ ] 回执可见：CLI 输出与回执（及看板任务面板完善记录）体现「已自动转入计划 / 未转入及原因」。
- [ ] 设置页：设置 → 批量任务区提供「完善完成后自动转入计划」开关，默认关闭；保存走 `/api/tasks/settings`，保存中防重复提交、成功 / 失败 toast、未保存草稿不生效；存量设置无新字段时按关闭回退。
- [ ] 生效时机：保存后仅对后续 done 回执生效；进行中与已完成的完善运行不追溯。
- [ ] Agent 纪律不变：Agent 侧执行 `atb status <ID> planned` 仍被 state-guard 拦截；本需求不放宽 HUMAN_ONLY_TO 语义，自动流转仅在回执处理内部由系统执行。
- [ ] 人工操作不回退：移出计划（planned → accepted）、详情页撤销等仍可用；自动置计划与人工置计划的条目在批量开发候选、认领、移出等行为上无差别。
- [ ] zcode CLI 路径与 codex 服务侧路径的触发口径一致；server 侧 settle 的存量核验差异（submitted vs accepted）在 design.md 有结论或对齐方案。
- [ ] Bug 条目完善后是否同样自动转入计划在 design.md 有明确结论（建议同口径，不默认臆断）。
- [ ] 开发阶段补充 design.md / test-cases.md 并通过相关测试（task settings、refine-*、状态流转、设置 UI）；当前完善阶段只交付本 README 与 ui-demo.html。
