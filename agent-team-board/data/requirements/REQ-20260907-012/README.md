# REQ-20260907-012 已接受的需求或 Bug 不要在列表界面或详细内容界面显示已接受便签，应呈现是否已进入批次

- 状态：submitted（待人工接受）
- 创建：2026-09-07T15:28:59.951Z

## 描述

「已接受」这一状态对人工的价值有限：条目一旦被接受，人工真正关心的是**它是否已经被安排进批量实施批次、排队等待派发**。现状是列表卡片和详情抽屉都只显示一个「已接受」状态便签，无法区分「已入批次排队/执行中」与「还没进任何批次」。

本需求把「已接受」便签替换为**批次进入状态**展示（ REQ-20260906-002 批量实施体系的入口可视化）：

### 界面布局与交互（涉及 UI，按 REQ-20260903-001 前置描述）

1. **列表界面（状态模块条目卡片）**
   - 现状：已接受条目卡片顶部状态 chip 固定显示「已接受」。
   - 改为：已接受条目不显示「已接受」chip，改为显示「已入批次」或「未入批次」chip（沿用状态 chip 样式）。
   - 悬停提示（title）说明依据：已入批次 → 显示批次号与批次状态（如 `已入批次 batch-20260908-010（执行中），等待派发实施`）；未入批次 → `未入批次：可在列表勾选进入批量实施，或用 /dev 认领`。
   - 其余状态（待接受/开发中/待测试/已完成）卡片不受影响。
2. **详细内容界面（详情抽屉）**
   - 「状态」字段：已接受条目不再显示「已接受」，改为「已入批次」/「未入批次」（已入批次悬停可见批次号与状态）。
   - 操作说明 notice：不再以「已接受。」开头；改为按批次进入状态给出指引——已入批次：等待按批次派发实施（附批次号）；未入批次：提示在 ZCode 会话运行 `/dev <单号>` / `/dev next` 认领，或在列表勾选进入批量实施。
   - 其余状态详情不受影响。
3. **判定口径（状态反馈）**
   - 「已入批次」= 条目编号出现在任一**未结束批次**（prepared/running/paused/needs_attention）的 candidates 中，取最早创建的那个批次；批次结束（finished）后其候选条目不再算「已入批次」（需要重新入批或已被认领/完成）。
   - 数据来源：服务端在 `/api/board` 与 `/api/item/:id` 响应中为 accepted 条目附加 `batchEntry: { batchId, status } | null`；前端缺省字段按「未入批次」兜底。
   - 列表轮询签名包含批次进入状态，条目入批/出批后 2 秒内自动刷新展示。
4. **不改动的部分**
   - 状态机、四档筛选条（「已接受」筛选档名称保留——它是列/档位名，不是条目便签）。
   - 批量实施面板（任务模块）内的批次/队列展示。

## 验收标准

- [x] 已接受条目卡片不出现「已接受」chip；显示「已入批次」（在未结束批次 candidates 中）或「未入批次」。
- [x] 详情抽屉「状态」字段同样不显示「已接受」，显示批次进入状态；操作说明 notice 不再以「已接受。」开头，并按入批与否给出对应指引。
- [x] 已入批次悬停可见批次号与批次状态；未入批次悬停有操作指引。
- [x] 非已接受条目（待接受/开发中/待测试/已完成）在列表与详情的展示不受影响。
- [x] `/api/board` 与 `/api/item/:id` 对 accepted 条目返回 `batchEntry`（未入批为 null，非 accepted 不附加）；批次 finished 后不再算已入批次。
- [x] 列表内容签名包含批次进入状态，入批/出批后无需手动刷新即可更新。
