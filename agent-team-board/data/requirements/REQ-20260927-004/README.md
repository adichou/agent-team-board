# REQ-20260927-004 合并视图需区分对合入 main 无影响的提交（明确告知或不展示）

- 状态：submitted（待人工接受）
- 创建：2026-09-27T10:53:55.622Z

## 描述

发布流程「挑选合并」步执行前展示隔离分析：对每个所选提交列出「main 可达之外、又不属于所选集合」的未选祖先提交（`analyzePublishIsolation`，scripts/lib/build-git.mjs；明细渲染在 scripts/web/build.js 渲染合并步）。该明细把全部未选祖先**一视同仁**列出，用户无法分辨哪些真正影响合并。

其中一类提交对挑选合并到 main **没有影响**：发布文档提交（如 `f1d15c79 docs: 发布文档 BLD-20260923-001`，仅触及根第一层发布文档）。它的合入由本版本「文档与翻译 → 文档合并」步单独处理（cherry-pick 重放进 main），不随挑选合并走；且发布文档按版本重写，旧版本的文档提交对新版本而言是纯噪音。实际案例：BLD-20260927-001 的未选祖先明细中出现该提交，用户询问「是必须要合入 main 的么」——答案是不需要（新基线版本的文档步会重新提交发布文档并经文档合并步合入），但界面上得不到任何提示。

要求：对合并到 main 没有影响的提交，在合并相关提交列表中**明确告知**（标注类别与处理去向）或**不展示**。

**落定口径（明确告知 + 默认收起，两者兼得）**：按提交变更文件静态判定——变更文件全部落在根第一层发布文档集合内（README / CHANGELOG / FEATURES / AGENTS / DESIGN 及语言变体、版本 `v.customDocs` 清单内自定义文档）的未选祖先提交，判定为「发布文档提交」：

- 未选祖先明细拆分为两段：**源码祖先明细**（现有折叠列表，行为不变）与**发布文档提交折叠行**（默认收起，一行汇总「另有 M 个发布文档提交 · 随『文档合并』步处理，不随挑选合并」，可展开查看 hash + 主题）；
- 汇总行分类计数：「发现 X 个未选祖先提交」只统计源码祖先（不含 M），发布文档提交数量单独说明，不再混为一个数字；
- 判定为只读展示，不改变合并执行语义。

## 验收标准

- [ ] 未选祖先提交按变更文件静态分类：变更文件全部落在根第一层发布文档集合内 → 「发布文档提交」；混合变更（根文档 + 其他文件）不分类，按现状展示。
- [ ] 隔离分析明细区拆分：源码祖先折叠列表行为不变；新增发布文档提交折叠行（默认收起），展开可见逐条 短 hash + 提交主题。
- [ ] 折叠行汇总文案明确去向：「随『文档合并』步处理，不随挑选合并」；徽标以颜色 + 文字双重区分（不只靠颜色）。
- [ ] 汇总行「发现 X 个未选祖先提交」不含发布文档提交；M 单独计数说明；X = 0 且 M > 0 时呈现「所选提交无未选祖先」+ 发布文档折叠行，不再出现空的源码明细。
- [ ] 分类判定只读，不改变 cherry-pick 执行集合、拓扑排序、共享提交去重与冲突阻止行为。
- [ ] 未选祖先数量上限（现 50 条截断）对两段分别生效或合并生效，以实现为准并在文案中如实说明。
- [ ] 新增用例覆盖：仅根文档提交判定、混合祖先不分类、X/M 分类计数、全部为发布文档提交的折叠形态；先红后绿，`npm test` 全量通过。
- [ ] 新增文案中英同步（scripts/web/i18n.js），i18n 相关测试通过。

## 明确不做

- 不改变挑选合并的执行范围与冲突语义，不自动把发布文档提交纳入或移出合并集合；
- 纯看板数据提交（`doc: 创建条目 …` 等仅触及 `agent-team-board/data/` 的提交）是否同样分类，本条不做，留后续观察；
- 不改动「文档与翻译 / 文档合并」步自身的行为与门禁。
