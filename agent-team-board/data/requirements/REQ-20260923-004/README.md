# REQ-20260923-004 删除需求需要同步提交

- 状态：submitted（待人工接受）
- 创建：2026-09-23T12:49:51.811Z

## 描述

### 背景与动机

`atb delete <ID>`（REQ-20260908-003，CLI 入口 `scripts/atb.mjs`）与网页端 `DELETE /api/item/<ID>`（`scripts/server.mjs`）删除待接受（submitted）条目时，`core.deleteItem`（`scripts/lib/core.mjs`）只做两件事：`fs.rmSync` 物理移除条目目录（`agent-team-board/data/{requirements,bugs}/<ID>/`，工程单据属用户数据、随代码进版本控制）+ 删除 runtime 状态文件（runtime/ 不进 git）。**全程不产生任何 git 提交**。

`core.mjs` 的删除注释声称「删除后无处留痕，故无 history 记录；追溯依赖 git 历史（data/ 随代码进版本控制）」，但现状与该口径不符——删除差异（porcelain ` D` 路径）只是留在工作区：

1. **无人收拾**：后续开发单的收口自动提交（`scripts/lib/git-flow.mjs` `autoCommitForRun`）按路径归属归因，被删条目目录的 owner 解析为被删单号、与在途开发单不同 → 划入 `excluded`，删除差异不会被任何单收口卷入，只能等人工在终端补提交；
2. **「追溯依赖 git 历史」名不副实**：人工忘记提交时，删除在 git 层面无痕，且脏差异长期滞留工作区、混入挂起确认面板的扫描视野（该面板每 2 秒全量扫描脏路径）；
3. **多机不一致**：`data/` 进版本控制，删除未提交时 git HEAD 中该条目目录仍在——换机器 clone 后按 data/ 目录扫描（`atb rebuild`，REQ-20260918-003）会把本机已删条目「复活」，两边看板状态分叉。

本需求：删除（待接受）条目时由 atb **同步产生一次 git 提交**，把该删除改动立即入库——「删除即留痕」，不再依赖人工事后补提交。

### 需求要点

1. **CLI 同步提交**：`atb delete <ID>` 删除成功后，对被删条目目录路径产生一次 git 提交——在当前检出分支上**只 commit、不 push、不切分支**；提交消息**包含被删条目单号**（与既有「消息含单号 ↔ 条目关联」口径一致，git 历史可检索）。消息前缀（如 doc/chore）与实现复用路径待设计阶段定。
2. **网页端同口径**：Status Board 卡片 / 详情页的删除入口（danger 确认 → `DELETE /api/item/<ID>`）同步提交行为与 CLI 完全一致；删除后的反馈（toast）体现提交结果（如提交短号）。
3. **提交范围严格限定**：只提交被删条目目录路径的删除差异（对齐 `autoCommitForRun` 既有的 `git add -A -- <路径>` + `git commit --only` 口径），**绝不卷入工作区其他脏改动**；runtime/ 状态文件本就被根 .gitignore 忽略，不产生 git 差异。
4. **提交失败不回滚删除**：目录已移除的事实保持不变，差异保留在工作区，命令反馈如实给出失败原因（如 index.lock 冲突）与人工补提交指引，不得静默吞错。
5. **非 git 仓库**：跳过同步提交，删除照常成功，反馈注明「非 git 仓库，无法同步提交」（对齐自动提交对非 git 项目的 skipped 口径）。
6. **既有删除约束全部不变**：仅 submitted 可删（已进入流程的走驳回 / 新单）；需求仍有下属 Bug 时拒绝删除；单号计数器不回退。
7. **Bug 条目同口径**：待接受 Bug（`data/bugs/<ID>/`）走同一条 `core.deleteItem` 路径，删除同步提交口径与需求条目一致。
8. **不涉及 `atb batch delete`**：批次账本在 runtime 域、不进 git，删除批次无需提交。

## 界面展示（网页端删除反馈）

本需求改动网页端删除入口的反馈链路（删除结果需体现 git 提交状态），界面说明如下，可交互演示见 [ui-demo.html](./ui-demo.html)：

- **界面布局**：Status Board「待接受」区的条目卡片（含标题、删除按钮）+ danger 二次确认弹层 + 右上角 toast 反馈；演示页额外并排展示「git 提交历史」与「工作区差异」两个面板，用于对照删除入库前后状态。
- **交互行为**：点卡片删除按钮 → 弹出 danger 确认（文案说明删除不可恢复、将同步产生一条 git 提交）→ 确认后按钮进入删除中加载态 → 请求完成后卡片移除、toast 反馈提交结果；取消则无任何变更。
- **状态反馈**：
  - 正常：删除成功，toast 显示「已删除 + 提交短号」，git 历史面板新增一条含单号的删除提交，工作区面板不再残留 ` D` 删除差异；
  - 提交失败：删除已生效，toast 转警示样式，给出失败原因与「人工在终端补提交」指引，工作区面板保留删除差异；
  - 非 git 仓库：删除成功，toast 说明已跳过同步提交；
  - 加载：删除请求期间按钮禁用 + 加载态，防重复点击；
  - 空：待接受列表清空后展示空状态占位。
  - 演示页另提供「旧行为（不提交）」对照开关，可对比现状「删除后差异滞留工作区、git 历史无痕」的缺陷表现。

### 边界与待确认

- **删除提交是否写入 commits 账本**（`committedItemIndex`，影响「已提交」徽标与 `atb commit log`）：被删条目已不在看板，倾向只留 git 历史、不写账本，**待设计阶段定**。
- **提交失败后的补救入口**：仅终端提示人工补提交，还是接入挂起确认面板形成闭环，**待确认**（演示按「终端提示 + 指引」口径呈现）。
- **网页端反馈形态**：toast 文案与提交号展示形态见界面展示演示，最终文案**以实现评审为准**。
- 同步提交由 atb 进程内部执行 git（不经 Agent Bash 工具、不受 state-guard 拦截，对齐 REQ-20260911-009 的授权口径）为**建议实现口径**，待设计阶段确认。

## 验收标准

- [ ] CLI 删除入库：git 仓库中删除一个待接受条目 → 命令成功，`git log` 新增一条消息含被删单号的提交，`git show --stat` 仅含该条目目录路径；工作区不再残留该条目的删除差异（porcelain 无该路径）。
- [ ] 网页端同口径：Status Board 删除（danger 确认后）→ 同样产生含单号的删除提交，toast 反馈体现提交结果；CLI 与网页端两条通道行为一致。
- [ ] 不卷入无关改动：删除前工作区预置其他脏文件（含其他条目目录路径）→ 删除提交的 `--stat` 不含任何无关路径，预置差异原样保留工作区。
- [ ] 提交失败不回滚：构造提交失败场景（如预置 index.lock）→ 条目目录仍被成功移除，反馈含失败原因与人工补提交指引，不静默吞错；之后人工补提交该删除差异可正常入库。
- [ ] 非 git 仓库：删除成功、不报错，反馈注明跳过同步提交。
- [ ] 只 commit 不 push：全程无 push、无分支切换、不触碰远端。
- [ ] 既有约束回归（测试覆盖）：非 submitted 状态拒绝删除；有下属 Bug 的需求拒绝删除；单号计数器不回退；待接受 Bug 条目删除同样同步提交。
