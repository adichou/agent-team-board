# 设计 — REQ-20260830-004 缺陷修复方案必须标注引入来源（哪个需求/Bug 引入）

> 由 Agent 在 /dev 开发前补充，人可随时批注。

## 背景

看板上已出现真实的因果链场景：BUG-20260830-001（顶栏按钮遮挡路径）由 REQ-20260830-002（File Board 引入视图切换按钮）引入，其 README 已有「关联」节记录来源。但该写法只是个案，/bug 与 /dev 流程没有强制要求，后续缺陷可能缺失归因，人工复核无法快速定位影响面。

## 方案

**纯流程/文档规范，不改任何运行时代码**（验收明确排除运行时改动；Agent 可直接编辑条目 markdown 是既有铁律 4，字段由流程写入而非工具生成）：

1. **统一「关联」节标准**（沿用 BUG-20260830-001 样例并标准化）：Bug README 末尾增加
   `## 关联` 节，其中引入来源一行固定为
   `- 引入来源：<REQ-YYYYMMDD-NNN | BUG-YYYYMMDD-NNN>（<一句话说明引入了什么>）`
   或 `- 引入来源：未定位（排查过程：<查了哪些条目/文件/变更>）`。可另附
   `- 相关：<其他有关联的条目>（<关系>）` 行。
2. **/bug 流程（commands/bug.md）**：登记**不要求**引入来源（2026-08-30 人工修订：登记时缺陷尚未定位）；
   文中仅保留指引——来源在修复阶段（/dev）补写。
3. **/dev 流程（commands/dev.md）**：修复 Bug 时归因**必填**——根因分析（design.md 或 README）与
   test-report 都必须写明引入来源；来源 ID 用 `atb list/show` 核验真实存在（格式 REQ-/BUG-YYYYMMDD-NNN）；
   写入 README 末尾「关联」节（样式同 BUG-20260830-001）；已有来源直接引用，缺失则排查补充；
   未定位须附排查过程，禁止猜测编造。
4. **SKILL.md 同步**：数据规范节说明 Bug README 含「关联（引入来源）」节；TDD 流程第 4 步加入 Bug 归因要求；与命令文件口径一致。
5. **验收方式**：新增静态契约测试 `scripts/tests/traceability.test.mjs`（node:assert 对三份文档与样例 README 的断言），先红后绿；三组既有测试全绿回归证明运行时未被触碰。

## 影响面

`commands/bug.md`、`commands/dev.md`、`skills/agent-team-board/SKILL.md`、新增测试文件；不改 `scripts/` 下任何 .mjs 与前端文件。

## 风险与边界

- 规范靠 Agent 遵守（钩子不拦截文档内容），「禁止编造」是行为约束；契约测试只能验证规范文本存在，无法验证每次执行——由人工复核兜底。
- 历史 Bug（BUG-20260830-001 已含来源）不回溯改写；新规范只约束此后流程。
- 引入来源的「真实性」核验限于看板内 ID 存在性；是否确为因果由人工判断。
