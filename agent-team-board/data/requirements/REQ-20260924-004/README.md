# REQ-20260924-004 整体审核界面的 AI 校对逐项增加修改按钮。

## 描述

### 背景与现状（代码事实）

发布流程第三步「文档编写」阶段三「整体审查完结」核对对话框（`scripts/web/build.js` 的 `renderFinalizeModal`；REQ-20260921-012 引入、REQ-20260924-001 补三类自动检查、REQ-20260924-003 精简为 3 条检查项）中，第 ③ 条「默认语言错别字与行文规范（AI 校对自动上报）」由 docscheck 账本驱动，现状：

- 「AI 校对」按钮复制提示词派发校对子代理，**只读核查不改文档**（提示词明示「发现问题只回执，不代改」，`scripts/lib/publish-flow.mjs` 的 `buildDocProofreadPrompt`）；子代理经 `atb docscheck file <runId> --file <文件名> --state fail --issues "…"` 逐文件回执——issues 是**每个文件一整段自由文本**（≤2000 字，提示词要求「逐条给出行号或原文片段与修改建议」，见 `scripts/lib/docs-check-store.mjs` 的 `markCheckFile`）。
- 前端展示（`renderFinalizeModal` ③ 项）：run 收尾（phase=done）且有 fail 文件时，明细**按文件**逐行列出——`<li><code>文件名</code> 问题清单整段文本</li>`；换行未做任何转换，多条问题在 HTML 里连排成一段；运行中只显示「校对进行中 x/N + 当前文件」，中断只显示原因。
- 问题修复没有任何直达入口：看到问题清单后，用户需自行「✕ 关闭」整体审查对话框 → 点「审查」→ 找到对应类型页签 → 找到默认语言栏 → 切「编辑」→ 在全文里人肉定位行号 → 改 → 保存 → 重新「通过审核」，再回到整体审查对话框重新「AI 校对」。环节割裂、定位靠人工翻找，整体审查核对效率低。

### 需求要点（原文）

「整体审核界面的 AI 校对逐项增加修改按钮」：

1. AI 校对结果的问题清单按**逐条问题**展示——每条独立一行（行号 / 原文片段与修改建议），不再整段连排；
2. **每条问题项带「修改」按钮**：点击直达该文档的编辑入口——打开审查对话框、自动切到该文件所属类型页签（README / CHANGELOG / FEATURES / AGENTS / 自定义文档）、默认语言文件栏进入编辑模式（现状 `openReview` 固定打开 README 页签且全栏预览态，需支持指定页签 / 文件 / 编辑态）；
3. 含可解析行号的问题条目，编辑器滚动定位到对应行附近并突出原文片段（选区或高亮）；解析不到行号时兜底为仅打开该文件编辑态，不定位不算缺陷；
4. 修改后链路沿用既有口径：编辑保存 → 文件回退「已总结待审核」→ 重新「通过审核」；AI 校对结果不自动失效或清除，重新「AI 校对」启动新一轮后按最新内容覆盖展示；
5. 只加修改入口，不改校对与完结口径：校对 Agent 仍只读不改；「修改」不改变 ①② 检查、`canFinalize` / `canCommit` 门禁与「确认完结」行为（REQ-20260924-001 口径：自动检查结果供人工决策、不设门禁）。

### 逐条拆分的实现口径（设计阶段定稿，本 README 只锁定行为目标）

issues 账本现状为整段文本，「逐条」需要一种拆分依据：**待确认**。候选：a. 提示词约束回执格式（一行一条、行号开头）+ 前端按行渲染，账本结构不变、兼容既有 run；b. 账本 issues 结构化为条目数组（涉及 `atb docscheck` CLI、`docs-check-store` 与既有 run 数据的兼容）。无论哪种，行为目标一致：界面每条问题独立成行、各带「修改」按钮；拆分失败时整段作为一条展示、按钮按文件级跳转，**不得丢失或截断回执内容**。

### 涉及文件（现状）

- `scripts/web/build.js`：`renderFinalizeModal`（③ 项明细逐条渲染 + 「修改」按钮）、`openReview` / `switchReviewTab` / `loadReviewPair`（固定 README 页签 + 全栏预览态，需支持指定页签 / 文件 / 编辑态与行定位）、`startProofread`（校对启动）；
- `scripts/lib/docs-check-store.mjs`：issues 形态（整段文本，`markCheckFile` / `checkRunView`）；
- `scripts/lib/publish-flow.mjs`：`buildDocProofreadPrompt`（回执格式约束，若选口径 a）；
- `scripts/web/i18n.js`：新增文案中英同步；
- `scripts/server.mjs`：预计纯前端改动可覆盖；若需接口配合以 design.md 定稿为准。

## 验收标准

### 逐项展示与修改按钮

- [ ] AI 校对 run 收尾（phase=done）且存在 fail 文件时，③ 项明细按逐条问题展示：每条问题独立一行，含行号 / 原文片段与修改建议原文（回执内容不丢失、不截断），行尾带「修改」按钮；同文件多条问题按回执顺序排列，归属文件可辨。
- [ ] 拆分依据按设计定稿口径实现；无法拆分的整段 issues 不得丢内容——整段作为一条展示，按钮按文件级跳转。
- [ ] 「修改」按钮只在逐条问题行出现：校对未运行（提示语态）、校对进行中（进度 + 当前文件）、中断（原因态）、该文件 pass 时均不出现。

### 点击「修改」的跳转

- [ ] 点击某条问题的「修改」：打开审查对话框，自动切到该文件所属类型页签（含自定义文档页签），目标默认语言文件栏为编辑模式且内容已加载；其余栏不受影响（沿用各自编辑 / 预览态与内容）。
- [ ] 该条问题含可解析行号时，编辑器滚动定位到对应行附近并突出该条原文片段（选区或高亮）；解析不到行号时打开编辑态不定位（不算缺陷）。
- [ ] 弹层处理按 design.md 定稿口径实现（先关闭整体审查对话框再打开，或两层叠放；演示按「先关闭再打开」示意）。
- [ ] 跳转沿用 `loadReviewPair` 既有读取接口与缓存口径，不新增数据源；读取中 / 读取失败反馈与现状一致。

### 修改后的状态联动（沿用既有口径，不新造）

- [ ] 编辑保存后目标文件回退「已总结待审核」，需重新「通过审核」才恢复「已审核」；提示与现状一致。
- [ ] 因该文件回退，整体审查入口缺口重现（尚缺该文件审核）；重新通过审核后可再次打开整体审查对话框；若此前已确认完结，完结按既有内容求值失效回退（现状口径，本需求不改动）。
- [ ] AI 校对结果不因修改自动失效或清除；重新点击「AI 校对」启动新一轮后按最新磁盘内容核查并覆盖展示（既有 docscheck 口径）。
- [ ] 「修改」不改门禁：①② 检查结果、`canFinalize` / `canCommit`、「确认完结」与完结回退行为零改动。

### 回归与质量

- [ ] 整体审查对话框其余区域（3 条核对项布局、「运行自动检查」、底部提示与「取消 / 确认完结」）行为不变；审查对话框既有交互（页签切换草稿防丢、编辑 / 预览、保存、通过审核、N 栏同步滚动、Esc 关闭）不回归。
- [ ] 界面文案改动同步中英双语（`scripts/web/i18n.js`），i18n 相关测试通过。
- [ ] `npm test` 全量通过（含整体审查 / 审查对话框既有测试随交互扩展同步更新）。

## 交互行为

- **逐条渲染**：AI 校对回执的问题清单按行（或按设计定稿的结构化条目）拆分，每条一行展示「行号 + 原文片段 + 修改建议」，行尾「修改」按钮；按文件分组排列，pass 文件不出现问题行；拆分失败整段作一条、按钮按文件级跳转（不丢内容）。
- **点击「修改」**：打开审查对话框并切到该文件所属类型页签、目标默认语言栏进入编辑模式；含可解析行号时定位到对应行附近并突出原文片段（选区或高亮），否则仅打开编辑态；整体审查对话框按定稿口径让位（演示按先关闭再打开）。内容读取沿用既有接口，读取中 / 失败反馈同现状。
- **编辑与保存**：审查对话框内沿用现状——编辑 / 预览切换、保存（防丢字草稿同步）、「通过审核」；编辑已审核文件保存后回退「已总结待审核」并有提示。
- **重新校对**：修改保存后 AI 校对清单不自动清除；用户回到整体审查对话框重新点「AI 校对」启动新一轮（沿用复制提示词 + 轮询自动回执口径），按最新磁盘内容覆盖展示。
- **门禁不变**：「修改」只是编辑入口——①② 检查、`canFinalize` / `canCommit`、「确认完结」与完结回退行为零改动；整体审查入口缺口因文件回退重现属既有求值口径。
- **状态联动**：任一环节（校对状态、文件四态、门禁）变化即时反映到对话框明细、文件列表、门禁条与按钮可用性。

## 状态反馈

- **正常态**：③ 项按 run 状态呈现——未运行（提示点击「AI 校对」）/ 进行中（校对进行中 x/N + 当前文件）/ 全部通过（✔ 通过 4/4，无问题行）/ 部分不通过（✗ + 逐条问题行各带「修改」按钮）/ 中断（✗ + 原因）。
- **修改按钮反馈**：hover / focus 显示该条问题摘要（文件 + 行号）；点击后跳转有加载反馈（内容读取中），定位成功行附近高亮短暂停留。
- **修改后回退提示**：保存成功 toast 说明文件回退「已总结待审核」、需重新通过审核；整体审查入口缺口重现（门禁条列明缺哪个文件）。
- **空态**：校对未运行时 ③ 项显示提示语、无问题行、无「修改」按钮；全部 pass 时无问题行（通过计数即终态）。
- **失败态**：目标文件读取失败沿用现状（错误 toast + 重试口径）；校对中断显示原因（无「修改」按钮）。
- **完结口径**：完结标识、提交解锁与范围变化回退等终态反馈与现状一致，本需求不新增不改动。
