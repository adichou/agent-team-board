# REQ-20260921-015 版本计划详细内容页签的合并入 main 页面去掉隔离分析下方的一大堆红色字体的文字，并提供一键加入所有依赖提交的按钮

- 状态：submitted（待人工接受）
- 创建：2026-09-21T08:07:24.896Z

## 描述

### 背景与现状

入口路径：构建模块 →「版本计划」页签（`scripts/web/build.js` `TABS = [['versions','版本计划'],['branches','分支浏览']]`）→ 左侧版本卡片选中 → 右侧详情五步导航（`renderStepNav`，`STEP_LABEL`：版本计划 → 关联条目与提交 → 文档编写 → **合并入 main** → 正式发布）→ 第 4 步「合并入 main」页（`renderMergePane`，`scripts/web/build.js`）。

现状（代码事实）：

- 隔离分析数据来自 `scripts/lib/build-git.mjs` 的 `analyzePublishIsolation()`（经 `GET /api/build/publish-plan` 的 `mergeAnalysis` 字段下发）：
  - `perItem`：每条目 `main..commit` 范围内、又不属于本版本所选 commit 集合的祖先提交（下称「依赖提交」）；依赖提交若不被纳入，隔离合并（逐条 cherry-pick）执行时依赖未选变化会冲突阻止；
  - `notes`：未选祖先提交总数与说明；`blocked`：同一 commit 关联多个条目（混合提交）的阻止说明。
- 「合并入 main」页渲染（`renderMergePane`）现状：
  - 「隔离分析」节内直接铺大段文字：`blocked` 逐条以「；」拼接成一整段**红色**告警（`rel-form-err`，`--warn` 红色）；`notes` 灰色长句；每个有依赖的条目一行「N 个未选祖先提交（普通 merge 会一并带入 main；隔离合并不带入，依赖其内容将冲突阻止）」并把祖先提交逐条列出（每条目至多 5 条）——同一句长说明逐条目重复，条目与依赖一多就形成「一大堆文字」；
  - 「隔离分析」节下方另有**红色**长句：不在 dev 的分支告警、门禁锁定「暂不可合并：…」（暂无关联条目 / 文档尚未编写提交 / 文档有未提交修改 / 发布范围已变化需重新核对等，来自 `publishStepsState`）、合并失败原因。
- 发现依赖提交后，把依赖纳入发布范围的唯一途径是回到第 2 步「关联条目与提交」→「＋ 添加条目」侧拉面板，在候选列表里逐个查找、勾选、添加（`POST /api/build/version/items`，action=add），操作繁琐且容易漏；不纳入则合并执行时被冲突阻止。

问题：该页以大段红色告警长文「轰炸」用户（其中大部分是可处理的依赖提示而非错误），且化解依赖的手工路径冗长。

### 需求要点（原文）

1. **去掉隔离分析下方的一大堆红色字体的文字**——「合并入 main」页不再以大段红色告警长文呈现隔离分析与前置问题，信息收敛为简洁反馈；
2. **提供一键加入所有依赖提交的按钮**——隔离分析发现所选提交存在未选祖先（依赖）提交时，一键把全部依赖提交对应的条目与提交纳入本版本发布范围。

### 目标行为

- 「隔离分析」区域改为简洁呈现：有依赖时给出一行汇总（依赖提交数、涉及条目数）与「一键加入所有依赖提交」入口，明细可展开查看（形态设计阶段定）；无依赖时保持现状简洁空态（「所选提交无未选祖先：变更可独立进入主分支。」）。
- 点击「一键加入所有依赖提交」：把全部依赖提交解析到所属看板条目（依据 `scripts/lib/git-flow.mjs` `itemCommitStatusIndex`：commit 台账 + 提交主题中的条目编号归因），逐条纳入本版本 `items`（沿用现有 `addItems` 数据口径：一条目一 commit），成功后发布范围列表更新、隔离分析收敛为「无未选祖先」，并按既有机制触发发布范围变化（`markDocsScopeStale` → 文档需重新核对 / 提交，合并门禁随之反馈）。
- 一键加入沿用既有条目增删锁与校验：merging 中禁用、已正式发布（推送完成）锁定；仅已完成（done）且未被其他版本占用的条目可纳入。
- 只做界面与操作路径收敛，**不弱化任何守卫**：混合提交（同一 commit 关联多条目）、不在 dev、文档门禁等真正阻止场景仍由服务端合并前置（`/api/build/version/merge` 内 `analyzePublishIsolation` / `assertOnDev` / 文档门禁）确定性阻止；移除红色长文后，阻止原因仍以简洁、可发现的方式反馈（沿 BUG-20260920-006「点击必反馈」原则，具体形态见设计待确认点）。

### 术语

- **依赖提交 / 未选祖先提交**：所选条目 commit 的祖先中、目标主分支（main）不可达且不属于本版本所选 commit 集合的提交；其内容若被所选改动依赖，隔离合并执行时将冲突阻止。
- **混合提交**：同一 commit 关联多个看板条目（提交主题含多个条目编号且被多条目关联），无法安全按条目拆分，合并前被阻止。
- **隔离合并**：把版本所选条目 commit 逐条 cherry-pick 重放入主分支（经临时工作树执行），不把未选祖先带入 main（`mergeIsolatedIntoMain`）。

### 涉及文件（现状）

- `scripts/web/build.js`：`renderMergePane`（合并入 main 页渲染，含隔离分析红字长文）、`mergeBlockReason` / `openMergeConfirm`（按钮禁用归因与点击反馈）、`doMerge`；
- `scripts/lib/build-git.mjs`：`analyzePublishIsolation`（隔离分析求值：perItem / notes / blocked）；
- `scripts/lib/git-flow.mjs`：`itemCommitStatusIndex`（条目 ↔ commit 归因索引，commit 反查条目的数据基础）；
- `scripts/lib/build-store.mjs`：`addItems`（条目纳入与 done / 占用校验、`markDocsScopeStale` 范围过期联动）；
- `scripts/server.mjs`：`GET /api/build/publish-plan`（mergeAnalysis 下发）、`POST /api/build/version/items`（add / remove / commit）、`POST /api/build/version/merge`（合并前置守卫）；
- `scripts/web/i18n.js`：新增 / 调整文案须中英同步（BUG-20260912-001 口径）。

## 验收标准

### 红色长文移除（需求 1）

- [ ] 「合并入 main」页不再渲染大段红色告警长文：现状「隔离分析」节内 `blocked` 红色拼接长段、逐条目重复的未选祖先长句说明、以及节下方不在 dev / 门禁锁定 / 合并失败的红色长句，均不再以红色长文形式出现。
- [ ] 隔离分析信息收敛为简洁呈现：有依赖时一行汇总（依赖提交数、涉及条目数）＋「一键加入所有依赖提交」入口（明细可查看，形态待设计定稿）；无依赖时保持「所选提交无未选祖先：变更可独立进入主分支。」简洁空态。
- [ ] 移除红字不丢失反馈：真正阻止合并的场景（混合提交 / 不在 dev / 文档门禁 / 合并失败）仍有简洁、可发现的原因反馈（hover / 点击 / 单行状态，形态待设计定稿），服务端守卫行为不变（混合提交仍被阻止合并）。
- [ ] 深浅色两套主题下新样式正常（沿用 CSS 变量口径，不新引入配色）。

### 一键加入所有依赖提交（需求 2）

- [ ] 隔离分析发现所选提交存在未选祖先（依赖）提交时，页面提供「一键加入所有依赖提交」按钮；无依赖时不提供（形态按设计定稿）。
- [ ] 点击后把全部依赖提交对应的条目与提交一次性纳入本版本：发布范围列表即时更新（新增条目与 commit 可见），隔离分析收敛为「无未选祖先」，按钮随之消失 / 置完成态。
- [ ] 纳入口径与手工「添加条目」一致：仅已完成（done）且未被其他版本占用的条目；条目与 commit 归因准确（以 commit 台账 + 提交主题条目编号为准，不误归因）。
- [ ] 无法纳入的依赖（归属条目未 done / 已被占用 / 无法归属条目）有明确反馈与清单，不静默丢失（处理口径待设计定稿，但不得出现「点了按钮却什么都没发生」）。
- [ ] 一键加入沿用既有条目增删锁：版本 merging 中按钮禁用（合并中条目不可增删）、已正式发布（推送完成）锁定；执行中有防重复触发与进行中反馈。
- [ ] 加入成功后按既有机制标记发布范围变化：文档需重新核对 / 编写并重新提交的提示与合并门禁反馈随之出现（`scopeStale` 口径不变）。
- [ ] 加入失败（如并发占用冲突）给出错误反馈，可重试，版本数据保持一致。

### 兼容与回归

- [ ] 五步流程其余四步（版本计划 / 关联条目与提交 / 文档编写 / 正式发布）与既有合并 / 重试 / 增量合并行为不变；手工「添加条目」路径保留。
- [ ] 中英文界面文案同步（`scripts/web/i18n.js`），i18n 相关测试通过；`npm test` 全量通过。

## 交互行为

- **一键加入所有依赖提交**：隔离分析存在依赖提交时可用；点击后按钮进入执行中反馈（防重复触发），成功后依赖条目与提交全部出现在「发布范围」，隔离分析收敛为「无未选祖先」并给出成功反馈；随后按既有机制提示「发布范围已变化，文档需重新核对 / 提交」（合并门禁随之收紧，属预期联动）。
- **查看明细**：展开依赖提交清单（条目 + commit + 主题），仅供核对，不改变任何数据（形态待设计定稿）。
- **合并入 main 主按钮**：沿用 BUG-20260920-006 口径——不可合并时 aria-disabled + title 真实原因，点击 toast 反馈；一键加入后未重新提交文档前，点击提示文档门禁原因。
- **状态联动**：一键加入成功 / 失败、依赖集合变化（重新求值隔离分析）即时反映到发布范围列表、隔离分析汇总与按钮可用性。
- **既有路径不变**：第 2 步「关联条目与提交」的手工添加 / 移出 / 换 commit 行为保留。

## 状态反馈

- **正常态（有依赖）**：隔离分析一行汇总（依赖提交数、涉及条目数）＋一键加入按钮；页面无红色长文。
- **正常态（无依赖）**：「所选提交无未选祖先：变更可独立进入主分支。」，无一键加入按钮。
- **执行中**：一键加入执行中按钮态反馈（防重复触发）；隔离分析读取中显示「正在加载合并分析…」。
- **加入失败态**：错误反馈（原因 + 可重试），版本数据不变。
- **分析失败态**：「合并分析读取失败：…」＋重试按钮（现状口径保留）。
- **阻止态（简洁反馈，形态待设计定稿）**：混合提交 / 不在 dev / 文档门禁等原因以单行状态或按钮 title / toast 呈现，不再是大段红色长文；服务端守卫不弱化。
- **范围变化联动**：一键加入成功后提示文档需重新核对 / 提交（`scopeStale` 既有口径）。
