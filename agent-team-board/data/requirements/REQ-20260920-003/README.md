## 描述

将当前「构建」模块调整为「发布」，表达把已选需求和 Bug 发布到主分支、供用户公开使用的流程。开发过程仍可构建，不能把构建等同于正式发布。流程依次为：版本计划 → 关联条目与提交 → 文档编写 → 合并入 main → 正式发布（推送主分支、官网同步）。本单完善阶段只定义行为，不执行真实文档写作、Git 合并或发布。

### 版本计划与范围

沿用现有 BLD 计划编号和历史记录；界面同时显示完整计划编号及从后两段提取的版本号，例如 `BLD-20260920-001` 对应 `20260920-001`，保留前导零。版本列表、详情和后续步骤均可识别版本号，不另让用户重复输入一份不一致的版本号。保留现有计划名称、描述和关联条目能力；所选条目、每条提交 hash 与文档基准共同组成此次发布范围。无关联条目时提示先关联，不允许直接合并或发布。

### 文档编写与 AI 写作

关联完成后提供「AI 写作」：显示可复制的提示词，并明确由技术写作人员角色的子代理完成当前版本文档任务；主会话派发、接收短回执，子代理根据关联条目及实际代码核实变化，不简单罗列需求/Bug 原文。文字须简练、通俗易懂，说明用户能做什么、使用方式及变化。不得编造已实现能力。

人工已确认文档为 **README、CHANGELOG、FEATURES、AGENTS 四类**，全部提供预览和编辑；原文 `CHANGEME.log` 与「三个文档」均为笔误。中文文件分别为 README.md、CHANGELOG.md、FEATURES.md、AGENTS.md，英文分别为 README.en.md、CHANGELOG.en.md、FEATURES.en.md、AGENTS.en.md，共八个文件。

README 按语言链接对应 CHANGELOG 和 FEATURES，双语文档互链且链接可访问。AGENTS 内容应描述适用协作规则，避免将营销说明变成执行规则。文档与当前版本范围一致，不把未纳入发布的功能写成已发布。

在界面提供按文档、语言切换的预览和编辑、保存反馈，以及打开 TRAE CN / TRAE 编辑当前项目文档的入口。提示词须带项目路径、计划号、版本号、关联范围、文档清单和写作约束。第三方 IDE 未安装、启动失败或无法直达文件时明确提示并保留手动打开路径；打开 IDE 不等于已完成写作。

提供「提交文档到 Git」按钮：只提交本次确认的文档变化，展示提交范围；成功显示已提交及 hash，失败保留内容和重试入口。没有变化时不制造空提交。再次编辑后显示未提交；外部 IDE 修改后刷新状态。文档提交不得夹带业务源码或其他正在开发的工作区修改。

写作后新增/移除关联条目、更换 commit 或修改文档时，将对应文档标记「需重新编写」或「未提交」，说明变化来源，保留已写内容；不能继续拿旧的已提交标识放行合并。提示词、预览确认和提交应对应同一范围快照，提交期间的并发变化需重新核对。

### 合并入 main 与影响分析

前置条件为本次关联范围已核对、所需文档已完成且最新变化已提交。合并前列出计划条目提交、文档提交和目标分支；只包含此次版本范围及最新文档提交，不把其他未选需求/Bug 的变更混入。开始后禁用重复操作，显示处理中、成功/失败及原因；失败不显示已合并，重试不能重复引入已成功内容。

**已核实的现状和结论**：`scripts/lib/build-git.mjs` 的 `mergeCommitsIntoMain` 对每个选定 commit 执行 `git merge --no-ff`，当前非主分支时使用临时 worktree，不切换用户工作目录。普通 merge 会纳入该 commit 可达且目标尚未包含的祖先。因此在共享 dev 分支上，只选择 B 的提交也可能把先前未选 A 的变更带入；单纯把文档 commit 追加到此流程同样不能满足「只发布选中条目」。现有工作树隔离可以保护开发现场，却不能解决发布内容隔离，两者必须分别验收。

目标行为：对选定范围做提交/变更归属核对，给出实际将进入 main 的变化与依赖结论。独立的所选变化应可单独发布；如选中条目依赖未选变化、同一提交混有其他条目或发生冲突，明确阻止并列出原因，不能自动扩大范围。具体选取提交/补丁方式留开发设计决定，不在本轮承诺普通 merge 或 cherry-pick 一定无冲突。已有 `build-publish.mjs` 通过原始提交的祖先关系检验包含性；若开发采用重放提交，必须同步适配对应证据，否则已发布代码可能被误判缺失。

从 dev 发起时，完成或失败后工作目录仍在 dev，未提交文件、暂存区和其他分析/开发任务不受影响；使用隔离工作树时「回到 dev」表现为工作目录始终留在 dev。人工已确认：当前工作目录不在 dev（含 main、其他分支及 detached HEAD）时阻止发布，提示「请自行切换回 dev 后重试」，不自动切分支，也不允许通过隔离执行绕过该前置条件。合并和推送前均重新检查；用户仍可查看计划和文档。主分支仅有 master 的现有兼容行为需保持并显示实际目标。

### 正式发布与官网同步解耦

合并成功后，第一步由用户触发把本地 main（或已解析的 master）推送到所选远端。显示目标、待推送版本、进行中及结果；推送失败可重试，不能进入完成状态。不因本需求顺带推送 dev、强推或发布其他范围；若主分支已前进，重新核对目标范围。

推送成功后，第二步提供「官网 AI 写作」提示词。提示词在**官网仓库**执行，以技术写作人员角色读取本项目已发布版本的 CHANGELOG、FEATURES 中英文材料，根据官网自身架构更新相应内容，并在完成的提交消息中带完整发布计划号。包括项目路径/已发布基准、官网仓库路径、计划号和版本号，避免读取后来尚未发布的 dev 内容。此提示词不强制官网技术栈、目录或构建命令。

当前 `scripts/lib/build-publish.mjs` 的 `siteMaterials` 要求官网存在 `src/data/apps.js` 与 `content/<产品>/` 结构，本单目标解除这种架构绑定：ATB 提供固定材料与完成检测，官网端自行解释并同步，不由项目仓库执行官网结构改写。

正式发布页定时读取已配置官网仓库 main/master 提交记录，寻找含当前**完整计划号**的提交；匹配后展示提交 hash、分支、检测时间并标记正式发布完成。不能以只有版本号、相似编号、其他分支或其他计划提交代替。未命中显示等待官网同步，读取失败显示失败及重试，不能误报完成；离开页面/切换版本时停止旧版本轮询或隔离响应，返回可继续核对。人工已确认检测仅以官网仓库**本地主分支**为准，不自动 fetch；每 **60 秒**检测一次，并提供立即检测。界面始终提示「每分钟检查官网本地主分支；匹配仅表示本地提交已同步，不代表已推送或网站已部署」，显示官网路径、实际分支、上次检测时间及下一次检测时间。主分支解析沿用现有 main 优先、仅无 main 时回退 master 的兼容规则（代码事实见 build-git.mjs），界面显示实际分支；这属于沿用现状，不另宣称人工确认了分支优先级。扫描起点采用下文已确认的项目推送成功时间。

### 界面布局、交互行为与状态反馈

- 顶部导航为「发布」，左侧版本计划列表显示计划号、版本号、名称及阶段，右侧为所选计划详情和五步导航。
- 关联页展示条目及 hash；文档页上部是 AI 写作/IDE 操作，下部文档与语言选择、编辑和预览并列、提交状态及 Git 按钮。
- 合并页展示范围和隔离分析、禁用原因、合并结果；正式发布页按顺序呈现主分支推送、官网提示词、同步检测结果。
- 空态引导创建计划/关联条目；加载时保留上下文并阻止重复写操作；失败就地显示原因、保留编辑内容并支持重试；文档过期明确提示回到写作步骤。所有状态不能只靠颜色区分，窄屏布局纵向排列。

## 人工决策与时间窗口扫描

2026-09-20 看板已确认续跑：四类文档及 `.en.md` 命名已确认；官网以本地为准、每分钟检测且明确提示；非 dev 阻止发布并提示自行切回 dev。第二轮人工明确否决首次扫描全部历史，要求「就在项目仓库完成推送之后的时间开始扫描」。以下落实该时间边界，并补充避免阻塞的建议；这些是需求行为，不代表功能已实现。

- **起点**：当前版本首次成功推送主分支后记录并持久保存推送完成时间（带时区，界面可读显示）。失败的推送不建立起点；同一已成功发布基准的重试或页面重载不重置起点，避免漏掉重试前已完成的官网提交。已发布基准发生变化则先重新核对版本范围，不能沿用旧完成证据。
- **检测窗口建议**：只核对官网当前本地主分支中提交者时间不早于该起点的提交（含等于边界），并精确匹配完整计划号；采用提交者时间而非作者时间，降低变基保留旧作者日期造成的漏检。完整计划号须有标识边界，不能把 `BLD-20260920-0010` 当作 `BLD-20260920-001`。不进行首次全历史扫描，也不在失败后偷偷降级为全历史扫描。
- **避免阻塞建议**：检测在后台执行，按批次限制读取量和执行时间；每分钟最多一个检测任务，立即检测复用或等待正在执行的任务。尚未完成当前窗口的检查时显示「扫描中」，达到预算时显示「本轮检测未完成，可继续检测」，不能当作已确认未命中。具体批量、超时数值与实现方式由开发阶段按仓库实测确定，当前待确认；不是要求每次轮询从仓库根提交遍历到 HEAD。
- **后续检查建议**：保留已检查 HEAD，主分支正常前进时只检查新增提交且继续受上述时间边界约束；历史改写或目标分支变化时重新检查同一时间窗口，不能扩大为全部历史。命中证据仍须可达且对应当前计划；证据被移除后退回等待并解释原因。分页、取消和并发隔离应确保切换版本后旧结果不覆盖新版本。
- **明确边界**：时间条件依赖本机与提交时间正确，无法证明真实的官网操作先后；倒填日期或设备时钟偏差可能漏检。界面提供扫描起点、当前分支和未命中排查提示，供用户核对时间与完整计划号，不自动扩大时间范围。浅克隆/历史缺失、仓库不可访问和超时分别提示，不能冒充检查成功。
- **存量计划**：没有可信推送成功时间的历史记录显示「缺少推送完成时间，待核对」，不使用计划创建时间、页面打开时间或猜测值替代，不启动全历史兜底扫描。存量时间的人工补录方式留开发阶段设计。

建议理由：以用户指定的成功推送时间限定检测范围，配合后台分批和时间预算控制响应；HEAD 增量仅作优化，不改变时间窗口与完成判据。Git 历史的日期可能不单调，开发阶段须验证日期过滤不会误把窗口内后续提交漏掉，也不能以「未命中」掩盖未完成的扫描。

具体算法、迁移策略与开发用例留待开发阶段补充 design/test-cases；本轮不修改它们。
