# REQ-20260921-001 开发中的需求待人工确认的场景下，只有首次进入需求列表或重新刷新需求列表，人工确认补决策的入口才会出现，请修复

- 状态：submitted（待人工接受）
- 创建：2026-09-20T23:46:06.339Z

## 描述

### 背景与现状（已核实）

开发中的条目（in-progress）由 worker（Agent）走 hold 流程声明受阻后（`atb hold declare`），人工在看板需求模块补决策的唯一入口是**需求列表下方的「待人工确认」持久聚合区**（`#holdArea`，REQ-20260911-007 引入）——每条阻塞条目一张卡片，卡片的「补决策」按钮打开右侧「人工决策」侧拉面板逐项作答（`#holdPanel`）。列表行上另有 `⚠ 等人工决策` 旗标，悬停提示「到列表下方『待人工确认』区补决策并复工」。

数据链路（现状，均已核实无问题）：

- 主轮询 `poll()` 每 2 秒执行（scripts/web/app.js:8525），无论当前在哪个模块都会 `refreshHolds()` 拉取 `/api/holds` 快照并调用 `renderHolds()`；拉取失败保留上次数据并置 `state.holds.error`；
- `/api/board` 为处于 `holding` 状态的条目附加 `it.hold`（scripts/server.mjs:3369 起），列表行旗标由含 `it.hold` 的行签名驱动（scripts/web/app.js:2067）；
- 切换模块 `setView('status')` **不调用** `renderHolds()` / `renderBoard()`（scripts/web/app.js:1107 起），聚合区恢复显示完全依赖下一轮轮询里的 `renderHolds()`。

### 缺陷现象（复现路径）

前置：某开发中条目存在**活动 hold**（`/api/holds` 返回非空），且期间 hold 数据不变化（无新作答、无新声明）。

1. 页面加载后进入需求模块：聚合区正常出现（页面加载后 `area.dataset.rendered` 尚未置位，首次渲染必然执行）——即「首次进入需求列表时能看到」；
2. 切到任务 / 发布 / 设置任一模块再切回需求模块：**聚合区不再出现**（列表行 `⚠ 等人工决策` 旗标仍正常显示），行旗标悬停提示引导到列表下方补决策，但下方没有该区域，人工无入口；
3. 浏览器刷新（F5）后聚合区恢复——即「只有首次进入或重新刷新才会出现」。

同根因的伴随症状：停留在需求模块时若 `/api/holds` 瞬时失败（错误条出现）随后恢复且数据未变，错误条会残留、卡片列表不自动回来，须等数据变化或刷新。

### 根因（已定位）

`scripts/web/app.js` 的 `renderHolds()`（约 2952–3002 行）：

- **非需求视图 / 未初始化 / 加载失败分支**与**空清单分支**都会 `area.classList.add('hidden'); area.replaceChildren();`（隐藏并清空 DOM），但**不重置** `state.holds.sig` 与 `area.dataset.rendered`；
- 正常渲染分支开头的签名剪枝 `if (sig === state.holds.sig && area.dataset.rendered === '1') return;`（scripts/web/app.js:2979）在数据签名未变时**直接早退**，不检查区域当前是否实际处于「已隐藏且被清空」状态。

触发时序：用户在其他模块期间，每 2 秒的 `renderHolds()` 走隐藏分支反复清空 DOM（签名与 rendered 标记留存）；切回需求模块后，下一轮轮询的 `renderHolds()` 因签名未变早退，聚合区保持隐藏——直到 F5 重置页面状态或 hold 数据实际变化。

注意：`renderConfirmArea()`（任务页「待人工确认」挂起确认区，scripts/web/app.js:3382）存在**同型早退写法**，是否同样可复现属排查项（见验收标准），是否纳入本条修复范围**待确认**。

### 修复方向（方案细节留 design 阶段）

纯前端渲染层修复，不改 hold 状态机、CLI（`atb hold *`）与任何 API 契约：让「区域实际呈现状态」参与剪枝判定——例如隐藏 / 清空 / 错误条等**非卡片分支重置签名与已渲染标记**，或早退条件加 入「区域当前可见且有卡片内容」的前提。保留既有签名剪枝能力（数据与展开态未变时不重绘、不打断点击与填写），仅修正其失效条件。具体取哪种实现、以及是否在 `setView('status')` 时即时渲染（而非等 ≤2 秒轮询）**待确认**（design 阶段定；默认满足轮询周期内恢复即可）。

## 界面布局

本条为缺陷修复，**不改变既有布局**（REQ-20260919-002 已交付的聚合区卡片分层与决策面板布局全部保留）：

- 需求模块页：状态筛选条 → 需求列表（`#reqList`）→ 列表尾部「待人工确认」聚合区（`#holdArea`，空态整体隐藏不占版面）；
- 聚合区：区头「⚠ 待人工确认 + 计数徽标」+ 说明行；卡片四层（元信息行 / 标题 / 问题摘要（未答置前、已答折叠）/ 操作区（补决策、复工为主组，查看进展记录、确认完成为次组））+ 可展开进展记录；
- 「人工决策」侧拉面板：头部（标题 + 关闭）→ 声明 meta → 逐问题表单组 → 底部消息行 + 关闭 / 保存决策。

本条修复后唯一布局层变化是**可见性正确性**：切回需求模块时上述聚合区按数据状态恢复显示（有活动 hold 即可见），不再依赖页面刷新。

## 交互行为

- **模块切换**：从任务 / 发布 / 设置切回需求模块，若存在活动 hold，聚合区最迟在下一轮主轮询（2 秒周期）内恢复显示，「补决策」入口可达；无需刷新页面。首次进入 / F5 后行为不变。
- **停留需求模块**：hold 从无到有（worker 声明）聚合区随轮询出现；从有到无（复工 / 作废 / 随完成闭环）聚合区随轮询消失（空态整体隐藏）。
- **补决策链路（不回退）**：卡片「补决策」→ 侧拉面板逐项作答 → 可只保存部分（草稿）→ 「未答 x/y」与卡片计数同步 → 齐备后「复工」可点（未答 > 0 禁用 + tooltip）→ 复工后条目回已计划队列、离开聚合区；「确认完成」保留未答防呆二次确认。
- **轮询不打断（不回退）**：数据签名未变时不重绘；重绘不丢失「查看进展记录」展开态、「已答 n 项」折叠态与面板内正在填写的内容。
- **列表行旗标与承接区一致**：行 `⚠ 等人工决策` 旗标出现时，列表下方承接区可达（旗标悬停引导文案指向的位置确有该区）。

## 状态反馈

- 聚合区四态：正常（卡片列表）/ 空（整体隐藏不占版面）/ 加载失败（错误条 + 重试按钮；失败期间保留上次数据）/ 恢复（错误清除后自动回到正常卡片，错误条不残留）；
- 保存反馈：部分保存提示草稿已保存与尚缺项数；齐备提示可复工；失败提示且输入保留可重试（均不回退）；
- 「复工」禁用态与 tooltip、确认完成二次确认弹层、未答 ○ / 已答 ✓ 语义区分、「已等待 <时长>」均保留；
- 修复不新增界面文案；若实现中确需增改文案，集中在 scripts/web/i18n.js 并中英双语同步（见验收标准）。
