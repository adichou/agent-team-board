## 描述

### 背景

看板四条 AI 流水线均以「系统生成提示词 → 人工/主会话粘贴执行」的方式驱动 Agent，提示词由代码装配、事实源如下（均为 scripts/ 源码内联字符串拼接）：

| 流程 | 提示词事实源 | 生成时机 |
| ---- | ---- | ---- |
| AI 分析（需求完善） | `scripts/lib/refine-store.mjs`：`buildRefinePrompt`（主调度提示词）与 `buildRefineWorkerPrompt`（codex 单项提示词） | 启动任务时生成主调度提示词；每领取一个条目生成一份单项提示词 |
| AI 开发 | `scripts/lib/batch.mjs`：`generatePrompt`（主调度提示词）；执行规范为快照文件 `<dataDir>/dispatch/worker-spec.md`（源自 `skills/agent-team-board/worker-spec.md`），提示词内只给路径 | 启动任务时生成一次 |
| AI 完善（提示词与回答回填） | `scripts/web/build.js`：`buildPrompt(v)`（前端本地生成） | 打开「AI 完善」弹窗 / 复制时，按当前版本实时生成 |
| AI 总结 | `scripts/lib/publish-flow.mjs`：`buildDocSummaryPrompt`（阶段一默认语言四文档） | 「文档编写」页启动 AI 总结时生成，含逐文件回执命令（内嵌 runId） |

### 问题：当前提示词结构不利于提示词缓存命中

提示词缓存通常要求**请求间保持稳定且足够长的公共前缀**；前缀一旦分叉，后续全部内容（含静态规则段）都无法复用缓存。逐源码核查，四条流水线存在同类问题：

1. **动态值出现在前部，静态规则反而靠后**：
   - AI 分析主调度提示词第 2 行即 `项目：<projectRoot>`，后续流程正文又多次内插 `--dir <projectRoot>`、`atb 指 node <atbPath>`；单项提示词则把条目编号、runId、缺失原因放在开头，固定「补全要求」段在后。
   - AI 开发主调度提示词同样第 2 行为项目路径，静态调度规则段在后。
   - AI 总结提示词首行内嵌计划号/版本号，随后是项目路径、runId、动态关联条目清单，静态「写作约束」段在末尾。
   - AI 完善提示词首行内嵌版本号，第 2–3 行即当前名称/描述与逐条关联条目+提交哈希列表（每版本必不同），固定「回答格式」约定在末尾——动态内容整体置于静态约定之前。
2. **同一流程存在多种前缀分叉**：
   - 模型跟随行（`FOLLOW_SESSION_PROMPT_LINE`）按 modelSource/model/level 条件注入，有/无两态前缀不同（AI 分析与 AI 开发同口径）。
   - AI 分析约束段按「完善完成后自动转入计划」开关分两态（autoPlan 开/关文案常量不同）。
   - AI 总结的执行编号行、逐文件回执命令段按 runId 有无条件增删；`buildRefineWorkerPrompt` 同理。
3. **同轮多次调用难以共享前缀**：AI 分析每条目一份、AI 总结每文件一报，公共说明段（补全口径、Bug 分支、演示质量门槛、写作约束、回执语义）本可跨子代理/跨文件复用，却因动态值前置而每份前缀都不同。

### 目标

优化上述提示词的**内容组织**（不改各流程的调度、领取、回执、锁与账本语义），使稳定不变的角色、规则、流程、约束段构成统一前缀，把随调用变化的值（项目根、条目编号、执行编号 runId、版本号/计划号、关联条目清单、路径、开关态说明等）收敛到提示词尾部统一的「运行参数」区，并消除或收敛条件行造成的前缀分叉，从而提升 Agent 会话与模型服务侧的提示词缓存命中率，降低重复前缀的处理时延与成本。

### 影响面与约束

- 提示词是「接口」：`buildRefineWorkerPrompt` 的条目目录行等形态被测试夹具与运行核验解析（源码注释明确「保持稳定形态」）；调整形态须同步受影响测试与解析逻辑。
- 提示词在启动/创建时冻结落账（如 batch.json 的 prompt 字段、codex run 记录），存量账本历史提示词按现行口径「原样保留、不回写」，仅新生成的提示词采用新结构；展示/回显层须兼容新旧两种形态。
- AI 完善提示词在前端生成（build.js），其余在后端 lib 生成；前后端同步调整，涉及界面文案（按钮 title、toast 等）如有变化须中英文同步（scripts/web/i18n.js）。
- 各流程的回执命令、CLI 参数、锁与状态机行为不得变化（只重组提示词文本，不改语义）。

### 待确认

- 目标模型/服务商的提示词缓存机制细节（前缀命中判定粒度、最小命中长度、是否需显式开启）在项目内无配置事实：**待确认**——本需求先按「稳定公共前缀」这一通用原则优化。
- 缓存命中率的量化指标（命中前后成本/时延对比）如何验证（依赖具体 Agent 会话环境，项目内无法直接观测）：**待确认**，验收以结构断言为准。

## 验收标准

- [ ] 四条流水线（AI 分析主调度与单项、AI 开发主调度、AI 完善、AI 总结）的提示词生成逻辑完成重组：不变内容（角色、规则、流程、约束、回执语义、质量门槛等）构成稳定前缀；随调用变化的值（项目根、atbPath、条目编号/标题/目录、缺失原因、runId、计划号/版本号、关联条目清单、开关态文案差异）统一收敛至尾部参数区，不再散布在前部。
- [ ] 前缀分叉收敛：同一流程在同一开关/配置组合下生成的前缀保持一致；条件行（模型跟随行、autoPlan 分态、runId 条件行/回执段）不再改变公共前缀（移入参数区或统一恒定形态）。
- [ ] 同轮多次生成（AI 分析逐条目单项提示词、AI 总结逐文件回执语境）共享完全一致的静态前缀，仅尾部参数区不同。
- [ ] 行为零回归：各流程调度、领取（claim/next）、回执（done/fail/hold/release/check 等）命令与语义、锁与账本字段、AI 完善回答解析（`parseAnswer` 的「版本名称：/版本描述：」约定）均不变；提示词输出的指令内容语义不变（仅顺序与组织调整）。
- [ ] 存量账本兼容：历史运行/批次中已冻结的旧提示词不回写，展示与回显（任务面板提示词页签、AI 完善弹窗等）对新旧形态均正常。
- [ ] 依赖提示词形态的测试夹具与解析逻辑同步更新；按 TDD 在 scripts/tests/ 新增/更新对应测试（断言静态前缀跨调用一致、动态值不出现在前缀区等结构性质），实现后 `npm test` 全量通过。
- [ ] 若涉及界面文案变化，中英文在 scripts/web/i18n.js 同步并通过 i18n 相关测试；未引入新的开源依赖（无 licenses.md 变更）。

## 界面展示

本需求不涉及界面改动：对象是四条 AI 流水线的提示词文本组织（生成逻辑在 scripts/lib/refine-store.mjs、scripts/lib/batch.mjs、scripts/lib/publish-flow.mjs 与 scripts/web/build.js 的 buildPrompt 函数），不改任何页面的界面布局、交互行为与状态反馈。描述中出现的「弹窗 / 按钮 / 界面文案」等词仅为指代既有界面入口与文案同步约束（AI 完善弹窗、按钮 title 等），实施默认不触碰这些界面元素；如实施中确需调整界面文案（按钮 title、toast），按验收标准在 scripts/web/i18n.js 做中英文同步，仍不涉及布局、交互与状态反馈的变化。
