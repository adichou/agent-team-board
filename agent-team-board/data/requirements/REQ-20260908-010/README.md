# REQ-20260908-010 批量实施应改名为批量开发，方案应优化为提供一个已计划的状态分类，按照已计划的单自动串行处理。

- 状态：submitted（待人工接受）
- 创建：2026-09-08T02:50:12.373Z

## 描述

0、已接受的单的状态支持修改为已计划。已计划的单只要没有进入开发中状态，可以批量移出计划，变回已接受。
1、提供开发启动按钮，可以选择 zcode 或 codex 的模式；
2、开发启动后，实时从已计划的单中获取需处理的单，先处理最旧的单；处理的单进入开发中状态。

## 问题描述（背景与现状）

现有「批量实施」能力由三条路径组成（详见 `docs/agent-team-board/batch-execution.md`）：

1. **Zcode 批次**（REQ-20260906-002）：顶栏勾选已接受条目后点「进入批量实施」（`scripts/web/index.html` 中 `implGo` 按钮）进入任务模块，点「创建批次并复制提示词」**冻结当前候选快照**（`scripts/lib/batch.mjs` 的 `createBatch`，候选 = `status === 'accepted' && !owner` 的条目，需求优先 → 创建时间 → 编号），再由人工把提示词粘贴到新建的 Zcode 会话逐项派子 Agent。
2. **Codex 自动派发**（REQ-20260906-003）：任务模块内开关式开启，看板服务串行从 `accepted` 取单（`scripts/lib/scheduler.mjs`），每项后台启动独立 `codex exec` 会话。
3. **手工认领**：`/dev next` / `atb claim`（`scripts/lib/core.mjs` 的 `claim()`，accepted → in-progress）。

现状痛点：

- 「批量实施」名字与实际行为（调度 Agent 开发）不符，且 Zcode 批次要「创建批次 + 复制提示词 + 手动粘贴」三步，批次冻结快照后新接受的条目进不了本批，操作链路长。
- 已接受条目没有「排入待办计划」的中间态：入不入批次只能靠批次账本（REQ-20260907-012 的「已入批次」便签）间接表达，条目状态本身仍是 accepted，无法直观表达「这些单是我计划要做的」。
- Zcode 与 Codex 两种模式分散在任务模块的两个子面板（`scripts/web/app.js` 的 `renderBatchDrawer`：Zcode 批次 / Codex 自动派发 / 需求完善），没有统一的「启动开发」入口。

## 目标方案（重述）

1. **改名**：界面与文档中「批量实施」统一改称「批量开发」。
2. **新增状态分类「已计划」**：条目状态机在 `accepted` 与 `in-progress`（开发中）之间增加「已计划」档：
   - 人工把已接受的单改为已计划（单个操作）；
   - 已计划且尚未进入开发中的单，支持勾选后**批量移出计划**，状态变回已接受；
   - 已进入开发中（in-progress）的单不可移出计划。
3. **开发启动按钮**：任务模块提供统一的「开发启动」按钮，启动时选择执行模式：zcode 或 codex。
4. **自动串行处理**：开发启动后，调度器实时从「已计划」队列取单，**最旧的单优先**处理；被取到处理的单状态流转为开发中（in-progress），后续仍走既有 `claim → report → 人工确认完成` 流程。

## 界面布局、交互行为与状态反馈（UI 要求）

- **顶栏选择工具条**：`scripts/web/index.html` 的「进入批量实施」按钮（id=`implGo`）文案改为「进入批量开发」，交互保持现状（勾选条目为范围、未勾选为全部候选）。
- **列表筛选档**：需求列表现有五档（待接受/已接受/开发中/待测试/已完成，`scripts/web/app.js` 的 `LANES`）需要容纳「已计划」——是新增第六个独立档，还是在「已接受」档内做子分类，**待确认**（默认按独立档设计）。
- **改为已计划（单个）**：已接受条目的详情页操作区（`drawerActionsButtonHtml`，现状 accepted 档只有「驳回接受」按钮）新增「改为已计划」按钮；点击免二次确认（对齐既有驳回接受的免确认交互），操作后卡片状态标签即时变为「已计划」。
- **批量移出计划**：在「已计划」档勾选多个条目后，选择工具条出现「移出计划（退回已接受）」按钮（交互对齐现有「接受所选」批量接受，见 `acceptItems`）；已进入开发中的单不可勾选或置灰并提示原因。
- **开发启动**：任务模块新增「开发启动」按钮 + 模式选择（zcode / codex，下拉或分段控件）。启动前面板展示当前已计划队列（按最旧优先预览）；启动后按钮变为「停止」/「暂停后续」（沿用现有批次暂停语义：只阻止领取下一项，在途执行不受影响）。
- **状态反馈**：
  - 被取到处理的单：看板状态标签变为「开发中」，任务面板「当前条目」区显示该单编号与执行器（对齐现有 Codex 面板「当前执行」展示）。
  - 队列实时变化：新改为已计划的单出现在队列中；处理完一项（`report` 后释放占用）自动取下一项。
  - 队列已空：显示等待提示（对齐 Codex 面板现有「队列已空：等待已接受条目」文案风格，改为等待已计划条目）。

## 验收标准

- [ ] 界面（顶栏按钮、任务模块、toast/提示语）与项目文档中「批量实施」文案均改为「批量开发」，无残留旧称误导（`scripts/web/` 下 `grep` 不再出现面向用户的「批量实施」字样；历史需求文档与批次账本旧数据不要求回改）。
- [ ] 已接受条目可在详情页单个「改为已计划」；操作后 `status.json` 状态变为已计划（新状态值命名以 design 为准），看板列表、筛选档、状态标签同步更新。
- [ ] 已计划且未进入开发中的条目可勾选批量「移出计划」，全部变回已接受；批量操作有结果反馈（成功/失败清单，对齐批量接受的 `acceptResult` 区域）。
- [ ] 已进入开发中（in-progress）的条目无法被移出计划：不可勾选或操作被拒绝并给出明确原因。
- [ ] 任务模块提供「开发启动」按钮，启动前可选择 zcode 或 codex 模式；未选择时不可启动。
- [ ] 开发启动后按「最旧优先」从已计划队列串行取单：被处理单状态流转为开发中，占用项目实施互斥（同一项目同时只有一个实施任务，与手工 `/dev` 互斥）；处理完上报后自动取下一项。
- [ ] 「实时获取」：调度器运行期间新改为已计划的条目无需重启即可被后续取到（不再受 Zcode 批次旧模型「创建时冻结候选快照」限制；冻结快照模型的去留见 design 待确认项）。
- [ ] 状态机守卫不变的部分继续成立：只有人能接受/确认完成；Agent 不能自行把条目置为已计划或移出计划（`scripts/state-guard.mjs` 拦截清单同步覆盖新状态的人工专属流转）。
- [ ] 存量兼容：升级后既有条目（submitted/accepted/in-progress/done）与未结束批次账本不受破坏；老数据无需迁移即可正常展示与流转。
- [ ] 完整状态链路可走通：已接受 → 已计划 → 开发中 → 待测试 → 已完成；已计划 → 已接受（移出计划）回退可用。

## 边界与不做的事

- 不改变「只有人能接受需求与确认完成」的铁律；已计划档不改变 report 后等待人工验收的语义。
- 需求完善（REQ-20260907-003，submitted 层面）不在本需求范围内。
- 「已计划」与依赖策略（`policies.json` 的 `dependsOn`）的关系沿用现有规则：依赖未满足的已计划单暂不派发，不自动降级。
