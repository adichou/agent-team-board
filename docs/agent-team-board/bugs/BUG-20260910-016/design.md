## 根因分析

**与 BUG-20260910-012 的重叠归因（验收先决项，三选一定案）：完全同源，且已由 012 修复覆盖。** 证据：

1. **现象逐点吻合**：本条登记的失败形态（timeout-sleep 轮、第 64 行 `waitFor` 等待「后续可运行条目」
   `agentCompletedAt`、断言文案「等待运行结算超时」、负载相关、单独重跑即过）与 012 定案的失败闭环完全一致；
   两者是并行批次对同一 flaky 的两次独立登记（012 于 05:34、本条于 07:52，本条晚登记、早于 012 修复上报 08:11）。
2. **机制核对（当前工作树实测）**：HEAD（`0f84698`）测试对 timeout-sleep 模式全程 `timeoutMs: 150`，
   重启后 worker-ok run（fake-codex 启动 + `atb claim` + `atb report` 三个串行 node 子进程，空闲 ≈85ms、
   余量仅 ≈65ms）在负载下必超 150ms 被调度器按超时强杀、run 落 `failed`，`agentCompletedAt` 永不出现，
   第 64 行 `waitFor` 空转至自身 5s 预算耗尽断言——本条现象由该机制完全解释，无需引入第二故障点。
3. **012 修复在位且针对该机制**：当前工作树 `scheduler-unclaimed.test.mjs`（未提交）已含 012 修复——
   `waitFor` 预算 5s→15s 并给三处等待打标签；`makeScheduler({ probeTimeout })` 按阶段取时限
   （首个 timeout-sleep run 保持 150ms 验证超时强杀路径，重启/后续阶段 5000ms）。
   `git diff scripts/lib/scheduler.mjs` 中生产逻辑与默认参数零改动（`tickMs: 4000 / cancelGraceMs: 10_000 /
   settleMs: 1500 / timeoutMs: 60*60_000` 原样；唯一 diff 是 REQ-20260909-015 的 worker 提示词文案增补，与本条无关）。
4. **复测数据（覆盖登记失败条件，详见本目录 test-report.md）**：在含 012 修复的当前工作树上——
   直连 `node scripts/tests/scheduler-unclaimed.test.mjs` 10/10 通过（其中 4 轮与一次全量 `npm test`
   并行施载执行，正对登记的「负载下失败」条件；其余 6 轮空载）；全量 `npm test` 连续 3 次全绿
   （158 文件/次，`scheduler-unclaimed.test.mjs` 每次通过）；直连单次 ≈2-3s，远低于 run-all 单文件 180s 上限。
   本条登记的失败已无法复现。

**结论：重复登记，不重复改动代码。** 结项依据引用 012 的修复（同工作树未提交改动）与本条上述独立复测数据。
