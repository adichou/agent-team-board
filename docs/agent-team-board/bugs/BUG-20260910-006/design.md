# 设计 — BUG-20260910-006 讨论（开放式）要修改

> 由 Agent 在 /dev 开发前补充，人可随时批注。

## 引入来源（源单）

本 Bug 由哪个需求 / Bug 引入？登记时可暂空或写「未定位」，修复阶段必须归因（三选一，禁止编造）：

- 引入来源：BUG-20260907-014（经 `atb list` 核验存在）。该单将新建弹窗类型选项由「讨论单」更名，
  落地为 `讨论（开放式）`（仓库初始提交即含此文案），其测试断言消息自述「类型文案用类型名『讨论』」
  却带上了「（开放式）」后缀；REQ-20260909-004 W9 断言「面向用户文案统一 讨论」随后固化了该写法。

## 根因分析

- `scripts/web/index.html` 的 `#fType` 讨论选项文案为「讨论（开放式）」。同弹窗其余两项
  「需求（REQ）」「Bug（BUG）」括号内均为编号前缀，唯独讨论选项括号内是形态修饰词「开放式」，
  与既定口径（BUG-20260907-014「类型文案用类型名『讨论』」、REQ-20260909-004 W9
  「面向用户文案统一 讨论」）不符，用户在截图中红框要求修改。
- 类型名之外的「开放式」字样（模块副标题「开放式讨论，看板沉淀成果」、讨论视图空态/详情的
  描述性用法）描述的是模块形态而非类型名称，不属于本 Bug 现象范围。

## 方案

**最终文案决策（解决 README「待确认」项）**：

1. 类型名称统一为「讨论」：`<option value="ask">讨论</option>`。依据：BUG-20260907-014 断言口径
   「类型文案用类型名『讨论』，不得写『讨论单』」；REQ-20260909-004 W9「面向用户文案统一 讨论」；
   导航页签、模块标题、空态引导等面向用户位置均已称「讨论」，新建弹窗对齐后全前端类型名唯一。
   展开列表与收起选中值为同一 option 文字，天然一致，不出现一处更新一处保留旧称。
2. 同步范围：仅新建弹窗 `#fType` 讨论选项（本 Bug 定位）。其余「开放式」字样保留——
   副标题「开放式讨论，看板沉淀成果」是 BUG-20260909-013 的既定口径（有独立断言），
   oncall.js 空态「创建第一条开放式讨论」、详情「开放式 · 无需关联需求」为模块形态描述，非类型名称。
3. 行为不变：类型值仍为 `ask`，仍走 `/api/discussion`，选中后由 `syncNewFormFields` 显示
   标题 + 背景（可选）、隐藏截图区块；标题必填、背景可空的校验口径不变。
4. 测试同步：`workbench-layout.test.mjs` W6 精确断言更新为 `<option value="ask">讨论</option>`；
   W9 改为断言新文案存在且 `讨论（开放式）` 不再出现（BUG-20260910-006 口径）。

**开源选型（REQ-20260909-015）**：纯界面文案修改，无新增依赖，不涉及开源库；未使用开源库，不创建 licenses.md。
自研理由：无合适库的原因——单处静态文案替换，引入任何库的成本均高于直接修改。

## 风险与边界

- 断言「讨论（开放式）」的既有测试（W6/W9）已同步更新；`discussion-ui.test.mjs` 的宽松断言
  `/option value="ask">讨论/` 前后均通过。全量回归 141 个测试文件 0 失败。
- 不改 `ask` 值与 `/api/discussion` 接口，存量讨论数据（ASK 序列编号）不受影响。
- 不修改副标题等「开放式」描述性文案，避免越出本 Bug 范围、破坏 BUG-20260909-013 既有断言。
- 人工验收项（浏览器展开/收起视觉一致性、焦点边框）不在静态测试范围，按 README 验收说明执行。
