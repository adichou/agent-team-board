# 设计 — BUG-20260914-019 REQ-20260914-004 这个需求对生成的提示词追加一个换行符，用户的问题和提示词可以有明确的换行分隔

## 引入来源（源单）

本 Bug 由哪个需求 / Bug 引入？登记时可暂空或写「未定位」，修复阶段必须归因（三选一，禁止编造）：

- 引入来源：REQ-20260914-004（已核验：`atb list` 存在，状态 done；其 commit 8196d60 落地右键「讨论」提示词追加「讨论要求」，`buildDocRef` 以 `lines.join('\n')` 返回，末行「4. 每轮回答回显本轮 commit log 与 commit 号（短哈希即可）。」后无换行）。

## 根因分析

`buildDocRef`（`scripts/web/app.js`，唯一组装点，`onDocCtxMenu` 单点调用）以 `lines.join('\n')` 返回提示词：join 只在行间插入分隔符，最后一行之后即字符串结尾，末尾无换行符。该提示词的标准用法是「粘贴到 Agent 会话输入框 → 紧接着输入自己的问题」，粘贴后光标停在末行行尾，用户直接键入的问题与「…（短哈希即可）。」连在同一行，既难读也可能被 Agent 理解为第 4 条指令的延续。自动复制（`copyPlain` 双回退原样写剪贴板）与失败回退弹窗（`uiCopyBox` textarea 展示同一 `info.text`）走的都是同一组装结果，故三条链路末尾均无换行——一处根因，一处修复全部生效。

## 方案

`buildDocRef` 返回值改为 `lines.join('\n') + '\n'`：末尾恰追加一个换行符，其余内容一字不变。用户粘贴后光标已在新行，直接输入的问题与提示词有明确换行分隔；`copyPlain` 主路径 / `execCommand('copy')` 回退 / `uiCopyBox` 手动复制均消费同一文本，自动带上末尾换行，零额外改动。

测试（TDD）：`scripts/tests/doc-ctx-discuss-req-20260914-004.test.mjs` 追加 T9——有选中 / 无选中两场景断言 `endsWith('\n')` 且不以 `'\n\n'` 结尾、末行内容保持不变、开头不加换行；先跑红（现状 `join('\n')` 无末尾换行）再实现跑绿。既有 T1–T8 及 `doc-ctx-discuss-20260909-014.test.mjs`、`doc-ctx-discuss-bug-20260913-003.test.mjs` 断言均为 `includes` 口径，不受末尾换行影响，全量 `node scripts/tests/run-all.mjs` 回归通过。

**开源选型（REQ-20260909-015）**：未引入开源库——改动为单行字符串拼接（追加一个 `'\n'`），无成熟库适用场景，自研成本低于任何引入成本；不创建 licenses.md。

## 风险与边界

- 只追加**一个**换行：不以 `'\n\n'` 结尾（避免粘贴后出现空行）、不在开头 / 中间加空行；提示词其余内容（引用要素 + 讨论要求四条指令）一字不变（T9 断言末行内容不变）。
- 交互零回退：右键菜单唤起 / 收起通道、`copyPlain` 双回退、toast 摘要口径、`uiCopyBox` 只读全选弹窗均不动，仅文本内容末尾多一个换行。
- 纯前端剪贴板文本改动：无后端 API、无文件写入、无状态机 / 样式变化；有 / 无选中、README / design / test-cases 三页签与需求 / Bug 抽屉共用 `buildDocRef`，同口径全部生效。
- 范围边界（README 已声明默认不改）：`scripts/web/req-disc.js` 另一套讨论提示词（REQ-20260914-003 优化）不在本单范围，如需对齐另行确认。
- 对剪贴板消费方的兼容性：多出的末尾换行对 Agent 输入框 / 文本编辑器均为常规段落分隔，无已知副作用。
