# BUG-20260909-001 开发任务终止后看板不显示「已终止」口径：/api/batch/current 未透出 aborted 字段

- 状态：in-progress（开发批次 batch-20260909-019 实施中）
- 归属：独立 Bug
- 引入来源：REQ-20260908-020（引入开发批次人工终止收尾与前端「已终止」展示（renderZcodeBatchPanel 依赖 b.aborted），但 /api/batch/current 的 batch 视图与 CLI batchPublicView 未同步公开 abortRequested/aborted 字段；ID 经 `atb list` 核验存在）
- 创建：2026-09-08T18:00:21.911Z

## 现象

人工终止开发批次后，账本已记录终止，但看板「任务 → 批量开发」面板显示「已结束」，缺少「已终止」徽标和「任务已人工终止」警告。用户无法从面板区分自然处理完毕与人工中断，也看不到仍需到在途子代理会话人工停止的提示。暂停按钮已由 `status === 'finished'` 兜底隐藏，本 Bug 不表示后台仍在继续派发。

2026-09-09 静态核对当前代码：

- `scripts/server.mjs` 的 `GET /api/batch/current` 手工构造 `batch`，漏掉 `abortRequested`、`aborted`；`POST /api/batch/abort` 则调用 `scripts/lib/batch.mjs` 的 `abortBatch` 收尾。
- `scripts/web/app.js` 的 `renderZcodeBatchPanel` 已依赖 `b.aborted` 显示终止徽标、警告和当前条目替代文案。HTTP 缺字段使这些分支无法反映账本真实状态。
- `scripts/atb.mjs` 的 `batchPublicView` 同样遗漏两个字段，影响 `batch summary --json` 等使用该公开视图的输出。
- `/api/batch/current` 的 `queue` 也未列出这两个字段，但 `unfinishedBatches` 仅返回 `status !== 'finished'` 的批次，已终止批次按现有规则不属于队列。不能通过把终止批次重新塞入队列来解决展示问题。
- 完善侧 `scripts/lib/refine-store.mjs` 的 `refineBatchPublicView` 已使用 `Boolean(...)` 公开这两个字段，可作为字段口径参照。

上述为代码核对，尚未在真实服务执行终止请求；实际浏览器与运行环境复现结果待开发阶段确认。

## 复现步骤

### 前置条件

使用可丢弃的测试项目及测试批次；准备至少一个已接受且已移入计划的候选，创建开发批次。确保当前只有这一个未结束批次，且没有更新的批次，以便终止后 `/api/batch/current` 回退显示同一批次。记录批次 ID。不要在真实在途业务批次上为复现而终止任务。

### 界面与 HTTP 对照

1. 打开该测试项目的 Status Board，进入「任务 → 批量开发」，确认能看到目标批次 ID。
2. 点击「终止任务」，阅读二次确认说明后确认。浏览器网络面板应看到 `POST /api/batch/abort`，请求体为 `{"batchId":"<目标批次ID>"}`；确认请求成功。
3. 等面板刷新，核对随后 `GET /api/batch/current` 的 `batch.batchId` 仍是目标 ID。对照测试项目 `docs/agent-team-board/dispatch/batches/<批次ID>/batch.json`：账本应为 `status: "finished"`、`abortRequested: true`、`aborted: true`。
4. 缺陷版本的 HTTP `batch` 只有 `status: "finished"`，缺少两个终止字段；界面显示「已结束」，当前条目无在途运行时显示「本轮已结束」，没有人工终止警告。
5. 手动刷新页面后重复核对，缺陷仍在。若返回的是后续排队批次，属于正常队首切换，需重置上述前置条件后再验证，不能据此判定终止信息丢失。

### CLI 公开视图对照

对同一个测试批次运行只读命令 `node scripts/atb.mjs batch summary --batch <批次ID> --json --dir <测试项目路径>`，检查 `batch` 对象。当前代码同样不输出 `abortRequested`、`aborted`。此步骤只验证摘要输出，不再次终止或修改批次。

## 期望行为

1. HTTP 当前开发批次的 `batch` 和 CLI `batchPublicView` 均公开 `abortRequested`、`aborted`，值分别按原始字段 `Boolean(...)` 归一化。存量缺字段输出 `false`，不能把所有 `finished` 都推断为人工终止。
2. 同一已终止批次被展示时，徽标为「已终止」，显示人工终止警告；没有当前在途记录时，当前条目显示「任务已终止」。自然结束批次继续显示「已结束」与自然完成提示。
3. 保留现有批次 ID、开发人员、计数和执行记录；终止后不显示暂停/恢复入口，启动新一轮沿用现有执行 Agent 选择与可用性规则。本修复不改变终止收尾、条目业务状态和项目队列调度。
4. 核对 queue 视图口径并在开发记录说明结果：正常未结束队列顺序不变，终止批次仍不入队。是否为 queue 的每个成员同步新增布尔字段待确认；不作为终止徽标修复的必要前提。

## 界面布局、交互与状态反馈

沿用现有「批量开发」面板：顶部同一状态行依次放状态徽标、批次 ID、执行 Agent 与开发人员；状态行下方放提示条；再显示当前条目、计数、待处理队列与执行记录。警告使用现有 `notice warn` 样式，徽标使用 `s-aborted`，文字不能只通过颜色区分。

- 人工终止：徽标「已终止」；警告完整文案为「任务已人工终止：本轮全部处理记录已保留；在途子代理请在对应子代理会话人工停止。」不同时显示自然完成的成功提示。
- 正常运行：保留当前条目与「终止任务」入口；终止前二次确认，取消维持原状态，确认成功后刷新真实响应再更新展示。
- 自然结束：显示「已结束」和「本轮已结束」，无人工终止警告，暂停/恢复入口隐藏。
- 空状态：`batch: null` 时仍显示候选统计与原有启动引导；没有候选时提示先接受条目并移入计划，不生成空批次或误显示终止。
- 加载状态：首次没有数据时显示「加载中…」，不提前展示终态结果。
- 失败状态：获取当前批次或终止请求失败时沿用错误 toast，保留上次可信数据；不把请求失败渲染成终止成功。后续成功刷新恢复实际状态。无需为本 Bug 新增产品重试按钮。

## 界面展示

界面展示对照：当前缺陷为「已结束」徽标、当前条目「本轮已结束」且没有人工终止警告；期望修复后为「已终止」徽标、当前条目「任务已终止」，状态行下方显示完整人工终止警告。批次 ID、开发人员与处理记录保持可见。其余正常、空、加载和失败状态按上一节核对。

## 验收说明

- [ ] 同一已终止批次在 HTTP `batch` 与 CLI 摘要 `batch` 中均有 `abortRequested: true`、`aborted: true`，类型为布尔；账本终态与既有其他返回字段保留。
- [ ] 存量缺字段、正常运行、暂停及自然结束批次的两个字段按原值布尔化；缺字段为 `false`，自然结束不被误判为人工终止。
- [ ] 已终止批次经实际 HTTP 刷新和整页重载后均显示「已终止」及完整人工终止警告；无当前项显示「任务已终止」，不出现自然完成成功提示。
- [ ] 自然结束仍显示「已结束」；运行/暂停批次保持原展示；终态不出现暂停/恢复按钮，启动新一轮仍受现有 Agent 选择条件约束。
- [ ] 无后续队列的复现可稳定观察同一终止批次；有后续队列时保持 FIFO 队首切换，终止批次不回到未结束队列，后续批次不继承其终止标记。
- [ ] 终止前取消确认无请求、无状态变化；请求失败显示错误且不伪报成功；首次加载与无批次状态不渲染终止徽标。
- [ ] 处理记录、计数和条目业务状态未因字段透出而改变；完善侧终止展示未受影响。开发阶段以真实 HTTP/CLI 验证字段，不能只向渲染函数手工传入 `aborted: true`。
