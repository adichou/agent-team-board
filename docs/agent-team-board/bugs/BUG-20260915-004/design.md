# 设计 — BUG-20260915-004 挂起确认面板错误提示透传截断的原始 git 报错，缺少可读原因与处理指引

> 由 Agent 在 /dev 开发前补充，人可随时批注。

## 引入来源（源单）

- 引入来源：REQ-20260914-001（引入「自动提交不完整时挂起条目并暂停队列，人工确认后恢复开发」闭环；挂起原因的采集、截断与面板透传展示均由该需求引入）

## 根因分析

两处叠加（开发阶段核实行号）：

1. 挂起登记处对 reason 做 120 字符硬截断：`scripts/lib/batch.mjs` 收尾登记 `receipt.suspended = { …, reason: suspendReason.slice(0, 120) }`。本例原文关键段 `…/.git/index.lock': File exists` 落在 120 字符之后，被整段截掉，只剩现象开头。
2. 面板无归因与指引层：`scripts/web/app.js` 挂起确认面板直接把 `d.reason` 原样渲染为 `confirm-reason` 段落，没有任何「常见失败原因归类 + 建议操作」的翻译层。用户看到的是截断的机器输出。

## 方案

**开源选型（REQ-20260909-015）**：纯自研文案/截断逻辑，无外部依赖诉求（无合适库：仅字符串归类的几十行代码，引入依赖成本高于自研）。

方向（开发阶段细化并补测试）：

1. 采集侧：挂起 reason 不再 `slice(0, 120)` 拦腰截断；保留完整原文（账本字段），展示层负责收纳。
2. 展示侧：面板把挂起原因分两层——默认一行归类结论（新增 `classifySuspendReason`：匹配 `index.lock`/`File exists` →「git 索引被并发进程占用，属瞬时冲突，可重试」等）+ `<details>` 折叠完整原始输出。
3. i18n：归类文案走现有 `scripts/web/i18n.js` 双语表。

## 风险与边界

- 账本 reason 字段加长后注意各读取方（batch check ≤2KiB 摘要等）不受影响——摘要处自行截断，但展示详情不截断；
- 归类只做「建议」，不自动重试、不代替人工确认（闭环语义不变）。
