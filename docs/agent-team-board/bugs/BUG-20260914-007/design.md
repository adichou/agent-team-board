# 设计 — BUG-20260914-007 body-limit.test.mjs 在 run-all 全量跑下偶发失败（单独运行通过）

> 由 Agent 在 /dev 开发前补充，人可随时批注。

## 引入来源（源单）

- 引入来源：BUG-20260907-004（已经 `atb list` 核验存在且 done）
  `scripts/tests/body-limit.test.mjs` 是该 Bug 修复时新增的回归测试（文件头注释与用例名均标注该编号），
  其环境敏感实现（启动就绪预算 ≈ 6s、单请求 20s 超时、无重试、无失败定位输出、server stderr 直接丢弃）
  随该测试一并引入，本 Bug 修复的就是该测试自身的稳定性缺陷。

## 根因分析

全量 `run-all.mjs` 顺序执行约 250 个测试文件，期间持续 spawn 大量子进程，机器负载显著高于单文件运行。
该测试的两处环境敏感环节在原实现中预算过紧且无任何诊断信息：

1. **服务就绪等待过紧**：spawn 真实 `server.mjs` 后轮询 `/api/health` 仅 40 次 × 150ms ≈ 6s。
   高负载下 Node 冷启动 + server.mjs 加载可超过 6s → `assert.ok(up, '服务应启动')` 失败。
   且原轮询把「任何响应」都当作就绪（非 200 也算），对健康语义校验不严。
2. **大包传输超时过紧且不可定位**：每个请求 `timeout: 20000`，高负载下 2MB–18.7MB 级请求体的
   写入/回包可能超过 20s；超时错误只抛裸 `new Error('timeout')`，无法区分是哪一步（T1/T2/T3/恢复）超时。
3. **失败输出截断 + 诊断信息丢弃**：文件内 runner 只打印错误第一行；server stderr 用
   `stdio: 'ignore'` 丢弃，失败后无法判断是服务崩溃还是负载抖动。

单独运行时负载低，两处预算均远未触顶，故稳定通过。

## 方案

**开源选型（REQ-20260909-015）**：未引入开源库。自研理由：所需能力仅为 node:http 内建超时事件的
包装、指数级不需要的重试循环与文本诊断输出，Node 标准库已完整覆盖，引入第三方测试工具库
（如 jest/awaiter 类）替换单文件轻量测试的成本与依赖面远高于自研，无合适且值得引入的库。

仅改测试层（验收边界 5），`scripts/server.mjs` 的 `BODY_MAX_BYTES = 12MB` 与超限 400 JSON 行为零改动：

1. **启动等待放宽 + 快速失败 + 诊断**：`waitReady()` 默认预算 45s（原 ≈6s）、间隔 200ms、
   单次探测超时 ≤2s；仅 `/api/health` 返回 200 才算就绪；server 进程退出即停止轮询快速失败；
   预算耗尽抛「服务启动未就绪」，附探测次数、最后错误（ECONNREFUSED=未监听 / HTTP xxx / 超时）、
   进程退出信息（code/signal）、server stderr 尾部（≤1500 字符，stderr 落临时文件）。
2. **请求环节标签**：`req()` 增加标签参数，超时 → `请求超时[<环节>]：Nms 无响应`，
   连接错误 → `请求失败[<环节>]：错误码`；环节覆盖 健康检查 / T1 2MB 附件创建 / T1 附件查询 /
   T2 总量超限 400 / T3 /api/new 超限 400 / 超限后恢复。
3. **传输类抖动重试（留痕不静默）**：`withTransportRetry()` 仅对传输类错误
   （超时 / ECONNRESET / EPIPE / ECONNREFUSED，以 `err.transport` 标记）重试，默认 1 次；
   每次重试打印 `↻ <环节> 疑似环境抖动（原因），重试 n/N`；功能性失败（断言、状态码不符）不重试直接抛出。
   单请求超时默认放宽为 30s。
4. **注入旋钮（验收 3/4 的失败注入方式）**：环境变量
   `ATB_TEST_BODY_LIMIT_STARTUP_BUDGET_MS`（默认 45000）、`ATB_TEST_BODY_LIMIT_REQ_TIMEOUT_MS`（默认 30000）、
   `ATB_TEST_BODY_LIMIT_TRANSPORT_RETRIES`（默认 1）；非法值在加载期快速失败并提示。
5. **文件内 runner 输出完整多行错误**（原只打印第一行），保留诊断留痕。
6. **新增 3 个轻量自检用例**（不 spawn server、不传大包，确定性验证诊断契约）：
   启动未就绪消息可定位（ECONNREFUSED/探测次数/退出信息/stderr 尾部，且非 200 不算就绪）；
   请求超时带环节标签；传输类重试留痕后成功且功能性失败不重试。
   原 4 项功能断言（2MB 200 / 2×7MB 400 / 13MB 400 / 超限后恢复 200）语义与文案不变。

## 风险与边界

- **重试语义**：重试仅发生在未收到响应的传输类错误上；T1/T3 的 POST 若在超时后实际已落盘，
  重试会多创建一条记录，但断言只依赖成功那次响应（按返回 id 查询），不构成语义破坏。
- **最坏时长**：启动 45s + 每请求 30s×(1+重试 1) 仍受 run-all 单文件 180s 上限保护，
  真正的功能性挂死会被 runner 终止并以非零退出暴露（与修复前一致）。
- **Node 版本**：本机 Node 17.8，未使用 18+ 专属 API（如 `server.closeAllConnections`），
  自检用例的 never-respond server 用手动 socket 追踪清理。
- 不修改 `run-all.mjs` 与任何其他测试；不触碰 `status.json`；不自动 commit。
