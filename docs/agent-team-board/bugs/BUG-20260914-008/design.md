# 设计 — BUG-20260914-008 新建版本是关联条目重复提示。导入条目到已有版本一样重复提示，请修复

> 由 Agent 在 /dev 开发前补充，人可随时批注。

## 引入来源（源单）

- 引入来源：BUG-20260913-001（经 `atb list` 核验存在，状态 done）
- 归因依据：`git log -S` 定位到提交 87a2fca「fix: 版本创建时应该允许关联的需求范围是已完成
  BUG-20260913-001」。该修复在 `renderPanel()` 候选空态正文新增
  「暂无可纳入版本的条目：仅已完成（done）的需求单 / Bug 单会出现在候选中」，而面板头部
  副标题（`side-panel-scope`，随 REQ-20260913-001 构建模块初始实现引入）本就承载同一候选
  口径——空态分支从此在单个面板内口径出现两次。后续 BUG-20260914-004 只是给空态加了
  `totalDone` 两分支并把口径文案更新为「未纳入其他版本」，未消除重复（其改动的只是重复的那段正文）。

## 根因分析

`scripts/web/build.js` `renderPanel()`（约 802–831 行）把候选口径写在两处：

1. 头部副标题：调用方传入的 `scope` 参数（约 1104–1105 行，新建 / 添加两面板各自文案，
   均含「仅已完成（done）且未纳入任何版本的需求单 / Bug 单…」）；
2. 空态正文：`p.candidates.length === 0 && !p.totalDone` 分支渲染
   「暂无可纳入版本的条目：仅已完成（done）且未纳入其他版本的需求单 / Bug 单会出现在候选中」。

两段语义相同、表述近似，叠加后读起来啰嗦且像 bug。重复只发生在「无 done 条目」空态分支：
`totalDone > 0` 的占用态文案（BUG-20260914-004）不含口径、正常候选态只有头部一处。

## 方案

**开源选型（REQ-20260909-015）**：纯文案展示修复（删一段字符串），无合适库可复用；
自研理由：无合适库的原因——改动为单行模板字符串收敛，引入任何依赖的成本都高于自研。

- 口径单点化：保留面板头部副标题（两面板现有文案不动），「无 done 条目」空态正文精简为
  「暂无可纳入版本的条目」，不再整段复述口径（与 README 期望文案一致）。
- 保留 BUG-20260914-004 空态区分：`totalDone > 0` 分支文案「已完成的条目均已纳入版本计划：…」
  原样保留；缺 `totalDone` 字段时仍回落「无 done 条目」分支。
- 不触碰其他状态：加载中「正在读取条目…」、加载失败（错误 + 重试）、正常候选态
  （全选条 / 候选行 / 版本名称输入）渲染逻辑不变。
- 测试：新增 `scripts/tests/bug-build-scope-dup-empty-20260914-008.test.mjs`——vm 前端
  断言两面板空态下口径关键词「仅已完成（done）」在面板 HTML 中恰好出现一次、空态正文为精简
  文案；并回归占用态文案与正常态口径单次。既有两测试对空态断言的是前缀
  `/暂无可纳入版本的条目/`，精简文案仍匹配，无需改动（README 第 5 条要求核验，已核验通过）。

## 风险与边界

- 空态正文信息量下降：口径仍在头部副标题可见，无信息丢失；文案精简后与
  BUG-20260914-004 占用态文案的区分度更高（一个短句 vs 一个长句）。
- 既有测试断言前缀仍匹配（见上）；`ui-demo.html` 的「期望修复后」演示与最终文案一致。
- 不改后端接口与数据结构，无兼容性影响。
