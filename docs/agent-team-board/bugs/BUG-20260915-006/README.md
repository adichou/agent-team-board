# BUG-20260915-006 default-port 测试以 800ms HTTP 探活判定端口占用不可靠，面板触发核验时必现假失败

- 状态：submitted（待人工接受）
- 引入来源：REQ-20260905-003（引入 scripts/tests/default-port.test.mjs 及其「HTTP 探活判端口占用」策略）
- 创建：2026-09-15T00:39:41.577Z

## 现象

同一份 `scripts/tests/default-port.test.mjs`（工作区与提交内容一致，无未提交改动），两种环境跑出**不同的假失败**：

1. **面板触发核验（BUG-20260914-020 挂起确认，09-15 08:35）**：`✗ V6 集成：未设 ATB_PORT 时 /api/health 返回 port=8888 —— 默认端口 8888 上应能探活`，240 个测试文件仅此一个失败。后果：确认并继续的「测试全绿」关卡被卡死，条目无法恢复队列。
2. **终端单独运行（服务空闲时）**：V6 正确跳过（探活命中 →「8888 已被占用，跳过」），却 `✗ V7 集成：ATB_PORT=7737 覆盖仍生效 —— 未设默认端口时不应再占 8888`。

即测试结果取决于瞬时环境，与被测代码无关。

## 根因（登记时已实证）

`default-port.test.mjs` 的 `portBusy()` 用 **800ms 超时的 HTTP GET /api/health** 来判定端口是否被占用：

- 探活**超时/出错即判定「未占用」**——把「占用者响应慢」误当「端口空闲」；
- 面板核验场景：Status Board 服务进程用 `spawnSync` 同步跑 `npm test`（最长 600s），**阻塞自身事件循环**，期间 8888 上真正的看板服务无法在 800ms 内应答 → V6 的跳过护栏失效 → 尝试自起服务 → EADDRINUSE 静默失败 → 探活 8s 无果 → 断言失败（此场景为必现）；
- 终端场景：V7 起始的 `portBusy(8888)` 预检偶发超时（看板服务正常但那一刻响应慢，如 2s 轮询/health 扫描项目列表）→「跳过『不应再占 8888』断言」的护栏未武装 → 结尾探活又命中真服务 → 断言 `portBusy(8888)===false` 失败。

## 复现步骤

1. 面板必现路径：看板开着（8888 有服务）→ 任务页对任一提交挂起条目点「重新核验」或「确认并继续」→ 服务端 spawnSync 跑 `npm test` → default-port.test.mjs 的 V6 假失败；
2. 终端偶现路径：看板开着 → 终端 `node scripts/tests/default-port.test.mjs` 反复跑，V7 的 8888 预检超时即失败。

## 期望行为

端口占用判定改为**真实 bind 探测**（`net.createServer().listen(8888)`：EADDRINUSE = 已占用；成功 bind = 空闲，随即关闭），不依赖占用者的 HTTP 响应速度；V6/V7 的跳过护栏与「不应再占 8888」断言都基于该可靠判定。

## 验收标准

1. 看板服务运行中，从面板触发核验：default-port.test.mjs 的 V6 稳定走「已占用 → 跳过」分支，不再假失败；
2. 看板服务运行中，终端反复单跑该文件（≥10 次）：8 个用例全绿，无 V6/V7 抖动；
3. 8888 确实空闲时：V6 仍真实起服务并断言 `port=8888`（跳过逻辑不误杀）；
4. 新增 bind 探测有单测或用例内自证覆盖（占用/空闲两分支）。
