# Codex 批量开发 A/B 测试方案

日期：2026-09-07。阶段：合成任务试跑和 Luna/high 正式主测均已完成。试跑结果见 [2026-09-07 Codex A/B 试跑报告](test-runs/20260907-codex-ab-pilot/README.md)，正式结果见 [2026-09-07 Codex A/B 正式主测](test-runs/20260907-codex-ab-main/README.md)。

对比目标：量化“轻量主会话＋每项新子 Agent”相对“后台程序＋每项独立 Codex 会话”的 Token 增量、上下文增长及使用体验。结论同时考虑完成质量，不能把少做工作或提前失败算作省 Token。

配套：[结果报告模板](codex-ab-test-report-template.md)。关联：[批量开发说明](batch-execution.md)、[后台派发需求](requirements/REQ-20260906-003/README.md)、[模型配置需求](requirements/REQ-20260906-024/README.md)。

## 1. 实验分组

| 项目 | A：主会话派发子 Agent | B：后台自动派发 |
| --- | --- | --- |
| 调度者 | 一个全新 Codex 主会话，仅派发、等待短回执、最小核对 | 看板普通程序调度 |
| 实施者 | 每项一个新子 Agent；同一时间一个；不再嵌套派发 | 每项一个新的 codex exec；不再嵌套派发 |
| 输入 | 本项任务包、必要项目规则、固定 worker 指令 | 同样的本项任务包、项目规则、worker 指令 |
| 历史隔离 | 主测显式不继承主会话历史；必须验证实际入口支持 | 不跨条目 resume/fork；同项只用确切会话 ID |
| 输出 | 每项最终短回执≤2 KiB，详细日志落盘 | 同样的最终回执与落盘证据 |
| 主会话工作 | 不读完整日志，不复做实现或验收，不高频轮询 | 相同选单与完成核对由程序执行 |

A 测的是经过约束的轻量调度模式。若实际入口不能关闭历史继承，将其标为 A-native 并单独报告；不能把这种结果写成“无历史继承 A”。当前会话可用的子 Agent 创建工具有历史控制参数，但不能据此假定所有 Codex 入口都提供同一参数。

A-native 默认继承模式、A 主调度改用较轻模型、20 项以上长批次均为后续扩展实验，首轮不混入。

## 2. 先固定比较口径

- 首轮 A 主调度、A worker 与 B worker 使用同一明确模型、推理强度、提供方、服务档位和账户；关闭测试内自动换模型。每次执行记录实际请求设置，有运行时确认值则另存。
- 固定同一源码基线、依赖版本、Node/CLI 版本、项目规则、必需工具、权限、测试命令、任务顺序及续跑策略。必需规则两组均保留，不为缩短 A 上下文削掉实施约束。
- A 应使用能与 B 对齐版本的本地 Codex 入口。若选择桌面入口且内置版本、工具封装与 B 不同，记录差异；结果属于“实际工作流对比”，不能全部归因于调度方式。
- 两组实现并发都为 1。首次启动、工具初始化、主调度输出、失败、重试、续跑和压缩的可观测用量均计入；本次方案讨论、测试准备和独立验收不计入实施用量。
- 首轮不使用额外模型评审；预先固定的自动验收＋人工检查一致应用于两组。后续若加入模型评审，应单列其用量。
- 保留原生缓存和自动压缩。分开记录缓存输入，不能通过给提示词添加随机垃圾、关闭压缩或移除工具来制造比较优势。

本实验主要比较完整工作流，因此 A worker 自行领取任务而 B 程序选单等实际差异也纳入结果。分解“主调度用量”与“worker 用量”后，再判断开销来自哪里。

## 3. 任务样本与代码隔离

### 任务集

主测目标为 10 项：4 项轻量、4 项中等、2 项复杂。下面是选样口径，不是已经准备好的任务，也不是虚构的 REQ 编号。

| 层级 | 数量 | 适合的工作 | 预先固定的验收证据 |
| --- | ---: | --- | --- |
| 轻量 | 4 | 局部 UI 状态/交互、小范围输入校验、展示或格式处理 | 精确的状态/输入输出断言；UI 项附页面验证 |
| 中等 | 4 | 设置持久化、API 与 UI 联动、分页/过滤、错误反馈 | 存储/API 行为、刷新恢复与回归检查 |
| 复杂 | 2 | 调度恢复、并发互斥、跨模块状态衔接 | 并发/故障夹具、恢复后状态和原有行为回归 |

优先选择已人工接受、尚未实施、描述清楚的真实条目。实施前冻结 task-manifest：真实编号、难度、描述及验收文件哈希、顺序、依赖、相关模块、验收命令和时限。样本不足时缩小并明确样本量；不能用当前已经实现的需求让某组直接回答“已完成”。

若通过 atb 真实状态机运行，使用已接受条目的隔离副本；Agent 仍只通过 claim/report 更新副本，不在原项目接受、认领或上报实验任务。合成夹具另行标识，不能冒充真实需求。

### 隔离方法

每个完整批次从同一个冻结源码及任务状态快照创建新目录。可用 Git 时使用独立副本/工作树并核对文件哈希；非 Git 项目使用明确排除旧执行日志、构建产物的文件快照，不能假定能从历史提交还原。

目录示例：R1-A、R1-B、R2-B、R2-A。各自使用独立的看板执行账本、锁、缓存产物目录及服务项目绑定；必要的本机认证保持同一配置。不要在同一工作目录轮流执行 A、B，也不要让 B 读取 A 的实现、报告或主会话摘要。

批次内保留本组上一项的改动，这是批量开发的真实行为；进入下一个完整批次时重新从基线复制。避免任务互相依赖，尤其避免修改同一个核心模块。如果无法避免，冻结相同依赖顺序并标记：两组后续源码可能因先前实现不同而分化，此时比较单位是整批，不是互相独立的十个任务。

已有失败若使继续不安全，应停止该组，记录未执行任务及批次完成率，不为了凑满样本清空改动或跳过问题。需要诊断后续任务时，在另建的独立单项实验中进行，不混回主批次。

## 4. 分阶段执行

| 阶段 | 安排 | 规模与目的 |
| --- | --- | --- |
| 0：采集预检 | 检查 CLI/模型能力、日志路径、父子关联、用量字段、上下文可观测性、隔离目录与验收基线 | 静态工作，不发模型请求；已有适配器不等于采集已就绪 |
| 1：试跑 | 取独立于主测的 1 项轻量＋1 项中等，两组各跑一次 | 共 4 个任务执行；先验证每一项是否能闭环统计，估算主测预算 |
| 2：主测 | 第 1 轮先 A 后 B，第 2 轮先 B 后 A；每组跑相同的 10 项完整批次 | 共 40 个任务执行，另有 2 个 A 主调度会话；批次内顺序对应一致 |
| 3：必要时扩展 | 结论摇摆时增加新的成对批次；需评估更长运行时再做 20 项配对批次 | 不从 10 项结果直接推断 100 项或永久无人值守 |

阶段 1 的试跑任务不再进入主测；至少使用不同任务输入，避免直接复用试跑答案。主测前任务与验收已冻结，之后不得根据哪组表现好而换题。AB/BA 用来平衡先后顺序与缓存影响，不能保证完全消除缓存或模型服务波动。

默认单项时限建议 30 分钟，同项最多追加 2 个 Codex turn，自动网络重试最多 2 次，两组一致。这里的 turn 不是每个工具调用。时限覆盖同项正常续跑及重试；人等待时间另列，问题导致用户必须介入时计一次介入并按预定暂停规则处理。

先完成阶段 0、1，再用试跑的实际用量和耗时制定主测上限。主测预计任务数为 40，使用按难度估算的总量并预留约 30% 余量；这是预算建议，不是已有测量。只做方案时不启动任何阶段的模型任务。

若只能在 turn 结束看到用量，则预算是“下一次调用前停止”的软门槛，不能保证硬 Token 上限。采集不完整、模型变更、认证/额度异常或隔离失效时停止新派发；实际进程/工具未结束前保留占用，并保留失败成本。

## 5. A 组执行约束与提示词模板

运行前核实所选入口支持创建子 Agent、选择固定模型/强度、控制历史及读取子会话用量。以下是待填的实验提示词，不是现在执行的指令：

> 你负责本项目固定批次的轻量调度。项目、批次、worker 规范和最小核对入口见实验清单。
> 每次创建一个新子 Agent，只实施清单中的下一项；并发固定为 1。使用实验锁定的模型与推理强度，创建时显式不继承主会话历史，保留必要项目规则。子 Agent 不再派发子 Agent。
> worker 自行读取本项资料、认领、实现、测试、上报并落盘详细证据。最终回执不得超过 2 KiB。
> 主会话只发短指令、等待结束并调用最小核对。不得读取全量队列/日志或重新实施、评审本项；不要高频询问进度。
> 核对允许继续时派下一项；全部完成或受阻时按实验暂停规则结束。收尾只给计数与异常入口。

A 的批次内主会话保持同一个 ID；自动压缩照常记录。需要人工重开主会话属于实验结果中的介入，不悄悄当成从未发生。主会话每完成一项的可见新增文本长度单列统计，2 KiB 是字节限制而不是 Token 数量。

历史继承验证分两层：记录实际创建参数；在试跑主会话加入一个无业务意义的固定审计标记，只读检查子会话可导出的输入记录是否含该标记。不要额外询问子 Agent“是否记得”，以免污染测量。不可导出时标为未完全验证，不据此宣布历史绝对隔离。

## 6. Token 数据采集及去重

### 可用来源与前置核验

官方 exec JSONL 示例包含 turn.completed.usage，可报告 input_tokens、cached_input_tokens、output_tokens、reasoning_output_tokens；具体字段和累计范围以本机版本及试跑验证为准。[Codex 非交互执行](https://learn.chatgpt.com/docs/non-interactive-mode)

App Server 提供 thread/tokenUsage/updated，父子关联可从协作事件和会话 ID 记录，压缩可从 contextCompaction 条目观察。当前客户端是否能导出这些信息必须先验证；不要假定新启动一个观察进程就能收到别的桌面任务的全部实时事件。[App Server 事件说明](https://learn.chatgpt.com/docs/app-server)

本项目 scheduler 已保留原始执行事件，也会传递 run.modelSnapshot 的模型设置；尚需验证或补齐 A 组父子会话采集、Token 归一化和报告汇总。这份方案不声称现有看板已经提供完整 A/B 统计功能。

### 记录与归一化

每条用量记录至少保留：experimentId、round、arm、batchId、taskId、position、runId、threadId、parentThreadId、role、turnId/可用 requestId、时间、模型配置、原始来源、字段语义与原始事件引用。

role 区分 coordinator 与 worker。采集 B 的所有实施会话及续跑，A 除 worker 外还须采集主调度会话，包括开始、核对、汇总、失败和压缩期间的可观测模型调用。

- 先用试跑核对事件表示“单次增量”“本轮累计”还是“会话累计”。增量按唯一事件/请求计一次；累计只取同一范围的末值或边界差值，不能把每次累计更新相加。
- 用 threadId、turnId、事件类型和请求/序列标识去重。同一 usage 从 CLI、会话文件及 App Server 重复出现时选一个主来源，其他只用于核对。
- fork/恢复可能带入父历史和已有计数。先记录新工作开始前的基线，旧累计数字不重复计；本次请求确实再次输入的继承历史则必须计入，不能因文本重复而扣掉。
- 父会话统计是否已汇总子会话用量需要验证。已包含子会话时不能再相加；无法拆分时可报可信批次总量，但主调度占比标为未知。
- cached_input_tokens 通常是 input_tokens 的子集，不能再加一次。reasoning_output_tokens 是否已包含在 output_tokens 中须按实际 schema 归一化，避免重复计算推理。
- 重试、报错、取消的实际用量计入总量；中断后没有完整 usage 则标记该批统计不完整，不能当作零用量。压缩费用无法观测时也标记缺失范围。

公式中的 input 与 output 均指完成上述归一化后的增量，output 已统一为“含推理且不重复计数”的输出：

    T_A = A 主调度 input + output + 所有 A worker input + output
    T_B = 所有 B worker input + output
    Token 增幅 = (T_A - T_B) / T_B
    A 主调度占比 = T_A_coordinator / T_A
    缓存命中率 = cached_input / input
    每成功项用量 = 本组全部用量（含失败）/ 通过预定验收的项数

缓存输入仍计入原始 Token 总量。原始用量和成本分别展示；API 成本必须按实际模型及缓存计价计算，缺价格/缓存写入细分就不输出精确金额。账户额度百分比受其他任务和套餐规则影响，不能作为本实验 Token 主指标。

## 7. 上下文测量

上下文测量的是单次模型实际可用输入/占用，不能用累计 Token、日志文件大小或一次 turn 的累计 input_tokens 代替。一个 turn 可能包含多次模型请求。

按以下证据等级选择：

1. 有运行时明确的当前上下文/请求输入计量：保存值、分母（若有）和采样时刻，报告实测峰值。
2. 只有经验证的单次模型请求 input_tokens：以最大请求输入作为上下文压力代理，明确它未必等于完整窗口占用，尤其涉及隐藏/保留的推理内容时。
3. 只有可导出文本：使用匹配 tokenizer 估算可见文本，单列为估算值；隐藏提示、工具封装未知，不输出“精确上下文占用率”。
4. 只有 turn/会话累计用量：仍可做 Token 对比；上下文结论记为数据不足，不填零。

采样位置：

- A 主会话：启动后、每次派发前、每项回执与核对后、压缩前后、批次结束。
- A worker 与 B worker：初次模型请求、任务执行期间可观测峰值、每次恢复首个请求、结束前。
- 记录每个会话的压缩次数、第一次压缩发生在第几项，以及人工换主会话次数。

B 的“主调度聊天上下文”记为不适用；图表可表现为无此部分，但 B worker 上下文仍须展示。不同 worker 的峰值不能相加后与 A 主会话峰值比较。

输出三条随任务位置变化的曲线：A 主上下文、A worker 起始上下文、B worker 起始上下文。第 5 项与第 10 项的累计用量可作批次内检查点，不能当成相互独立的重复实验。

## 8. 完成质量、耗时和介入

每项开跑前冻结验收条件。由实验外的检查流程核对功能、固定回归测试、必要 UI 行为及报告真实性，不以 Agent 的“完成”文字、exit 0 或 report 本身直接判成功。

- 记录每项通过/失败/阻塞/未执行，及失败原因。成功率、整个批次完成率和新增回归均与用量一起汇报。
- 同项采用同一验收工具和规则；检查人员可用隐藏 A/B 标签的结果副本降低偏见。若要求补充修复提示，应两组遵循同一轮数政策，并计入人工介入和用量。
- 人工介入按原因统计：需求澄清、权限、模型/登录/额度、失败恢复、主会话重开、手动补发下一项。固定的一次初始启动单独记，不混入异常介入。
- 耗时分别记录整体墙钟时间、任务执行、排队/初始化、调度间隔及人工等待。两组串行，不能把其中一组改为并发后宣称调度更快。

如果一组因前面失败而少执行后续任务，原始总用量只描述实际花费；同时报告完成范围和每成功项用量，不能得出“较少的一组更省”的性能结论。只在两组均有结果的同项上做补充配对对比，并注明这种成功子集有选择偏差。

## 9. 分析方法与建议判定线

主比较单位是整批：分别给出 R1 和 R2 的 T_A/T_B、成功率、总时长、介入次数，再给合并总量比值。按轻/中/复杂任务展示明细，不能只算不加权百分比平均掩盖大任务。

10 项共享同一主会话，不是 10 个独立调度样本；两轮仅用于初步工程决策。报告两轮范围和是否同方向，不凭 40 次任务执行声称统计显著。若差异接近决策边界或两轮相反，增加独立成对批次；需要置信区间时按成对批次做重采样并披露样本量，不能按工具事件伪造大样本。

以下是可在开跑前调整的工程判定线，不是实测结论或产品性能保证：

| 条件 | 建议 |
| --- | --- |
| 两组完成质量相当，A 的 Token 增量在两轮均≤15%，10 项内无需人工重开主会话 | 有限批次可优先考虑 A 的桌面交互便利 |
| 增量在 15%～30%，或上下文/缓存结果差异明显 | 结合主调度占比、任务难度、缓存和介入成本评估；必要时增加配对批次 |
| A 增量>30%，或随着任务位置持续增加并出现人工重开/重复调度 | 持续无人值守优先 B |
| 任一组少做任务、模型不一致、采集缺失或关键回归更多 | 暂不做 Token 优劣结论，先解释质量与测量差异 |

A 初始上下文或子会话起始上下文异常大时，先核对历史继承、重复注入项目规则与日志回传。优化后应另起实验版本，保留原结果，不能只删掉“不好看”的试次。
