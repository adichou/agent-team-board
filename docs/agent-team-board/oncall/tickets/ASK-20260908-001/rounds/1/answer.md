# ASK-20260908-001 回复：为什么「驳回 / 接受」在网页上不能操作，反而要 ATB？

## 先说结论

「接受」「驳回接受」「确认完成」「驳回完成」这四个操作在设计上**都可以在 Status Board 网页上完成**。网页按钮和终端 ATB CLI 是**等价的两个人工入口**，并不存在「必须用 ATB」的限制。如果你在网页上找不到或点不了，通常是按钮入口位置、条目当前状态、或看板服务版本的问题，下文给出具体排查方法。

## 一、网页上这些按钮在哪里

1. **列表卡片**：只有「待接受（submitted）」状态的条目，卡片上才有「✓ 接受」「✎ 改标题」快捷按钮；待接受列表还支持多选后「接受所选」批量接受。
2. **详情页（点击条目打开的抽屉）**：**驳回类操作只放在详情页**，且按条目当前状态显示对应按钮：

   | 条目当前状态 | 详情页显示的按钮 |
   | --- | --- |
   | submitted 待接受 | ✓ 接受　✎ 改标题 |
   | accepted 已接受 | ↩ 驳回接受（退回待接受） |
   | in-progress 开发中 | ✓ 确认完成 |
   | done 已完成 | ↩ 驳回完成（退回开发） |

3. **事后撤销**：详情页操作后还支持撤销——「撤销接受」即驳回接受、「撤销确认完成」即驳回完成（只走状态机合法回退边）。

所以如果你是在**列表页**找「驳回接受」，确实找不到——请先**点击条目进入详情页**再看操作行。

## 二、为什么这些操作「仅限人工」（这是特性，不是缺陷）

看板的核心机制是人机分工：`accepted` 与 `done` 两个人工节点 Agent 无权触达，Agent 侧由 PreToolUse 钩子（`scripts/state-guard.mjs`）确定性拦截——无论 Agent 直写 `status.json`、跑 `atb status <ID> accepted|done`，还是 curl 调看板网页 API，都会被拒绝。因此「要 ATB 来操作」的真实含义是：**这类操作必须由人决定**；而人工有两条等价入口：

- Status Board 网页点按钮（`/board` 打开）；
- 或自己在终端执行 `node <插件>/scripts/atb.mjs status <ID> accepted|done`（驳回则 `atb status <ID> submitted`）。

两条路效果完全一致，网页不是「不能操作」。

## 三、网页上唯一被有意排除的流转

`accepted → in-progress`（认领）：网页端不承担认领，这是设计决定——认领由 Agent 执行 `atb claim <ID>`（或 `/dev`），自动进入 in-progress 并加原子认领锁（含 owner 会话、24h 过期）。除此之外的四条人工流转网页全部支持。

## 四、如果详情页也看不到按钮 / 点击报错，按此排查

1. **核对条目状态**：按钮严格按状态渲染（见上表）。状态不对就不会出现对应按钮。
2. **看板服务版本过旧（已知问题 BUG-20260907-017）**：看板 server 是常驻进程，路由集在进程启动时固化，而前端页面实时读盘。插件代码更新后，旧服务进程缺少新接口（「驳回接受」是 REQ-20260907-011 才引入的能力），在较新的前端上点按钮就会报「未知接口」。当前版本 `atb serve` 已能检测磁盘代码新于服务并自动重启；若仍异常，请手动重启服务（终端重新运行 `node <插件>/scripts/atb.mjs serve`），并强制刷新浏览器页面（避免缓存的旧前端）。
3. **确认打开的是本项目看板**：多项目场景下网页需指向正确项目（URL 带对 project 参数），且项目已 `atb init` 初始化。

## 五、如确认是缺陷

若按上述排查后按钮仍缺失或点击必现报错，那就属于看板自身问题。建议用 `/bug` 登记（附：条目编号与状态、所在页面位置、报错原文），由人工接受后派 Agent 修复。本咨询为只读回复，不直接改代码；若你希望「列表卡片直接提供驳回快捷按钮」这类体验改进，也可以 `/req` 提需求。
