# 「冻结后文档已被人工编辑，基线失效」是什么意思？

## 一句话回答

这是「需求完善（refine）」流程的**领取前复核保护**：批次创建时会给每个候选项的文档（README.md、design.md、test-cases.md、ui-demo.html）算一个内容哈希（sha1 指纹）作为「基线」并冻结在 batch.json 里；子 Agent 领取该项前会重算一次指纹，**若与冻结基线不一致，说明文档在冻结之后被改过，为避免覆盖人的修改，该项跳过不完善**，并落一条 skipped 记录，提示语就是这句话。代码位置：`scripts/lib/refine-store.mjs` 的 `nextRefineItem()`（第 651–653 行），`scripts/server.mjs` 的 `precheck()`（第 869–884 行）也有同口径复核。

注意「跳过」**不等于丢单**：条目本身仍是 accepted、未完善，文档原样保留，skipped 只是执行账本里的一条记录；下一次新建完善批次会重新冻结最新基线，该项会被再次领到（`atb refine create` 后即自动纳入）。

## 针对 BUG-20260908-018 这次的具体排查结论：是误报，文档其实没被人工编辑

我复算了指纹，确认这不是真的「人工编辑」，而是**指纹算法升级导致的假阳性**：

1. 冻结基线的算法是旧版：REQ-20260908-021 之前指纹只覆盖 3 个文件（README.md、design.md、test-cases.md）；该需求给 `DOC_FILES` 加了 `ui-demo.html`（`scripts/lib/refine-store.mjs` 第 43 行），算法变了，**同样的文件内容算出的哈希也必然变了**。
2. 实证：批次 RFB-20260908-010/011 里 BUG-20260908-018 的冻结基线是 `1be8550c…`，用**旧 3 文件算法**复算当前磁盘文件得到 `1be8550c…` 完全一致；用现行 4 文件算法算出的是 `dc34b10c…`。也就是说文档从创建（22:06:15）起就没改过，改的是「算法」。
3. 为什么会出现新旧算法混用：批次是 22:07:48 / 22:09:26 创建的，而 `refine-store.mjs` 在 22:03:50 就已更新——最可能是批次经一个**仍在运行、内存里还是旧代码的看板服务进程**（`atb serve`）创建并冻结了旧算法基线；而领取方 `atb refine next` 是新起的 node 进程，加载的是新代码，两边指纹口径不一致 → 判定「基线失效」。
4. 同批受影响的不止这一单：BUG-20260908-017 在两个批次里同样以该理由被跳过（其旧算法基线 `85980045…` 也已复算验证一致），共 4 条 skipped 记录。

## 影响与建议

- **无需修复数据**：两个条目仍是 accepted、文档完好，没有任何内容被覆盖或丢失；再建一个完善批次即可正常完善它们。
- **避免复发**：更新插件/代码后请重启看板服务（`atb serve`），确保「冻结基线」和「领取复核」跑同一版代码。server.mjs 里也已有类似警示（旧进程与更新后代码混用的问题）。
- 若希望从根本上解决（例如给指纹加算法版本号、或领取时检测到算法差异自动重冻基线而非判出局），建议另建需求（`/req`）处理，本次 oncall 未做任何代码改动。
