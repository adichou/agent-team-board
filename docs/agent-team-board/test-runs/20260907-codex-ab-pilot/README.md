# 2026-09-07 Codex A/B 合成任务试跑报告

本次试跑创建了两条隔离的合成需求，并完成四次实施：一条轻量任务 [P01](requirements/P01.md) 和一条中等任务 [P02](requirements/P02.md)，A、B 两组各执行一次。完整归一化字段见 [results.json](results.json)，实验方法见 [A/B 测试方案](../../codex-ab-test-plan.md)。

结论只适用于这次两项试跑：**A 组总 Token 为 B 组的 1.991 倍，高 99.1%**。A 的主调度会话单独消耗 289,829 Token，占 A 总量的 42.8%。两组功能验收均为 2/2；上下文压力代理的峰值接近，没有出现压缩或上下文爆炸。当前证据支持继续把后台独立会话作为长期无人值守的首选，但样本不足以给出稳定的总体百分比。

## 分组和控制条件

| 项目 | A：主调度＋新子 Agent | B：后台独立会话 |
| --- | --- | --- |
| 调度入口 | 一个 Codex 主会话 | 普通程序 |
| 每项实施 | 新子 Agent，`fork_turns=none` | 新 `codex exec` |
| 执行顺序 | P01 → P02，串行 | P01 → P02，串行 |
| 模型 | `gpt-6-astra` | `gpt-6-astra` |
| 推理强度 | `xhigh` | `xhigh` |
| CLI | 0.153.4 | 0.153.4 |
| 工作区 | 同一冻结基线的 A 副本 | 同一冻结基线的 B 副本 |
| worker 指令与验收 | 同一任务文本和固定检查 | 同一任务文本和固定检查 |

A 的两次创建调用均明确记录了 `fork_turns=none`、模型和推理强度。父会话审计标记只出现在父会话的可导出文本中，没有出现在两个子会话的可导出文本中。这能证明可见历史没有直接复制；它不能证明运行时不存在任何隐藏的系统上下文。

B 使用的是只负责串行启动独立 `codex exec` 的简单试跑程序，没有经过 Agent Team Board 的完整任务状态机。因此本报告能比较实施会话和主调度会话的用量，不能据此评估生产调度器的状态恢复、锁和进程回收可靠性。

## 结果

| 指标 | A | B | 差异 |
| --- | ---: | ---: | ---: |
| 计划 / 通过 | 2 / 2 | 2 / 2 | 相同 |
| input tokens | 671,174 | 336,265 | +99.6% |
| cached input tokens | 608,128 | 291,712 | 缓存输入已包含在 input 中 |
| output tokens | 6,759 | 4,233 | +59.7% |
| 总 Token | 677,933 | 340,498 | **+99.1%** |
| 每成功项 Token | 338,966.5 | 170,249 | +99.1% |
| 可观测模型请求数 | 31 | 16 | +93.8% |
| 活跃墙钟时间 | 328.952 秒 | 266.891 秒 | +23.3% |
| 单次请求 input 峰值 | 26,217 | 24,409 | +7.4% |
| 上下文压缩 | 0 | 0 | 相同 |

Token 按运行记录中的 `total_tokens = input_tokens + output_tokens` 归一化。`cached_input_tokens` 是 input 的子集，`reasoning_output_tokens` 是 output 的子集，两者都没有重复相加。

A 可拆为：主调度 289,829 Token，两个 worker 合计 388,104 Token。只比较 worker，A 比 B 高 14.0%；加上主调度后高 99.1%。本次主调度发出了 14 次模型请求，主要用于创建、等待、检查和收尾，因此调度层没有保持到预期的低调用次数。

| 任务 | A worker | B worker | A 相对 B |
| --- | ---: | ---: | ---: |
| P01 轻量 | 102,906 | 165,186 | -37.7% |
| P02 中等 | 285,198 | 175,312 | +62.7% |

同一任务的 worker 用量波动很大，说明两项样本无法估算稳定的 worker 差值。主调度额外用量则是 A 结构固有的新增部分。

## 上下文观察

日志没有提供“当前真实窗口占用”字段。本报告使用每次请求的 `last_token_usage.input_tokens` 作为二级代理，因此不能把累计 Token 当成上下文大小。

- A 主调度首次请求为 19,495，峰值为 21,682；处理两项后增长 11.2%，没有压缩。
- A 两个 worker 的首次请求均为 19,088，峰值分别为 21,290 和 26,217。
- B 两个独立 worker 的首次请求均为 19,068，峰值分别为 21,513 和 24,409。

这次试跑中，A 的主要代价是主调度反复调用产生的累计 Token，而不是两项之内的单次上下文峰值。更长批次仍需观察主调度曲线、压缩次数和重开次数。

## 验收与异常

两组都通过 `node checks/check.mjs P01` 和 `node checks/check.mjs P02`，任务文本、检查文件、项目规则和包配置的哈希保持一致。两组只修改各自允许的源码并生成不超过 2 KiB 的回执。

A 在两个 worker 和两次外部检查都完成后，主调度生成最终汇总时收到 `usage_limit_exceeded`，进程退出码为 1。实现仍判定 2/2 通过，但无人值守调度会把该批次识别为异常并需要复核。A 开跑时账户剩余额度少于 B，且 B 在额度窗口重置后才执行，因此这次异常不能用于判断哪种架构更稳定；A 的最终汇总用量也没有完整产生。

首次 A 启动还出现过一次网络预检失败：CLI 没有显式继承本机代理，请求在模型执行前超时，夹具未改变且没有可归一化模型用量。修正后 A、B 均显式使用同一个现有本机代理，该预检尝试从比较中排除。

## 决策与下一步

这次结果越过方案预设的 30% 判定线，方向上支持长期无人值守继续采用 B。A 仍适合用户希望在 Codex 桌面中观察父子任务、且批次很短的场景；若采用 A，应把主调度改为事件驱动等待并限制每项只做一次领取和一次完成核对。

正式结论需要执行方案中的两轮 AB/BA 主测：每轮每组 10 项，任务难度为 4 轻量、4 中等、2 复杂，并保证每组启动时额度足够。当前生产看板只有一项符合候选条件，所以本次没有创建、接受、认领或上报任何生产需求。
