# 设计 — REQ-20260914-004 优化需求说明、设计文档中右键讨论菜单生成的提示词

> 由 Agent 在 /dev 开发前补充，人可随时批注。

## 背景

右键「讨论」复制的自包含引用只解决「让 Agent 定位到文档位置」，未约定修改文件后的落盘与提交口径，
用户需在会话中反复口头补充要求。本需求在引用文本后追加「讨论要求」，把同轮 commit、
commit message 规范、回显提交信息三条指令固化进提示词。纯前端剪贴板文本优化：不改交互流程、
不新增后端 API、不写文件 / 记录、不改状态机。

## 方案

（技术选型、接口设计、影响面）

**自研说明**：纯文案字符串拼接改动（现有 `buildDocRef` 单函数组装），无合适开源库可引用，
引入库成本高于自研，不创建 licenses.md。

### 实现点

改动集中在 `scripts/web/app.js` 的 `buildDocRef`（约 4388 行）一处：

- 引用部分：首行前加分区标记「【文档讨论引用】」，其余要素（单号 / 文档名 / 源码行范围 /
  文档路径 / 有选中时的原文）逐项保留，行号口径（源码 1 基）不变。
- 空一行后追加「【讨论要求】请在本轮及后续讨论中遵守：」+ 四条编号指令：
  1. 围绕上方引用（文档路径 + 源码行范围）展开讨论与修改；
  2. 每轮回答中如需修改相关文件：修改完成后同轮同步执行 git commit，不留未提交改动；
  3. commit message 须包含：条目单号（动态取当前条目 id，如 REQ-20260914-004）、
     本轮用户问题摘要、本轮回答（改动）摘要；
  4. 每轮回答回显本轮 commit log 与 commit 号（短哈希即可）。
- 无选中时同样携带「讨论要求」，只是无「原文」节；整体为单次复制的纯文本。

### 「待确认」结论

1. **措辞与排版**：加「【文档讨论引用】/【讨论要求】」分区标记；指令为编号列表（1 条讨论
   范围 + 3 条 commit 指令）；条目单号示例动态取当前条目 id；注明 commit 号短哈希即可。
2. **覆盖范围**：`buildDocRef` 是三份文档页签（README.md / design.md / test-cases.md）与
   需求 / Bug 详情抽屉共用的唯一组装点，**同口径全部生效**（含 test-cases.md 与 Bug 单），
   不做按文档名拆分——拆分只增加分支复杂度，无收益。
3. **回显口径**：commit 号短哈希即可（完整哈希亦接受）；commit log 回显范围＝仅本轮新增提交。
4. **req-disc.js**：REQ-20260909-003「文档讨论」区块是另一套复制提示词，本需求标题限定
   右键讨论菜单，**不改动**；如需对齐另立需求。

### 影响面

- 复制链路其余环节零改动：`onDocCtxMenu` / `openDocCtxMenu` / `onDocCtxDiscuss` 只透传
  `buildDocRef` 产物；toast 摘要口径不变；自动复制失败时 `uiCopyBox` 只读 textarea 完整
  展示变长文本（8 行起步可拉伸，现状已支持）。
- 提示词对 Agent 的约束属约定层面，看板侧不校验、不追踪执行结果。
- 测试：新增 `scripts/tests/doc-ctx-discuss-req-20260914-004.test.mjs` 断言新格式；
  既有两份 doc-ctx 测试的 `buildDocRef` 断言经核验与新格式兼容（新「讨论要求」节不含
  「原文」字样，无选中断言仍成立），按需微调。

## 风险与边界

- 文本变长（约 5 行 → 约 12 行）：粘贴目标为 Agent 会话纯文本输入，无截断风险；手动复制
  弹窗可滚动查看，无布局风险。
- 追加内容不改动首行与「文档：」行的机器可读性（前缀追加只发生在其后），对已有按首行 /
  路径解析引用的消费方无破坏。
- 单一组装点共用意味着 Bug 单复制的提示词同样携带「条目单号（如 BUG-…）」动态示例，
  口径一致，符合结论 2。
