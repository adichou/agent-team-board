# REQ-20260909-015 需求或 Bug 方案设计时要牵引 Agent 尽可能复用网络上优秀的开源库，而不是重复造轮子

- 状态：accepted（已接受；实际状态以 status.json 为准）
- 创建：2026-09-09T12:52:29.710Z

## 描述

提出人原始诉求（两条）：

1. 开源库要引用，而不是复制代码到项目中。
2. 若使用了开源库，其 License 和仓库地址要在需求详细页面中单独页签展示，页签放在设计页签之后。只能使用开源友好的 License，避免陷入强制开源的境地。

拆成两条工作线：**A. 方案设计阶段的选型牵引**（让 Agent 优先复用优秀开源库、以依赖方式引用、只用开源友好许可）；**B. 条目详情页的开源信息展示**（新页签展示所用开源库的 License 与仓库地址，位置在「设计」页签之后）。

### 现状依据（基于当前代码，2026-09-09 核实）

- 详情抽屉页签：`scripts/web/app.js` `renderDrawer`（约 2196–2204 行）——固定「基本信息」+ `drawerDocTabs(it)`（`DRAWER_FIXED_DOC_TABS = ['README.md','design.md','test-cases.md']`，第 87 行；`test-report.md` 存在时作为附加页签排在其后，第 88–90 行）+ 末位「讨论纪要」；页签文案由 `DOC_LABEL`（第 77–82 行）管理。新增页签需扩展这两处。
- 文档加载链路天然可复用：`loadDoc`（app.js 第 2389 行起）走 `/api/item/:id/doc/:name` → `core.readDoc`（`scripts/lib/core.mjs` 第 1013 行，正则 `/^[\w.-]+\.md$/`，允许条目目录内任意 `.md` 文件名）；`orderedDocs`（core.mjs 第 989 行）已把四件套之外的 `.md` 一并列入 `it.docs`。即：条目目录新增 `licenses.md` 后，服务端读取与全文搜索（`searchDocs`）无需改动，仅前端缺展示页签。
- 方案设计指引落点（当前均无开源选型牵引）：design.md 模板 `reqDesign` / `bugDesign`（core.mjs 第 433 / 479 行，仅「背景 / 方案 / 风险与边界」骨架）；开发流程指引 `commands/dev.md` 第 2–4 步与 `skills/agent-team-board/SKILL.md`「TDD 开发流程」（第 97 行起）；批量执行 worker 提示词 `scripts/lib/scheduler.mjs` `buildWorkerPrompt`（约第 73 行起）。

### 目标口径

**A. 选型牵引（design 模板与流程指引）**

1. design.md 模板（`reqDesign` / `bugDesign`）「方案」节增加开源选型要求：动手自研前必须先评估「是否有成熟、维护中的开源库可复用」；有则优先引用；无合适库或引入成本明显更高（体量 / 许可 / 平台兼容）时方可自研，并在 design.md 写明理由——三选一不留空：引用了哪些库 / 无合适库的原因 / 引入成本高于自研的原因。
2. 「引用」的判定：以包管理器依赖方式引入（Node/Web 项目走 npm `package.json`；Apple 平台走 SPM / CocoaPods，按宿主项目技术栈），**禁止把开源库源码复制进项目仓库**；仅当库无包分发渠道且确需使用时才允许 vendor（内嵌源码），须在开源信息文档中标注复制范围与原因（此例外口径见「待确认 4」）。
3. License 合规白名单（开源友好、无传染性开源义务）：MIT、Apache-2.0、BSD-2-Clause、BSD-3-Clause、ISC、0BSD、Unlicense；MPL-2.0 等文件级弱传染许可是否放行**待确认**。GPL-2.0 / GPL-3.0 / LGPL / AGPL / SSPL 等强传染许可禁止引入；License 不明或仓库未声明的库不得引入。
4. 指引同步落点：`commands/dev.md`（读文档 / TDD 步骤）、`skills/agent-team-board/SKILL.md`（TDD 开发流程）、`scripts/lib/scheduler.mjs` `buildWorkerPrompt`，措辞以开发阶段 design.md 定稿为准。

**B. 开源信息展示（条目文档 + 详情页签）**

5. 条目目录新增 `licenses.md`（文件名见「待确认 1」）：由执行 Agent 在方案设计 / 实施阶段随 design.md 一并维护，以表格记录每个引入的开源库：库名、版本、引入方式（npm / SPM / vendor）、License（SPDX 标识）、仓库地址；未使用开源库的条目不创建该文件。
6. 详情抽屉页签：`licenses.md` 存在时在「设计」页签之后插入「开源许可」页签（口径同 `test-report.md` 附加页签：文件存在才显示，见「待确认 2」）；页签顺序变为 基本信息 / 说明 / 设计 / **开源许可** / 测试用例 / 测试报告（存在时）/ 讨论纪要。
7. 页签内容沿用文档页签渲染链路：首次激活经 `loadDoc('licenses.md')` 按需加载（加载占位）+ `docCache` 缓存回填 + 缺失空态 / 失效回落（REQ-20260909-006 口径）；表格按 Markdown 渲染。License 落在禁用名单（GPL / AGPL / LGPL / SSPL 等）的行给出醒目警示标识，白名单外未知许可给「待确认」标识——前端仅做展示层警示，是否加 CLI 硬校验见「待确认 5」。
8. 兼容性：与 REQ-20260909-013（隐藏「讨论纪要」页签）正交——「开源许可」插在「设计」与「测试用例」之间，不依赖讨论纪要页签存在；搜索命中 `licenses.md` 内容时经既有 `loadDoc(name, true)` 跳转链路切到该页签。

### 不改动

- 状态机与 status.json 协议；`/api` 现有路由语义（`core.readDoc` 文件名白名单天然覆盖新文档，服务端零改动）。
- 四件套（README / design / test-cases / test-report）的生成与渲染；`test-report.md` 附加页签口径不变。
- 既有条目不强制回补 `licenses.md`（新口径自本需求实施后的方案设计起生效，见「待确认 7」）。

### 待确认

1. 文件名 `licenses.md`（本 README 默认）是否合适（备选 `oss.md` / `open-source.md`）；是否需要 atb CLI 提供生成 / 校验子命令。
2. 页签展示策略：存在才显示（本 README 默认，同 test-report 口径）vs 固定显示 +「未使用开源库」空态。
3. License 白名单最终版：MPL-2.0 / EPL-2.0 等弱传染许可是否放行，由人工裁定。
4. vendor（库无包分发渠道时内嵌源码）例外是否允许；允许时 `licenses.md` 须标注哪些内容复制自哪个库及原因。
5. License 违规处理强度：仅界面警示（本 README 默认）vs `atb report` / 验收阶段硬校验拦截。
6. 指引落点是否包含批量执行 worker 提示词与 worker-spec（默认包含）。
7. 存量条目是否回补 `licenses.md`（默认不回补）。

## 交互行为

1. **页签切换**：点「开源许可」页签 → 首次激活经 `loadDoc('licenses.md')` 拉取并渲染（复用 REQ-20260909-006 的按需加载 + 缓存），再次激活命中 `docCache` 不重复请求；切走再切回内容保留。
2. **条件显示**：`licenses.md` 存在才渲染页签（同 test-report 附加页签口径）；条目数据轮询刷新后文件状态变化时，页签随下次 `renderDrawer` 增减；页签失效（如文档被删）回落「基本信息」（沿用 `drawerTabValid` 既有口径）。
3. **警示交互**：禁用许可的警示为纯展示层（红标 + 提示文案），不阻塞阅读；点击仓库地址按外链打开（沿用现有 md 渲染外链行为）。
4. **搜索跳转**：看板搜索命中 `licenses.md` 内容时，打开详情并切到「开源许可」页签（复用 `loadDoc(name, true)` 链路）。
5. **与相邻需求共存**：REQ-20260909-013 若实施（隐藏「讨论纪要」页签），页签顺序仍为 基本信息 / 说明 / 设计 / 开源许可 / 测试用例（/ 测试报告），互不影响。

## 状态反馈

- **正常**：页签点击即切，表格完整渲染，白名单许可无任何警示。
- **空**：`licenses.md` 未创建 → 页签不出现（默认口径）；若裁定固定显示口径，则页签内容区给「本条目未引用开源库」空态。
- **加载**：首次激活页签期间内容区显示「加载中…」占位，不闪空白。
- **失败**：文档请求失败 toast 报错（沿用 `loadDoc` catch），内容区不残留旧条目内容；License 警示（红 / 黄标）为内联标识，非错误弹窗。
- **警示**：禁用许可（GPL / AGPL / LGPL / SSPL 等）红色警示；未知 / 待裁定许可黄色「待确认」。
- 深浅色两种外观下页签行、表格、警示标识显示正常。

## 验收标准

**A. 选型牵引**

- [ ] design.md 模板（`reqDesign` / `bugDesign`）「方案」节含开源选型指引：优先复用开源库，自研须写明理由（无合适库 / 引入成本更高，三选一不留空）；新建条目生成的 design.md 即带该指引。
- [ ] `commands/dev.md`、`skills/agent-team-board/SKILL.md`（TDD 开发流程）、`scripts/lib/scheduler.mjs` `buildWorkerPrompt` 同步含「优先复用开源库、以依赖方式引入、禁止复制源码入库、仅用开源友好许可」的牵引表述（落点清单以 design.md 定稿为准）。
- [ ] License 口径落在指引中：白名单（MIT / Apache-2.0 / BSD-2-Clause / BSD-3-Clause / ISC / 0BSD / Unlicense）允许，GPL / LGPL / AGPL / SSPL 禁止，License 不明不得引入；白名单最终版以「待确认 3」人工裁定为准。

**B. 开源信息展示**

- [ ] 使用开源库的条目在条目目录维护 `licenses.md`，表格含 库名 / 版本 / 引入方式 / License（SPDX 标识）/ 仓库地址；未使用开源库的条目不创建该文件。
- [ ] `licenses.md` 存在的条目：详情抽屉在「设计」页签之后显示「开源许可」页签，页签顺序正确（基本信息 / 说明 / 设计 / 开源许可 / 测试用例 / 测试报告（存在时）/ 讨论纪要）；文件不存在时无该页签、无空占位与错位。

- [ ] 引入方式列能区分依赖引用（npm / SPM 等）与 vendor 复制；vendor 行附原因说明。
- [ ] 看板搜索命中 `licenses.md` 内容可跳转详情并切到「开源许可」页签（沿用既有文档搜索跳转链路）。
