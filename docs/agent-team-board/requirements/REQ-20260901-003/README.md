# REQ-20260901-003 钩子硬约束插件代码改动：必须先登记并认领条目

- 状态：submitted（待人工接受）
- 创建：2026-09-01T03:45:42.355Z

## 描述

问题：Agent 在获得用户口头同意后直接修改插件源码（曾实际发生并回退），纯规范（AGENTS.md、skill 文档）无强制力。目标：用 PreToolUse 钩子把「改动插件代码必须先走看板流程」升级为确定性约束。推荐方案 A：新增 code-guard 脚本（或给现有守卫加新模式），挂 Edit|Write 与 Bash 两个挂点：1) 守卫范围=插件源码根（以钩子脚本自身位置解析真实路径，兼容缓存软链）：scripts、commands、skills、hooks、.codex-plugin 及根级文件；豁免看板数据目录下的人读 markdown（允许直改，机器状态文件已有守卫）；2) 放行条件=该仓库看板存在未过期认领锁 .locks 目录下的锁文件（claim 已写 owner 与时间戳，O_EXCL 原子创建加过期接管，人工驳回即删，无需新令牌机制）；3) 无锁拒绝并提示正确流程（登记、接受、认领）；4) Bash 模式复用现有守卫的切段检测，拦 sed、重定向、tee 等改写源码路径。备选方案 B：仅 AGENTS.md 规范（无强制力，已被证不足）；方案 C：git 加 pre-commit（仓库非 git，且拦不住工作区改动，仅可作最后防线）。残留风险：Bash 花式绕过理论上可行，与现有守卫同级防护姿态（常规路径确定性拦截、绕过即违规）。开放设计点（对齐时定）：report 后是否释放认领锁（影响待确认期间能否继续修码）；是否按条目 design 影响面做文件级白名单（更强但更繁琐）；是否绑定会话身份。验收标准：1) 无认领锁时 Write/Edit/Bash 改插件源码被拦截并给出流程指引；2) 有效认领锁存在时放行；3) 看板数据目录 markdown 直改不受影响；4) 现有守卫行为与全部测试回归不破坏；5) 新增契约或功能测试覆盖拦截与放行两类路径。另：登记本条时发现现有守卫的 Bash 模式会把命令文本中同时提及看板目录与状态文件名的合法命令误拦（如本条首次登记），该误报应一并修复或另立 Bug。
