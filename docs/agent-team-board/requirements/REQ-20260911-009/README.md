# REQ-20260911-009 需求模块使用 dev 分支进行开发，每条需求或 bug 开发完到待测试状态都自动 commit

- 创建：2026-09-11T15:27:27.517Z
- 流程状态以系统维护的 status.json 为准。

## 描述

看板条目的开发工作固定在 dev 分支上进行，并把「开发完成进入待测试」与「提交进版本库」绑定起来，形成「dev 分支开发 + 到待测试自动 commit + 条目与提交互相索引」的闭环：

1. **项目初始化**：`atb init`（含看板网页初始化入口）时，若项目根还不是 git 仓库，按需自动 `git init`；随后在 main 之外按需创建 `dev` 分支（已存在则不重复创建），并把当前项目工作区自动切换到 dev 分支。
2. **已有项目**：Status Board「设置」页新增 git 分支初始化按钮，按需创建 dev 分支并把当前项目目录整体切换到 dev 分支。
3. **到待测试自动 commit**：每条需求或 bug 开发完上报、进入待测试状态时自动 commit——提交范围包含该单的业务代码、测试代码与需求相关文档；commit message 按现行规范书写（文字简洁、必须记录单号）。该提交在批量开发批次中执行，视同人工授权、不受 hook 拦截；hook 代码（`scripts/state-guard.mjs` 与 `hooks/hooks.json`、`hooks/codex.json`）须同步更新以纳入该授权口径。
4. **索引机制**：commit 与需求/bug 单建立索引机制，可从任一侧快速关联另一侧（单 → 该单全部提交；commit → 对应条目）。

### 已核实的现状

- `atb init`（`scripts/lib/core.mjs` 的 `initData`）与看板网页初始化接口 `POST /api/init`（`scripts/server.mjs`）目前只创建 `docs/agent-team-board/` 数据目录，不做任何 git 操作；数据目录定位优先取 git 仓库根（`gitRootFrom`），非 git 项目落在当前目录。
- Status Board 设置页（`scripts/web/app.js` 的 `paintSettingsView`、`scripts/web/index.html` 的 `#settingsView`）目前仅有「批量任务」一个分区（内含「完善完成后自动转入计划」开关）。
- 「待测试」= 条目 `in-progress` 且 `agentCompletedAt` 已置位（`atb report` 上报之后）；批量开发批次中经 `run receipt --result reported` 核验通过落账。
- 现行批量 commit 流程（`scripts/lib/commit-store.mjs`，CMT 批次）：人工创建批次派发子代理按单归因提交；消息规范为「类型: 描述 单号」（类型限 feat/fix/chore/doc/test，描述不含单号 ≤20 字），业务与测试代码（`scripts/tests/` 前缀）分开提交，条目目录文档归 doc 类，只 commit 不 push。
- 现行索引：`committedItemIndex`（条目 → 经核验的 commit hash 与批次号，看板「已提交」徽标数据源）与 `itemCommittedInGit`（git 历史消息含单号的幂等判定）。
- hook 现状：`hooks/hooks.json`（ZCode）与 `hooks/codex.json`（Codex）各配两条 PreToolUse 调 `scripts/state-guard.mjs`（file / bash 两模式），当前拦截面为 status.json 直写、人工专属状态命令、curl 人工 API、无有效认领锁改插件源码——**目前并不拦截 git commit**；「Agent 不自动提交」目前来自用户全局 Agent 规则（非 hook），批量 commit 流程靠「人工创建批次派发」获得显式授权。

### 待确认（开发阶段确定，不阻塞完善）

- 自动 commit 的触发点与执行主体：上报回执核验通过后由系统执行，还是子代理在回执前执行。
- hook 授权口径的实现方式（豁免标记如何传递与判定），以及是否同时新增「流程外 Agent 自动 commit」的拦截。
- 初始化自动 `git init` 是否需要开关（默认自动 vs 询问）；空仓库（`git init` 后尚无任何提交）创建 dev 分支的具体路径（先落首次提交或等价方案）。
- 设置按钮是否顺带为非 git 的已有项目执行 `git init`，还是仅提示引导走初始化流程。

## 界面布局

需求 2 的界面改动集中在 Status Board「设置」页签：在现有「批量任务」分区旁并列新增「Git 工作流」分区，沿用现有 `cx-config` 分区形态（标题、一句说明、内容块、操作工具栏与就近状态反馈行）与既有按钮、边框、深浅色变量，不引入新的弹窗容器类型。分区内容自上而下：

- Git 状态区（两行左右的信息行）：「当前分支：main / dev」「dev 分支：未创建 / 已存在」，附一行灰字说明（如「开发在 dev 分支进行，到待测试自动提交」）。
- 主操作按钮「初始化 dev 分支」，位于工具栏行；右侧同排放置状态反馈文字（与现有 `tsStatus` 同款就近反馈）。
- 确认操作复用看板现有确认弹窗形态；操作结果仅更新本分区状态行与反馈行，不整页刷新。

需求 3/4 无新增界面容器：自动提交沿用看板现有「已提交」徽标与条目详情展示，索引数据与徽标同源（详见状态反馈）。

## 交互行为

1. 进入设置页即加载当前项目 Git 状态（是否 git 仓库、当前分支、dev 分支是否存在）；加载期间按钮禁用。
2. 点击「初始化 dev 分支」→ 弹确认（说明将按需创建 dev 分支并把整个项目工作区切换过去）→ 执行中按钮禁用并显示进行中反馈 → 成功后状态区刷新为「当前分支：dev」「dev 分支：已存在」，按钮转为「已在 dev 分支」不可再点。
3. 幂等：项目已在 dev 分支时不执行创建/切换，仅提示已就绪；dev 分支已存在但当前在 main 时只切换、不重复创建。
4. 非 git 仓库项目：按钮禁用并提示「项目不是 git 仓库」（是否由按钮顺带 `git init` 见待确认），不出现可点击但必然失败的入口。
5. 执行失败（如工作区状态导致切换失败）：显示失败原因并提供重试；重试不重复创建已存在的分支。
6. 该按钮为人工网页操作，不经 Agent 权限通道，不触碰条目状态机。
7. 到待测试自动 commit（后台行为）：批量开发批次中条目上报核验通过后，该单的业务代码、测试代码与条目文档按现行分组规范自动提交（业务/测试分开、条目目录文档归 doc 类），消息含单号；提交后条目与 commit 建立索引，看板「已提交」徽标随之点亮。

## 状态反馈

- 正常：状态区显示「当前分支：main · dev 分支：未创建」，按钮可用；初始化成功后显示「当前分支：dev · dev 分支：已存在」并提示已切换完成。
- 空：非 git 仓库——状态区显示提示、按钮禁用；已在 dev 分支——按钮呈「已在 dev 分支」就绪态。
- 加载：状态查询期间显示加载占位并禁用操作；执行创建/切换期间按钮禁用并显示「正在创建并切换到 dev 分支…」。
- 失败：状态查询失败或执行失败显示具体原因与重试入口，不静默吞错，不改变仓库实际状态。
- 自动提交反馈：上报成功且自动提交完成后，条目获得「待测试」与「已提交」标记，索引可从条目查到提交列表；提交失败时改动保留在工作区并给出失败原因与重试口径，不丢失改动、不阻断其余条目处理；同一单重复上报不产生重复提交（幂等）。

## 验收标准

初始化与 dev 分支：

- [ ] 新项目经 `atb init`（含看板网页初始化入口）时，项目根不是 git 仓库则自动完成 `git init`；已是 git 仓库则跳过，不重复初始化。
- [ ] 初始化时按需创建 dev 分支（已存在则不重复创建），并把当前项目工作区自动切换到 dev 分支；初始化完成后当前分支为 dev。
- [ ] 空仓库等边界场景（`git init` 后尚无任何提交）有明确定义的处理路径并最终落到 dev，不因无初始提交而报错中断（具体方案见待确认）。
- [ ] 初始化过程只做本地仓库与分支操作，不 push、不改动远端配置。

设置页按钮：

- [ ] 设置页新增「Git 工作流」分区（布局/交互见上），展示当前分支与 dev 分支状态；点击按钮按需创建 dev 并把当前项目切换到 dev，成功后状态区刷新为当前分支 dev。
- [ ] 项目已在 dev 分支时按钮呈就绪态且不重复创建/切换（幂等）；非 git 仓库项目按钮禁用并给出明确提示，不出现可点击但必失败的入口。
- [ ] 创建/切换失败显示失败原因并提供重试，重试不重复创建已存在的分支，不静默吞错。

到待测试自动 commit：

- [ ] 批量开发批次中每条需求或 bug 上报进入待测试（回执核验通过）后，该单改动被自动 commit：业务代码、测试代码、条目相关文档一并纳入，分组沿用现行规范（业务与测试分开、条目目录文档归 doc 类）。
- [ ] commit message 符合现行规范「类型: 描述 单号」：类型限 feat/fix/chore/doc/test，描述简洁（不含单号 ≤20 字），单号（REQ-/BUG-）必须写入。
- [ ] 自动提交只 commit 不 push，不执行丢弃/还原/暂存无关改动的 git 命令，不影响其他单的未归因改动。
- [ ] 该提交视同批量批次内的人工授权：hook（`state-guard.mjs` 与 `hooks/hooks.json` / `hooks/codex.json`）同步更新后不拦截本流程发起的自动提交；「流程外 Agent 自动 commit」的拦截与豁免边界在同批 hook 更新中一并明确（口径见待确认）。
- [ ] 自动提交失败时改动保留在工作区并给出失败原因，可重试，不阻断批次内其余条目处理。

索引机制：

- [ ] 建立条目与 commit 的双向索引：从条目可查该单全部已核验提交（hash 与消息），从 commit 单号可反查条目；索引与看板「已提交」徽标展示同源。
- [ ] 幂等：同一单重复上报/重跑不产生重复提交（沿用「git 历史已含单号」判定或等价机制）。

通用约束：

- [ ] 不改变现有人机分工与状态机：自动 commit 不改变条目状态流转，accepted / planned / done 仍仅人工。
- [ ] 现有人工触发的批量 commit（CMT 批次）流程不回归；与自动 commit 并存时消息规范一致、索引同源。
