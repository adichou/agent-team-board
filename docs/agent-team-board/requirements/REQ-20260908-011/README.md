# REQ-20260908-011 修改单需支持修改标题和描述。

- 状态：submitted（待人工接受）
- 创建：2026-09-08T02:54:27.276Z

## 描述

需求 / Bug 登记时常因表述仓促需要回头修正，但现有「修改单」的直接编辑能力只覆盖标题，描述没有直接入口：

- 改标题（REQ-20260907-011 已交付）：仅待接受（submitted）条目可改，入口为卡片 / 详情抽屉的「✎ 改标题」按钮与 CLI `atb rename <ID> <新标题>`；保存后 `status.json.title` 与条目文档首行同步，history 留痕。
- 描述只能间接修订：用「修改」按钮（REQ-20260906-011）复制修改提示词粘贴到 Agent 会话等其改文档，或手动编辑条目目录下的 markdown。小改一个错别字也要走整套提示词流程，成本过高。

本需求把待接受条目的直接编辑能力扩展为**标题 + 描述一次改完**，并一并优化界面按钮文案——当前同一张待接受卡片上同时有「✎ 改标题」与「修改」两个近义按钮（后者实为复制修改提示词），用户难以区分，需借本次扩展统一理顺。

界面布局、交互与状态反馈：

1. **编辑入口**：待接受（submitted）的需求与 Bug（独立与归属）在卡片头部与详情抽屉操作区提供编辑入口，位置沿用现有「✎ 改标题」按钮处；非 submitted 状态不出入口（与现口径一致）。
2. **编辑弹窗**：点击打开页面内表单弹窗（与「＋ 新建」统一弹窗同范式，标题单行输入 + 描述多行文本域），两个字段均预填当前值：
   - 标题校验沿用创建 / 改标题规则：非空、不超过 120 字；标题未变而描述有变化时仍可保存（不得再报「与原标题相同」）。
   - 描述可多行编辑；清空的口径见 design.md（待确认项）。
   - 弹窗按钮「取消 / 保存」；Esc 与点击遮罩取消且不发请求；保存期间按钮禁用防重复提交。
3. **保存与反馈**：成功后 toast 提示，看板列表与详情抽屉标题即时刷新，描述写回条目文档对应章节（需求 → README.md「## 描述」节；Bug →「## 现象」节，Bug 口径待确认），history 留痕一条。失败时 toast 如实报错，弹窗内容保留可重试，不留中间态。
4. **按钮文案优化（待确认最终文案）**：编辑入口文案需明确覆盖「标题 + 描述」（候选：「✎ 改标题/描述」「✎ 编辑」）；近义的「修改」按钮同步更名（候选：「修改提示词」）以消歧；卡片与详情抽屉两处、aria-label / title 提示一并更新。
5. **CLI 对齐**：`atb rename` 用法保持不变；是否增加描述参数（如 `--desc`，多行经 stdin）待确认。

范围说明：讨论单（ASK，scripts/web/oncall.js 模块）没有「描述」字段口径且当前无任何编辑能力，默认不在本需求范围；如需支持另立需求（待确认）。

## 验收标准

- [ ] 待接受（submitted）需求与 Bug（独立与归属）可通过网页在同一个编辑弹窗中修改标题与描述；保存后 `status.json.title`、条目全部文档首行、README 对应描述章节三处一致更新，history 留痕。
- [ ] 仅改描述（标题不变）可保存成功，不触发「新标题与原标题相同」报错；仅改标题（描述不变）行为与既有改标题一致。
- [ ] 标题校验与创建时一致（非空、不超过 120 字）；标题与描述均无变化时明确提示无变化，不发写请求。
- [ ] 非 submitted 状态不出编辑入口，后端同口径二次校验并明确报错（与 `core.renameItem` 现口径一致）。
- [ ] 描述写回：需求写 README「## 描述」节、Bug 写「## 现象」节（Bug 口径如调整以 design 确认项为准）；章节缺失时明确报错，不模糊写入其他位置。
- [ ] 界面按钮文案完成优化并消歧：编辑入口文案明确覆盖标题 + 描述，与复制修改提示词的按钮不再混淆；卡片与详情抽屉两处同步更新（最终文案以人工确认为准）。
- [ ] CLI 与网页同口径（若确认纳入 CLI 描述参数）。
- [ ] 「修改（提示词）」「删除」「接受 / 驳回」等既有入口与交互不受影响；全部既有测试保持通过。
