# REQ-20260911-007 受阻待人工决策条目的承接机制：持久呈现、人工决策入口与复工通路

- 状态：accepted（已接受；实际状态以 status.json 为准）
- 创建：2026-09-11T14:43:46.066Z
- 提出背景：cam-media-man 项目 REQ-20260908-001 在批次 batch-20260908-001 中由 worker 完成首个切片后，因「缺人工确认首批平台、target、模块及覆盖率口径」交 blocked 回执（run-20260908-001），条目滞留 in-progress 三天无人发现，批量开发不再取到，最终靠人工翻 `dispatch/runs/` 目录才定位到原因。

## 描述

批量开发 / 单项开发中，worker 会遇到必须由人工决策才能继续的场景：范围与验收口径确认、方案取舍、外部账号或真机操作、排除项批准等。现行机制只有「交 blocked 回执然后结束」：条目留在 in-progress 等人工处置。但看板没有任何位置持久呈现这类「等人工决策」的条目，人工没有结构化的决策作答入口，补完决策后也没有把条目送回执行队列的通路——in-progress 在状态机中唯一出边是人工确认完成。结果是这类条目静默滞留，既不被批量开发取到，也没有待办视图提醒人工，成为流程黑洞。

本需求为「受阻待人工决策」建立完整承接闭环：**声明 → 持久呈现 → 人工决策 → 复工**。

### 已核实的现状与缺口

（2026-09-11 对插件 0.1.0 源码与 cam-media-man 看板数据的核实结论）

- worker-spec.md 规定 blocked 回执用于「依赖/信息缺失，可继续其他项」，reason ≤200 字，详情落 `dispatch/runs/<runId>/`；条目保持 in-progress 且无 report。受阻计数只在批次摘要（`batch check`）中短暂可见，批次 finished 后没有任何持久视图汇总「哪些条目在等什么决策」。
- 批量开发的派发判定只认 `status === 'planned'` 且无 owner；in-progress 条目永远不会被再次取单。
- 状态机中 in-progress 的合法出边仅有 done（人工确认完成）；不存在 in-progress → planned 的回退边，人工与 Agent 都无法把受阻单送回批量队列。可行的接手方式（换会话沿用原 owner 名续认）只是实现细节（core.mjs claim 对同 owner 幂等放行），未在任何用户可见文档中说明，不可发现、不可操作。
- 批次 needs_attention 仅由 failed 且 `safeToContinue=false` 触发（环境级失败 → 项目暂停，人工经 Status Board「暂停→恢复」解除），不覆盖「等人工决策」。
- oncall 咨询单（REQ-20260907-001）面向 Agent 客服答疑（`answer --mode zcode|codex`），不改变条目状态、没有复工语义，不能替代本需求。
- `dispatch/policies.json` 的 dependsOn 只表达条目间依赖（depBlocked → 派发受阻），无法表达「依赖某项人工决策」。

## 期望机制（目标口径，具体形态见「待确认」）

1. **声明**：worker 阻塞时能显式声明「需要人工决策」（与一般受阻可区分），附决策问题清单与详情记录入口；声明落盘、可追溯。
2. **呈现**：Status Board 与 CLI 都有持久的「待人工确认」聚合视图（不随批次结束消失）：条目、提出时间、未答决策项、详情入口。
3. **决策**：人工在结构化入口逐项作答/确认口径；决策内容写入条目文档（README/design.md 或条目内决策记录），留痕可追溯。
4. **复工**：决策补齐后，人工一次操作即可让条目回到可执行状态（进入 planned 队列被批量开发重新取单，或等价通路），流转留痕；不要求人工手改 status.json，不破坏「accepted/planned/done 仅人工」铁律。
5. **防呆**：待人工确认期间条目不被其他开发入口误认领；未补决策的条目被人工确认完成前需显式提示（拦截或二次确认）。

### 布局

- Status Board 既有看板列（待接受 / 已接受 / 已计划 / 开发中 / 待测试 / 已完成）保持不变；「等人工决策」的条目仍按其真实状态（in-progress）留在「开发中」列，仅追加「⚠ 等人工决策」角标，不新增看板列。
- 看板列之下新增持久聚合区「⚠ 待人工确认（N）」——不随批次结束消失。区内逐条呈现卡片：条目 ID + 标题 + 状态 chip（in-progress · 等人工决策）、已等待时长、待决问题清单与计数（已答 ✓ / 未答 ○ 逐项可见）、操作行（查看进展记录 / 补决策 / 复工 / 确认完成）。
- 「补决策」打开侧拉式决策表单：每个决策项一行（问题 + 作答控件 + 补充说明），底部「保存决策」按钮，顶部就近提示条；表单打开时先读取决策项再可编辑。
- 「查看进展记录」在卡片下方展开对应 `dispatch/runs/<runId>/` 的进展时间线（blocked 回执原因、详情入口）。

### 交互行为

1. worker 声明需人工决策后，该条目进入「待人工确认」聚合视图，显示等待时长与未答项计数；其在看板原列的呈现规则不变。
2. 「查看进展记录」打开对应 `dispatch/runs/<runId>/progress.md`（或条目内等价记录）。
3. 「补决策」打开决策表单，问题逐项作答、支持补充说明；保存后决策内容落入条目文档并刷新计数。允许保存未答完的草稿，但复工入口保持禁用并提示缺项。
4. 「复工」仅在决策项齐备后可用；人工点击后条目按待确认口径回到 planned（或等价可派发状态），历史留痕。与人工「确认完成」冲突时以人工显式选择为准。
5. 待人工确认期间，其他开发入口（batch next、claim）对该条目的行为保持确定性：要么明确拒绝并指向待确认原因，要么按设计放行并在视图中原样呈现，不得静默产生第二实施者。
6. 防呆：卡片同时保留人工「确认完成」入口，但条目仍有未答决策项时须先经显式二次确认（「尚有 N 项决策未答，仍要确认完成吗？」），不静默放行。

### 状态反馈

- 正常：待确认区显示条目、等待时长、未答计数；补决策与复工结果即时刷新并 toast 提示。
- 空：无待确认条目时该区整体隐藏（或显示空态文案），不占版面。
- 加载：待确认清单与决策表单读取期间显示加载态、禁用提交，保留关闭入口。
- 失败：清单加载失败显示错误条与重试入口；决策保存失败保留输入并提示可重试；复工失败显示原因（如条目状态已变化），不静默变更任何状态。

### 演示核对路径

1. 默认正常态：看板六列下方出现「⚠ 待人工确认（2）」，两张卡片各显示等待时长与待决清单计数；「开发中」列对应迷你卡带「⚠ 等人工决策」角标。
2. 点「查看进展记录」：卡片下展开模拟进展时间线（含 blocked 回执原因与 runId 详情入口）；再点收起。
3. 点「补决策」：表单先短暂「正在读取决策项…」（期间提交禁用、可关闭）；部分作答后「保存决策」→ 提示「草稿已保存，尚缺 N 项」，卡片计数同步刷新、「复工」保持禁用；切「保存失败」场景再保存 → 就近失败提示、输入保留可重试。
4. 全部作答并保存 → 计数归零、「复工」启用；点击 → 复工中 → 卡片移出待确认区、「开发中」迷你卡移入「已计划」列、toast 留痕；切「复工失败」场景 → 显示「条目状态已变化」等原因，状态不被静默变更。
5. 有未答项时点「确认完成」→ 显式二次确认拦截（防呆）；切「空」→ 空态文案；「加载中」→ 骨架占位；「加载失败」→ 错误条 + 重试，重试后回正常。
6. 深浅色切换：演示页整体适配，验证两种主题下均可用（可选项，仅演示用途）。

## 待确认

- 机制形态：新增独立状态（如 pending-confirmation）vs 保持 in-progress + 独立决策账本（类似 refine 三态的执行层索引，不动状态机）——后者风险更低，倾向后者。
- 复工目标：回到 planned 全局队列由后续批次取单 vs 续用/重开原批次重试该条目（REQ-20260908-026 已有 retry 标记机制可参考）。
- 决策记录载体：条目目录内独立文件 vs 追加 design.md 决策章节 vs 复用 oncall 咨询单绑定条目。
- 与 oncall 的分工：是否由 oncall 承载问答流程，本需求只补「声明、呈现、复工」三段。

## 验收标准

- [ ] worker 能显式声明「待人工决策」并附问题清单；与一般 blocked 受阻在看板和 CLI 中可区分，声明与答复全程留痕。
- [ ] Status Board 持久展示待人工确认条目（原因/问题、等待时长、详情入口），批次结束后仍可见；CLI 提供等价清单命令。
- [ ] 人工决策有结构化入口，作答内容写入条目文档并可追溯；支持草稿与缺项提示。
- [ ] 决策补齐后人工一次操作复工：条目回到可被批量开发取单的状态（或等价通路），状态流转留痕，全程无需手改 status.json。
- [ ] 存量滞留单（如 cam-media-man REQ-20260908-001）能用新机制登记并承接，不需要人工改历史数据文件。
- [ ] 不破坏状态铁律：accepted/planned/done 仅人工；Agent 写 status.json 仍被钩子拦截；既有 blocked/failed 回执语义与历史数据向后兼容。
- [ ] worker-spec、agent-team-board skill 文档、batch-execution.md 同步更新，新机制在批量与单项（/dev）两条路径下均可用。

## 非目标

- 不改变 blocked/failed 回执的既有语义，不迁移重写历史回执数据。
- 不让 Agent 代替人工作出决策或自动复工。
- 不替代 oncall 咨询看板的 Agent 答疑能力。
- 不引入实时推送/通知渠道（邮件、webhook 等），呈现以 Status Board 与 CLI 为准。
