# 批量需求开发说明：Zcode 与 Codex

文档日期：2026-09-06（2026-09-08 随 REQ-20260908-010 更新：更名「批量开发」、新增「已计划」状态与统一开发启动）。状态：方案已选定、需求已登记，功能尚未实现或验收。文中的新增按钮、命令和协议均为目标设计，不能当作现有能力调用。

## 1. 选定方案与需求入口

| 工具 | 选定方案 | 需求 |
| --- | --- | --- |
| Zcode | 用户手动新建一次调度会话；主会话只启动新子 Agent、处理短回执；每个子 Agent 自行选单并只实施一项 | [REQ-20260906-002](requirements/REQ-20260906-002/README.md) |
| Codex | 看板服务用普通程序持续调度，每项需求直接后台启动独立 Codex 会话，保存日志、结果并管理进程 | [REQ-20260906-003](requirements/REQ-20260906-003/README.md) |

两条需求均为 `submitted`，需要人工在 Status Board 接受后才能认领开发。登记文档不代表已开始实施。

| 对比项 | Zcode | Codex |
| --- | --- | --- |
| 用户启动动作 | 任务模块「开发启动」选 zcode：创建批次并复制提示词，用户在 Zcode 当前项目的新会话中发送 | 任务模块「开发启动」选 codex：开启当前项目的 Codex 自动派发 |
| 调度者 | Zcode 主会话 | 看板后台程序 |
| 执行单位 | 每项一个全新的通用子 Agent | 每项一个新的 `codex exec` 会话 |
| 主聊天上下文 | 每项累积少量派发记录、回执和核对结果 | 无主调度聊天上下文 |
| 工作记录 | 条目文档、批次执行记录；Zcode 子 Agent 返回摘要 | 条目文档、执行事件、标准错误日志、最终回复 |
| 自动接收后续新增需求 | 批次运行中新置计划的条目自动并入队列 | 自动派发开启期间继续接收新置计划的条目 |
| Terminal 窗口 | 无需通过终端打开 Zcode | 后台启动，不打开 Terminal 或生成 `.command` 来拉起窗口 |
| 桌面原生任务列表 | 不承诺每个子 Agent 都成为独立顶层任务 | 普通 `exec` 会话默认不进入桌面侧栏 |
| 中断恢复 | 新调度会话读取批次摘要，核对旧子 Agent 后续接 | 服务重启先核对执行记录，再按明确的会话 ID 恢复同一项 |

## 2. 两条路径共同遵守的业务规则

1. 需求与 Bug 使用状态机：`submitted → accepted → planned → in-progress → done`（planned = 已计划，人工置计划/移出计划，REQ-20260908-010）。只有人能接受、置计划和确认完成；Agent 通过 `atb claim`、`atb report` 认领和上报，不直接修改条目的 `status.json`。
2. 只从 `planned`（已计划）中选择新工作，按创建时间最旧优先（Bug 与需求同序）。accepted 不再被自动派发，需人工「移入计划」排期。父子归属不自动等同于执行依赖。已被认领的条目只进入原执行的恢复流程，不能作为新任务派发。
3. 每个项目同一时间只允许一个实施任务，Zcode、Codex 和手工 `atb claim` 共用实施互斥检查。不同路径指向同一项目时，按规范化真实路径识别同一个项目。
4. 完成一次 `report` 后即可释放实施占用并处理下一项；该条目仍为 `in-progress`、待人工验收。等待验收不占用实施并发名额。
5. 测试报告必须区分已验证、未验证和阻塞项。进程退出、子 Agent 的一句“完成”、一次 `turn.completed` 都不能单独证明需求已完成。
6. 独立会话不等于独立代码副本。首期共享工作目录、串行执行，尊重现有改动，不自动清空工作区、切换分支、丢弃改动或提交代码。失败遗留改动是否允许继续必须明确判定；无法判断时暂停该项目。
7. 调度记录是执行账本，条目状态仍以看板为准。恢复时交叉核对，不能依据一份旧回执自动重派、抢锁或伪造上报。

## 3. Zcode 使用流程（实现后）

1. 在看板接受本批条目，并补清前置依赖。
2. 打开任务模块「开发启动」，选择 zcode 模式（或进入“Zcode 批次”子面板）。批次创建冻结当前全部可实施候选（REQ-20260908-019 起不再有上限设置；运行中新置计划的条目自动进入队列）。
3. 点击“创建批次并复制提示词”。批次冻结当前已计划条目范围，运行中新置计划的条目在领取时自动并入（实时获取）；完整清单留在文件中，复制内容只包含项目、批次标识、执行规范路径和短指令。
4. 在 Zcode 手动新建项目会话并粘贴发送。只有收到运行登记后，看板才把批次从“待启动”显示为“执行中”。复制成功不算启动成功。
5. 主会话每轮只启动一个新子 Agent。子 Agent 读取必要规范、批次记录和条目文档，自行选择、认领、实施、测试并上报一项，然后结束。
6. 主会话收到短回执，调用最小核对入口，获得 `continue`、`stop` 或 `needs_attention`。主会话不读完整队列、源代码、测试日志或整个报告。
7. 批次范围已处理或全部受阻时停止，不空轮询等待未来条目。报告在条目详情中查看；失败和跳过清单按需查看，不逐轮追加到聊天。

“暂停后续”只阻止领取下一项。Zcode 中已经运行的工具，需在 Zcode 原生界面停止；看板不能把“已请求暂停”显示为“当前执行已终止”。Zcode 退出、子 Agent 失联或主会话更换时，先核对旧执行，再续接批次。

### 尽量减少主会话上下文

- 把选单也放到子 Agent；主会话不反复输出完整 `atb list --json`。
- 详细执行规范放到独立 worker 文档或 Zcode 支持的子 Agent 定义中，主会话只传路径与当前标识。
- 对新子 Agent 提供本项必要资料，不主动附带过去各项的完整聊天。运行时可能注入项目指令或父会话信息，不能仅凭提示词承诺完全不继承历史。
- 每项只发最终回执；长错误堆栈、测试输出、实现分析和覆盖率细节全部落盘。正常情况下不反复轮询子 Agent 进度。
- 主会话能读取的调度摘要只含当前项、数量、下一步和报告引用，不含累积的完整历史列表。
- 保留项目指令、权限和状态守卫；节省的是无关业务历史及重复输出，不通过关闭必需约束来缩小上下文。

首期以 10 项模拟批次测量主会话接收到的实际工具输入输出；把字节数与“直接把完整日志回传”的基线对比，不虚构 token 节省百分比。Zcode 原生系统消息和工具封装可能额外占用上下文，报告应说明可观测范围。主会话仍按项增长，系统压缩或人工重开后依靠文件续接。

## 4. Codex 使用流程（实现后）

1. 在“批量开发 → Codex 自动派发”完成运行环境检查，确认 CLI、模型配置、登录、项目读写与所需工具可用。默认关闭，不因置计划就擅自启动。
2. 用户「开发启动」（codex 模式）后，看板服务串行从已计划队列取单（最旧优先，实时获取）。使用 CLI 路径、参数数组、明确工作目录直接启动 `codex exec --json`，输入本项提示词；不调用 `open`、Terminal、AppleScript 或 `.command`。
3. 不同条目各自创建新会话；同一条目需要多轮或故障恢复时，只使用已记录的会话 ID 继续。不得用 `resume --last` 作为调度定位方式，也不通过 fork 继承上一项历史。
4. 服务持续保存事件与错误日志；看板展示当前条目、运行阶段、报告、最终回复和失败原因。没有收到日志不能直接推断进程已死或任务已完成。
5. 只有满足本次执行的完成证据、`report` 关联及进程/工具收尾条件后，才释放项目实施占用并启动下一项。
6. 关闭“自动派发”停止领取新任务，当前任务默认继续。显式“停止当前执行”才取消当前项；界面先显示“停止中”，确认停止后再显示“已中断”。

### 不堆积终端或失控进程

正常结束、用户取消、超时、启动失败和服务关闭都需要明确的收尾分支。只终止本调度器确认为其所有的进程与任务，不能按程序名杀掉用户的所有 Codex 会话或共享 app-server。

先请求中断，等待宽限期，再对仍存活且身份一致的受管进程执行强制回收。进程 ID 需结合启动时间、运行标识和归属校验，防止 PID 复用。CLI 退出后仍要核实它启动的工具或服务端 turn 已停止；收尾未确认时保留项目占用并提示人工处理，不立刻派下一项。

关闭浏览器标签不影响独立运行的看板服务。若 Electron 壳拥有后台服务，退出壳前必须协调停止及落盘；若壳只是连接已有服务，关闭壳不能杀死外部服务。电脑休眠、重启或断网不等于工作仍在执行，恢复时需重新核对。

### 桌面结果可见性

首期必须在 Status Board 查看每次执行的事件、最终回复、报告及错误原因。普通 `codex exec` 会话虽然能保存记录，本机桌面版的默认侧栏列表未包含它们。

“在 Codex 桌面打开”不是已接通的能力：只有对应运行路径通过桌面可见性实测后才显示可用入口；未支持时显示“桌面入口未接通，请查看看板日志”。不能仅有会话 ID 就声称桌面可见，不能伪造会话来源绕过列表过滤。独立桌面任务创建与集成可后续扩展，不阻塞本次后台调度的核心交付。

## 5. 共用执行协议（拟新增）

两条需求共用以下协议，首个实施者落地，后续复用。推荐按 Zcode、Codex 顺序实施；两者无必须互相完成的业务依赖，共享源码变更必须串行协调。

### 存储与标识

拟在 `docs/agent-team-board/dispatch/` 保存 `settings.json`、`policies.json`、`batches/<batchId>/` 和 `runs/<runId>/`。具体子文件见两条需求的 design。批次、执行尝试、条目分别使用 `batchId`、`runId`、既有 REQ/BUG 编号，三者不能混用。

执行占用使用原子获取的项目锁和条目认领锁。独立执行记录至少有：项目真实路径、执行器、条目编号、owner、尝试次数、批次、时间、会话 ID（未知时为 null）、运行阶段、取消请求、报告引用和恢复原因。Codex 另存进程归属信息。运行时记录与大日志不默认纳入版本控制，README/design/test-cases/test-report 继续作为可审阅文档保留；扩展局部忽略规则时不得误排除现有需求文档。

所有执行账本由受控 CLI/服务函数维护，Agent 不随意手写 JSON。保存采用原子替换或追加日志，恢复后按序核对。新增命令的名字可以在实现时调整，但不能把尚未实现的入口写成当前可执行指令。

### 依赖与互斥

首期依赖规则保存于单独的执行策略文件，字段为 `dependsOn: [真实条目编号]`，默认要求这些条目已由人工置为 `done`。详情中的“批量执行设置”提供依赖编号选择与说明，保存时校验存在性、自依赖和环；未配置时不从父子归属推断依赖。人工文档存在尚未结构化的依赖时，worker 上报阻塞，不自行忽略。

一个项目只运行一个调度模式：Zcode 批次或 Codex 自动派发。模式冲突显示持有者和当前项，不静默抢占。手工实施也需经过统一的 `atb claim` 互斥检查；已有 `in-progress` 且无本次有效上报的未知执行，要核对后再放行。Zcode 不存在可用于外部可靠判断生死的进程 ID 时，不以“心跳过期”单独认定可以接管。

### 状态与回执

运行阶段可使用 `reserved`、`starting`、`running`、`reported`、`blocked`、`failed`、`interrupted`、`cleanup_pending`；这些属于执行账本，不能写入条目 `status`。空队列是调度结果，不创建虚假的条目或成功执行。

回执示例（字段含义为协议，不是已有 CLI 输出）：

```json
{"version":1,"batchId":"batch-example","runId":"run-example","itemId":"REQ-YYYYMMDD-NNN","result":"reported","reportRef":"item-test-report"}
```

```json
{"version":1,"batchId":"batch-example","runId":"run-example","itemId":"REQ-YYYYMMDD-NNN","result":"blocked","reason":"依赖未验收","safeToContinue":true}
```

worker 回执及主会话核对响应分别限定为 UTF-8 编码不超过 2 KiB；错误正文单独落盘，不能通过直接截断 JSON 得到畸形回执。调度核对响应只包含当前执行、计数、异常引用和 `nextAction: continue|stop|needs_attention`，历史清单分页或按需读取。正常情况下每项只产生一份最终回执和一次最小核对。

`reported` 必须能关联本次 `runId`、owner、条目、报告文件与新的上报时间，排除旧报告误用；需通过受控上报入口扩展执行关联字段，不让 worker 直接修改 `status.json`。核对摘要只能证明记录一致，不能替代真实测试或人工验收。

### 失败与重试

未认领前的冲突可重新选单；环境级错误（登录/额度/必需工具不可用）暂停项目或执行器，不能把整批条目逐一领取后标失败。网络等可恢复故障默认最多自动重试 2 次，采用退避并记录尝试；实际重试前核对原进程/子 Agent、条目 owner 和工作区改动。实施失败或信息不足，不无条件重跑；转人工处理后可继续其他不受影响的条目。

不能仅凭锁超时自动切换 owner、将 `in-progress` 改回 `accepted`，或把另一会话的工作当成本次成功。已知会话恢复与新建执行分别记录，防止服务在“已创建会话但尚未保存 ID”的窗口崩溃后产生重复实施。

### 待人工决策承接（REQ-20260911-007）

blocked 回执适用于「依赖/信息缺失，可继续其他项」，但「必须由人工决策才能继续」（范围与验收口径确认、
方案取舍、外部账号或真机操作、排除项批准等）只交回执会让条目静默滞留 in-progress——不被批量取单、无待办
视图提醒。为此建立 **声明 → 持久呈现 → 人工决策 → 复工** 的承接闭环：

- **声明**：worker `atb hold declare <ID> (--question 决策问题)… [--reason 短句] [--run RUN-ID]` 显式声明
  待人工决策并附问题清单，随后仍按既有协议交 blocked 回执（声明与回执正交，历史语义零改动）。声明落
  `holds/holds.json`（执行账本，不进版本控制，不写条目 status.json），条目状态保持 in-progress；
  存量滞留单可由人工补登记（不要求 --run）。
- **呈现**：Status Board 需求列表下方持久聚合区「⚠ 待人工确认（N）」（不随批次结束消失；卡片含等待时长、
  未答清单、进展时间线入口），开发中列表行带「⚠ 等人工决策」角标；CLI 等价清单 `atb hold list` / `atb hold show`。
- **决策**：人工在聚合区「补决策」侧拉表单逐项作答（支持部分作答草稿，缺项时复工禁用并提示），或终端
  `atb hold answer <ID> --q q1 --text 答复`。作答与事件全程留痕写条目目录 `decisions.md`（随代码进 git）。
  作答为人工专属：Agent 的 CLI/HTTP 调用被 state-guard 确定性拦截。
- **复工**：决策齐备后人工一次操作 `atb hold resume <ID>`（或聚合区「复工」按钮）——条目经专用通路
  in-progress → planned（清 owner、释放认领锁、history 留痕；不进通用状态机边），回到已计划队列被批量开发
  重新取单（batch next 实时吸收新置计划条目）。
- **防呆**：待决期间 `atb claim` 对该条目一律拒绝（含原 owner 续认），指向待确认原因；确认完成遇未答项默认
  拦截，人工显式二次确认（终端 `--force` / 网页确认弹窗）可越过并留痕闭环；答完即确认则自动闭环。
- **作废与多轮**：`atb hold cancel` 作废当前声明（条目状态不变，按其他方式处理）；复工/作废/闭环后再声明
  开新一轮，旧轮归档保留于 decisions.md 历史轮次。
